# Design

## Context

TimeGenie 当前把事项实际时间建立在 `time_entries` 与 `time_allocations` 的非负分钟汇总上。普通补录只能增加时间，记录还要求可解释的开始、结束区间，因此无法自然表达“把今天最终实际从 60 分钟调成 45 分钟”这类负向修正。计划页、今日概览、日报、趋势和工时导出又分别读取实际分钟；如果只在某个页面追加计算，容易产生口径不一致。

本变更在计划页增加批量调整入口，以面板打开时的实际快照计算固定差额。正在计时或暂停的事项仍可调整，之后新增的计时与本次固定差额独立叠加。调整必须可追溯、可撤销、支持本地事务和多设备同步，且不得篡改原始计时、普通补录或分配记录。

## Goals / Non-Goals

**Goals:**

- 让用户按当前主体集中设置各叶子事项“今天最终应该是多少分钟”。
- 将正负差额保存为独立、可审计、可软删除的实际调整记录。
- 保证计划页、今日概览、日报、趋势和导出使用同一最终实际口径。
- 批量保存具备事务性、幂等性、结构与调整基线冲突保护。
- 调整记录接入现有本地优先和云同步链路。

**Non-Goals:**

- 不修改或重写原始计时、普通补录和工时分配记录。
- 不允许直接编辑已保存的调整；修正方式为删除旧记录后重新调整。
- 不调整父事项；父事项只展示叶子后代汇总。
- 不把普通计时增长视为冲突，也不承诺保存后最终值仍等于输入目标。
- 不在今日概览页复制完整批量调整能力。

## Decisions

### 1. 使用独立的实际调整实体

新增 `actual_time_adjustments`，而不是放宽 `time_entries` 或 `time_allocations` 的非负约束。建议字段包括：

- `id`、`workspace_id`、`subject_id`、`task_id`、`work_date`。
- `delta_minutes`：非零有符号整数。
- `baseline_minutes`、`target_minutes`：保存用户确认时看到的语义。
- `note`、`source_type`（固定为 `quick_actual_adjustment`）、`batch_id`。
- `created_at`、`updated_at`、`version`、设备来源字段、`deleted_at`。

该模型不伪造时间区间，不改变待分配分钟，也能直接表达负向修正。调整前快照和目标值仅用于审计；实际汇总以 `delta_minutes` 为准。

备选方案是把负数写进现有分配表，或创建虚假的负时长时间记录。前者破坏现有非负约束并混淆待分配语义，后者无法形成有效时间区间，均不采用。

### 2. 面板读取稳定快照，提交固定差额

新增按“主体 + 工作日期”读取的调整快照。返回事项树、叶子资格、事项版本、原始分配分钟、有效调整合计、最终实际、调整基线指纹、完成状态/日期和计时状态。

前端把叶子目标初始化为打开时最终实际，并计算：

`delta_minutes = target_minutes - baseline_minutes`

父事项当前合计和目标合计都由叶子后代推导。普通计时在面板打开后增长时，不重算本次差额；保存成功后重新读取最新数据。因此打开时 30、目标 45 对应固定 +15，即使保存前又计时 5 分钟，保存后最终值也可以是 50。

### 3. 使用专用批量命令原子校验与保存

批量保存请求包含 `subject_id`、`work_date`、`client_request_id`、`batch_id`、统一备注，以及每个变化叶子的 `task_id`、`expected_task_version`、`baseline_minutes`、`target_minutes`、`delta_minutes` 和调整基线指纹。

服务端在单个事务中：

1. 校验目标为 0 到 1440 的整数且 `target - baseline == delta`。
2. 校验事项仍存在、属于当前主体、仍是叶子且版本符合要求。
3. 校验同事项同日的有效调整集合与打开时指纹一致。
4. 基于当前原始工时和调整记录验证应用本批差额后最终实际不小于 0。
5. 创建全部调整记录并写入同步 outbox；任一步失败则整批回滚。
6. 按 `client_request_id` 返回幂等结果，避免响应丢失后重试产生重复记录。

普通计时和普通补录增长不参与调整指纹，不触发冲突；事项结构、事项版本或调整集合变化触发冲突并要求刷新。这样既符合“计时和调整互不影响”，又防止两次负向调整基于同一旧调整基线重复扣减。

### 4. 最终实际使用统一聚合口径

指定事项、指定日期的最终实际定义为：

`SUM(time_allocations.minutes) + SUM(actual_time_adjustments.delta_minutes WHERE deleted_at IS NULL)`

共享查询或共享聚合函数应成为以下消费者的唯一口径：计划事项 `direct_minutes` / `total_minutes`、调整快照、今日概览、趋势、日报、工时导出和保存时非负校验。父事项只汇总叶子后代的最终实际，避免父子重复计算。

写入端必须拒绝负结果；读取端可用不小于零的防御性限制处理历史异常数据，但不能用该限制掩盖新写入错误。

### 5. 时间记录使用判别模型展示调整

时间记录查询返回普通记录与实际调整的判别联合，或分别查询后按工作日期和记录时刻合并。调整项显示创建时刻、事项、`+30` / `-15`、来源“实际调整”和统一备注，不显示虚假的开始/结束区间，也不进入普通记录的修正或重新分配流程。

每日汇总应能区分原始工作、实际调整、最终实际和待确认分钟。删除使用专用软删除命令，参数至少包含 `adjustment_id`、`expected_version` 和 `client_request_id`。前端二次确认后删除，删除成功即撤销该差额；不提供更新调整值的接口。

### 6. 调整实体完整接入云同步

本地 SQLite 与 Supabase 同时增加调整表、索引、约束和 RLS。云同步覆盖快照导入/导出、outbox payload、远端应用、版本比较、软删除 tombstone 和任务依赖顺序。

两台设备可能基于相同旧基线分别创建不同的新记录，仅靠新记录自身版本无法发现业务冲突。因此批量保存必须携带调整基线指纹，并在云端原子写入路径再次校验；实现可使用事务性 RPC 或等价的服务端原子操作。删除按实体版本幂等收敛。

### 7. 导出使用独立正负调整行

现有工时归属导出已经按记录生成包含工作日期、主体、事项、分钟、时间段和备注的行，分钟字段为有符号整数。实际调整因此输出为独立行：沿用工作日期、主体和事项，分钟写入正负差额，时间段留空，备注标记“实际调整”并附带用户备注。该方案能覆盖没有原始计时行的纯调整，保留每条调整的审计边界，也使导出合计直接等于界面最终实际。预览、Excel 合计和测试必须接受负分钟，同时不把调整计入“未归属”时间。

## Risks / Trade-offs

- **正在计时使保存后最终值偏离目标** → UI 明确目标基于打开时快照，摘要展示固定差额，保存后刷新最新最终值。
- **分散查询遗漏调整记录** → 抽取共享最终实际查询，并为计划、今日概览、日报、趋势和导出增加跨模块一致性测试。
- **负向调整导致最终实际小于零** → 本地事务和云端原子写入都执行非负校验，失败时整批回滚。
- **混合时间历史模型增加前端分支** → 使用明确的判别 DTO；实际调整走只读展示与专用删除路径。
- **跨设备基线竞争** → 使用调整集合指纹和云端原子校验，冲突时保留草稿并提示重新加载。
- **导出消费者不熟悉负数行** → 时间段留空并在备注明确标记“实际调整”，文档和测试说明负数代表扣减；导出合计保持与最终实际一致。

## Migration Plan

1. 增加本地 SQLite migration 和 Supabase schema/RLS，表初始为空，不迁移既有记录。
2. 部署 Rust 模型、共享聚合、快照、批量保存、删除命令与云同步支持。
3. 接入前端服务、状态、计划页面板和时间记录展示。
4. 通过本地事务、汇总一致性和双设备同步验证后发布。

回滚应用版本时，新表及其数据可保留，旧版本不会读取调整记录；因此回滚期间界面实际时间会暂时不包含调整。若正式环境已产生调整数据，不应删除表，重新升级后数据恢复生效。
