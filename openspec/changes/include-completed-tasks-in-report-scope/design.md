# Design

## Context

见 `proposal.md`。当前 `ReportWorkspace.vue` 从全局 `store.tasks` 构造报告候选，而工作台为控制完成历史增长后的加载成本，已经将该数组调整为只承载进行中事项。后端 `report_task_suggestions` 虽然从数据库读取主体全部事项，但只返回周期内实际分钟大于零的事项，且 DTO 不包含标题、层级或完成归属，因此前端仍需和 `store.tasks` 取交集。

报告渲染已经能够读取完整事项、按报告日期解释重复事项轮次，并按 `time_entries.work_date` 聚合实际分钟。普通事项完成时间保存在 `tasks.completed_at`，重复完成记录保存在 `task_occurrences.occurrence_date`；工作空间时区已有统一解析和时间戳转工作日期工具。

## Goals / Non-Goals

**Goals:**

- 为报告弹窗建立自包含的候选查询，使其不依赖工作台进行中列表或已完成分页缓存。
- 在一个响应中返回候选展示、默认选择和周期统计需要的数据，保证搜索、汇总与提交口径一致。
- 使用同一周期归一化和工作空间时区规则覆盖日报、周报和月报。
- 保持稳定事项 ID、现有报告保存结构和重复事项报告统计规则。

**Non-Goals:**

- 不把主体全部完成历史重新加载到工作台或全局前端状态。
- 不改变“进行中 / 已完成”标签、完成历史分页或恢复操作。
- 不新增完成事件表、报告事项快照字段或数据库迁移。
- 不改变报告 Markdown 模板、明日计划规则和报告唯一性约束。

## Decisions

### 1. 将建议接口升级为报告候选接口

保留现有报告事项查询命令入口及其主体、报告类型、参考日期参数，但将响应从“只有实际用时的 ID 列表”扩展为自包含候选 DTO。每条候选至少包含稳定事项 ID、父 ID、标题、排序、整体预计、本期日报预计、本期实际分钟、当前基础状态、本期是否完成、是否默认选择和候选角色。前端用该响应直接构造列表，不再与 `store.tasks` 取交集。

候选角色区分可选择事项与仅用于层级识别的父级上下文。上下文父级可以显示，但不得仅因子项相关而默认选中。若父级自身符合完成、实际用时或当前未完成条件，则仍作为正常可选择候选。

备选方案是报告弹窗额外调用已完成分页接口并和工作台事项合并。该方案只能获得一页完成历史，无法按报告周期精确查询，也会让弹窗依赖分页与缓存状态，因此不采用。

### 2. 后端一次计算候选集合与默认集合

后端先使用现有周期归一化得到 `period_start` 和 `period_end`，再为所选主体构造以下集合：

1. 当前未完成的普通事项和仍可执行的重复事项定义；
2. `completed_at` 按工作空间时区换算后落在周期内的普通事项；
3. 周期内存在 `status = 'done'` occurrence 的重复事项；
4. 周期内实际分钟大于零的事项；
5. 上述事项保持层级所需的祖先。

默认选择集合为第 2、3、4 类的并集。第 1 类中没有完成或实际的事项默认不选，第 5 类不会因为只是祖先而默认选。候选按原事项树的稳定顺序返回，同一重复事项无论周期内完成多少次都只返回一个稳定 ID。

备选方案是在前端根据原始时间戳、occurrence 和工时分别计算集合。该方案会复制工作空间时区与重复规则语义，也更难保证多设备一致，因此不采用。

### 3. 普通完成时间通过统一日历工具归属周期

查询普通已完成事项时读取 `completed_at`，使用工作空间时区转换为 `YYYY-MM-DD` 后与归一化周期比较。实现可按周期边界预先换算成毫秒范围进行 SQL 过滤，也可在候选规模可控时复用 `work_date_at` 转换；无论采用哪种形式，日界线必须来自统一工作日历能力，不能使用 SQLite `localtime` 或设备系统时区。

重复事项直接使用 `occurrence_date BETWEEN period_start AND period_end`。实际分钟继续复用按 `work_date` 聚合的查询，从而和报告渲染、今日概览保持一致。

### 4. 前端候选状态与选择完全由弹窗局部状态维护

`ReportWorkspace.vue` 将候选响应保存为弹窗局部状态，`draftTasks`、搜索结果、层级深度、汇总、全选和提交都基于这份数据。创建模式或用户切换主体、类型、日期时，采用响应中的 `defaultSelected` 重置默认选择；调整范围模式加载新候选后，保留仍存在的报告事项 ID，不自动用默认集合覆盖用户已保存的范围。

加载期间通过现有请求序号丢弃过期响应。候选刷新后，已不再有效且不属于当前报告范围的数据从选择中移除；若既有报告绑定的事项因后来完成、恢复或状态变化仍属于候选规则，则继续显示并保留选择。

备选方案是把报告候选并入 Pinia 全局 `tasks`。这会重新耦合工作台性能策略和报告范围，且可能影响计时、计划和选中事项，因此不采用。

### 5. 状态展示使用“本期状态”而不是仅看当前基础状态

候选行按以下优先级显示：本期已完成、本期有实际、未执行。重复事项使用周期内 occurrence 完成事实；普通事项使用周期内完成时间。这样历史完成事项在本期继续产生工时时仍可显示为“有执行记录”，而不是误称为本期完成。整体预计、本期日报预计和实际分钟继续独立展示。

对于周报和月报，重复事项只显示一行“本期已完成”；完成次数仍由报告生成现有逻辑统计，不在候选列表复制轮次。

## Risks / Trade-offs

- [候选查询需要扫描完成事实和工时事实，主体历史较大时可能变慢] → 对普通事项先按周期时间边界过滤，复用已有工时日期索引和 occurrence 日期查询；只返回当前未完成、周期相关事项及必要祖先。
- [父级只作为上下文时，复选框语义可能含混] → DTO 明确区分上下文与可选择候选；前端对纯上下文使用非默认状态，并保持子项可独立选择。
- [调整报告范围时，默认集合可能覆盖用户历史选择] → 创建模式才应用默认集合，调整模式优先保留报告已保存且仍有效的事项 ID。
- [普通事项恢复后 `completed_at` 清空，重新打开历史报告范围时可能不再属于周期候选] → 若事项仍有本期实际则保留；否则范围调整按当前事实重新计算，已生成报告内容和既有 `report_tasks` 在用户保存前不改变。
- [当前存在其他未提交的 Rust 变更] → 实现阶段只修改报告相关代码和测试，避免覆盖无关工作区改动，并在合并前检查差异。

## Migration Plan

1. 扩展报告候选 DTO 与后端查询，保留命令参数和报告持久化结构。
2. 调整前端类型和报告弹窗局部状态，移除对 `store.tasks` 的候选交集依赖。
3. 补充后端周期、时区、普通完成、重复完成和工时组合测试，再运行前端类型检查与构建。
4. 发布无需数据库迁移；回滚时恢复旧 DTO 与前端列表来源即可，既有报告和事项数据不受影响。
