## Context

见 `proposal.md` 的 Why。`tasks` 保存 `planned_date`、`estimate_minutes` 和最终完成状态，用于表达预计开始日期、整体预计用时和完成状态。今日预计用时具有“事项 + 日期”维度，不能复用整体预计字段，因此需要独立的轻量按日预计实体。

计时模块已经使用“原始时间片 + 多条工时分配”模型，但 `AllocationInput` 只有事项、分钟和备注。事项完成通过独立命令更新，工时分配保存不能逐项附带完成意图。

## Goals / Non-Goals

**Goals:**

- 明确事项只保留单一预计开始日期，并区分整体预计与今日预计。
- 让预计开始日期已到或已过的未完成事项持续出现在今日待办。
- 让一次多事项工时结算可以逐项选择是否完成，并保证分配与状态更新原子提交。
- 保留事项主表语义稳定，通过轻量按日预计表承载日期维度。

**Non-Goals:**

- 不支持同一事项建立多个预计开始日期安排。
- 不增加包含状态、排序等复杂信息的每日计划实体；按日表只保存预计分钟数。
- 不增加“进行中、部分完成、暂停”等新的事项持久化状态；执行状态继续由工时和活动计时派生。
- 不根据预计完成比例、实际工时或所有子项状态自动完成事项。
- 不实现日历看板、容量排期、依赖关系或多人审批。

## Decisions

### Decision: 复用现有事项计划字段

继续使用现有字段，并固定其语义：

- `planned_date`: 预计开始日期，可空。
- `estimate_minutes`: 事项整体预计用时，可空。
- `status` 和 `completed_at`: 事项最终完成状态。

事项只能有一个预计开始日期，不再提供预计开始时间。用户修改日期时直接覆盖旧值，不生成历史计划记录。真实工作日期由 `time_entries.work_date` 和工时分配表达，与预计开始日期相互独立。

### Decision: 今日预计按事项和日期独立保存

新增 `task_daily_estimates(task_id, work_date, estimate_minutes)`。它只表示某个日期预计投入多少分钟，不表示事项被安排到该日期，也不改变预计开始日期。`tasks.estimate_minutes` 继续表示完成事项所需的整体预计分钟数。

同一事项同一天最多一条记录；清空今日预计时删除该记录。列表按当前日期加载，日报按报告日期加载，避免历史日报误用当前日期的预计值。

### Decision: 今日待办按预计开始日期和实际行为组成

今日待办的未完成事项集合采用以下并集：

1. `planned_date <= today` 且 `status = open` 的事项；
2. 今天存在最终工时分配的事项；
3. 今天通过临时事项入口创建的事项。

其中预计开始日期已过的未完成事项不会自动滚动修改日期，而是继续显示，并可在界面标识为已到期或逾期。`planned_date > today` 且今天没有实际工时的事项不进入今日待办。没有日期的普通事项保留在全部待办；只有今天临时创建或今天实际执行时才进入今日视图。

备选方案是每天自动把逾期事项的日期改成今天。该方案会丢失原始计划参考，无法看出事项何时开始逾期，因此不采用。

### Decision: 整体预计与今日预计互不覆盖

`tasks.estimate_minutes` 始终表示事项整体预计，不因计时日期或日报日期拆分。`task_daily_estimates.estimate_minutes` 表示某一天的预计投入。日报保持输出 `<预计：... 实际：...>`：预计优先使用报告日期的今日预计，未设置时回退到整体预计；实际只统计报告日期内的最终工时分配。

父事项仍不直接接受工时分配。父事项的实际用时由后代汇总；为避免与子项重复，报告中父事项是否显示预计沿用当前报告层级规则，不新增按日预计汇总。

### Decision: 分配输入携带逐项完成意图并在同一事务提交

扩展工时分配输入：

```text
task_id
minutes
note
complete_task = false
task_expected_version
```

前端每个分配草稿行维护独立的 `completeTask`。新建行、默认分配行和从已有分配恢复的行都初始化为 `false`。完成意图属于本次保存命令，不持久化在 `time_allocations`，因此重新打开记录时不会再次预勾选。

后端保存流程在一个 SQLite 事务中完成：

1. 校验时间片版本、可分配分钟和事项可选择性；
2. 按事项合并重复分配，分钟相加，完成意图采用逻辑 OR；
3. 替换时间片的工时分配；
4. 对 `complete_task = true` 且当前未完成的事项做带版本校验的状态更新；
5. 为实际状态变化写入 `task_status_events`；
6. 更新全局 revision 并提交。

任一事项版本冲突或校验失败时，整次保存回滚。已完成事项再次带完成意图保存时视为幂等，不重复写状态事件。

备选方案是前端先保存分配，再逐个调用完成接口。该方案可能出现工时已保存但部分事项未完成，且错误恢复复杂，因此不采用。

### Decision: 今日列表与全部待办使用不同过滤口径

全部待办负责展示当前主体下所有未完成事项，不受预计开始日期限制。今日待办用于聚焦当前应开始或已经执行的事项，采用前述并集规则。两个视图共享同一事项记录和排序数据，不复制事项。

预计开始日期、整体预计、今日预计和完成状态都在事项行内编辑。计时选择器继续按计划顺序展示可选择的叶子事项，并通过状态和实际用时提示是否已开始。

## Risks / Trade-offs

- [未填写日期的事项可能长期停留在全部待办] → 保留全部待办入口，并允许用户随时设置预计开始日期；今天实际执行后自动进入今日视图但不修改日期。
- [整体预计和今日预计容易混淆] → 所有列表和报告明确使用“整体预计”和“今日预计”，不再使用无修饰的“预计”。
- [完成事项时任务版本冲突导致结算失败] → 整体回滚并保留前端草稿，提示刷新事项状态后重试。
- [修改已结算历史分配时再次勾选完成] → 完成意图不存入分配记录，历史编辑默认不勾选；已经完成的事项执行完成操作保持幂等。
- [预计开始日期已过的事项数量较多] → 今日视图可按原有层级与排序展示，并增加逾期视觉提示，但不自动隐藏或改期。

## Migration Plan

1. 新增 `task_daily_estimates` 表；保留旧 `tasks.planned_time` 列以兼容已有数据库和云快照，但迁移时清空且业务接口不再读写。
2. 统一后端 DTO、接口注释和前端文案，将 `planned_date`、`estimate_minutes` 分别解释为预计开始日期和整体预计用时，并新增按日期的 `todayEstimateMinutes`。
3. 调整今日事项查询，纳入已到预计开始日期的未完成事项、今天有实际工时的事项和今天临时创建的事项。
4. 扩展工时分配请求和事务，支持逐项完成并补充状态事件。
5. 更新报告和相关测试，确认报告日期的今日预计、整体预计与报告日期实际用时互不混淆。
