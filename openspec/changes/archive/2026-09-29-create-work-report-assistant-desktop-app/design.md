## Context

见 `proposal.md` 的 Why。本项目是一个新建桌面应用，目标运行环境优先为 Windows。现有可复用资产包括多份 Python 脚本，它们已经包含 Obsidian 日报生成、时长转换、SeaTable 事项导入和周报生成规则，但当前脚本彼此分散，且以 Markdown 解析为主数据入口。

新的设计需要支持托盘计时、主窗口编辑、本地持久化、Obsidian 文件读写和 SeaTable API 调用。工时模型必须明确区分“原始计时记录”和“最终工时分配”。

## Goals / Non-Goals

**Goals:**

- 使用本地优先的数据模型支撑计划、计时、工时分配、日报和同步。
- 提供 Windows 主窗口和系统托盘入口，减少日常操作跳转。
- 保留 Obsidian 作为 Markdown 归档与可读输出目标。
- 保留 SeaTable 作为事项同步、报销数据和外部管理目标。
- 将现有脚本中的业务规则迁移为可测试的应用服务，而不是继续依赖多个人工脚本入口。

**Non-Goals:**

- 第一阶段不实现多人协作、账号系统或云端主数据库。
- 第一阶段不替换 Obsidian 或 SeaTable 的全部能力。
- 第一阶段不做复杂项目管理功能，例如甘特图、团队看板和审批流。
- 第一阶段不强制接入自动电脑活动追踪；空闲检测可作为后续增强。

## Decisions

### Decision: 使用 Tauri + Vue + SQLite

桌面应用 SHALL 采用 Tauri 2.x 作为桌面壳，Vue 3 作为前端界面，SQLite 作为本地结构化数据存储。

理由：Tauri 适合 Windows 托盘、窗口控制、本地文件访问和较小安装包；Vue 适合快速构建计划列表、计时面板和结算表单；SQLite 能可靠表达事项、时间片、分配记录和同步状态。相比 Electron，Tauri 更轻；相比 Python 桌面 UI，Tauri 的托盘、现代界面和打包体验更适合长期维护。

备选：

- Electron：生态成熟，但体积和资源占用偏高。
- PySide/PyQt：能更快复用 Python，但 UI 体验、前后端分层和后续打包更新不如 Tauri 清晰。
- Obsidian 插件：能贴近 Markdown，但托盘计时、本地数据库和 SeaTable 同步边界会更别扭。

### Decision: SQLite 是主数据源，Markdown 和 SeaTable 是同步目标

应用 SHALL 以 SQLite 中的结构化数据作为当天计划、原始计时、工时分配和同步状态的主数据源。Obsidian Markdown 作为导入来源和输出归档，SeaTable 作为外部同步目标。

理由：计时暂停、继续、补录、拆分分配和重新分配都是结构化关系，直接写在 Markdown 里会持续增加解析复杂度。SQLite 可以稳定记录事项身份，避免任务改名后丢失历史工时。

备选：

- Markdown 作为主数据源：初期简单，但随着工时拆分和同步状态增加会变得脆弱。
- SeaTable 作为主数据源：跨设备方便，但计时器和本地离线操作依赖网络，且桌面体验受 API 延迟影响。

### Decision: 工时采用“原始时间片 + 分配记录”双层模型

应用 SHALL 使用原始时间片记录客观时间，使用工时分配记录表达最终归属。开始计时的默认事项只保存为 `default_task_id`，不得直接等同于最终工时归属。

建议核心表：

- `work_days`: 日期、工作日标题、默认工作时间、日报状态。
- `tasks`: 日期、父任务、标题、预计分钟、状态、排序、来源、外部 SeaTable 行 ID。
- `time_entries`: 日期、开始时间、结束时间、原始分钟、默认任务、备注、来源、运行状态。
- `time_segments`: 时间片内的有效工作区间，用于表达暂停/继续后的多个区间。
- `allocations`: 时间片、任务、分配分钟、备注。
- `sync_jobs` 或 `sync_state`: Obsidian/SeaTable 同步状态、最近错误和外部标识。

理由：该模型直接对应用户的实际习惯：开始时只知道大概在做什么，结束后才决定具体归属。它也支持后续审计和重新分配。

### Decision: 托盘只处理高频轻操作，主窗口处理结构化编辑

托盘窗口 SHALL 只提供开始、暂停、继续、结束本段、选择默认事项、查看今日已记录/待结算和打开主窗口。计划整理、拆分分配、日报编辑和同步预览 SHALL 在主窗口完成。

理由：托盘窗口需要轻量、快速、低打扰；复杂结算如果塞入托盘会增加误操作。主窗口可以提供更完整的列表、预览和校验。

Windows 实现应遵循托盘悬浮窗口的延迟显示、右键菜单抑制和窗口恢复规则，避免托盘面板抢焦点或菜单被遮挡。

### Decision: 先迁移业务规则，再考虑完全重写脚本

第一阶段可以从现有 Python 脚本中提取规则和测试样例，但应用内应逐步形成自己的服务层：Markdown 解析器、日报渲染器、SeaTable 同步服务和周报生成服务。

理由：直接从 Tauri 调用多个现有脚本能快速验证，但会保留分散入口、命令行窗口、编码和错误处理问题。更稳的路径是先复用规则，再把规则收敛到应用服务和测试中。

### Decision: 外部写入必须预览和可重试

Obsidian 文件写入和 SeaTable 同步 SHALL 在执行前展示目标和变更摘要，执行后记录成功、失败和可重试状态。

理由：日报、周报和事项表是对外使用资料，静默覆盖或重复创建会影响上报和管理。同步状态需要可见，避免用户误以为已完成。

## Risks / Trade-offs

- Markdown 格式变化导致导入失败 → 解析器保留原文、展示未识别行，并允许手动编辑候选计划。
- SeaTable API 或表结构变化导致同步失败 → 同步层做字段映射配置和逐条结果展示，本地数据不因同步失败而丢失。
- 托盘计时和主窗口状态不一致 → 计时状态统一由后端持久化和事件广播驱动，前端只订阅状态。
- 用户同时在 Obsidian 中编辑目标日报 → 写入前检查文件修改时间和内容差异，要求用户选择覆盖或合并。
- 任务改名或拆分后同步重复 → 每个任务保存稳定本地 ID，并尽量保存 SeaTable 行 ID；无法匹配时展示人工确认。
- 敏感配置泄露 → Token 存放在本地配置或系统凭据区；普通数据导出时脱敏。

## Migration Plan

1. 初始化桌面项目和本地数据库结构。
2. 使用现有 Obsidian 日报样例验证 Markdown 导入和日报渲染。
3. 实现今日计划编辑和本地保存。
4. 实现计时器、暂停继续、手动补录和工时分配。
5. 实现日报预览和写入 Obsidian。
6. 实现 SeaTable 同步预览、写入和失败重试。
7. 实现周报生成和报销汇总。
8. 将现有脚本作为回退方案保留一段时间，确认桌面工具稳定后再考虑废弃分散脚本入口。

## Open Questions

- 是否需要开机自启动、全局快捷键和空闲检测可以作为后续增强，不影响 MVP 主流程。
