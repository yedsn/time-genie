# Design

## Context

参见 `proposal.md`。当前 `report_list` 查询全部报告 ID，再逐个调用完整报告加载；前端 store 保存整个工作空间的全部报告，页面使用计算属性做主体、类型和关键词筛选。报告侧栏本身是可滚动区域，但没有分页状态。

本地 SQLite 已有 `(workspace_id, updated_at DESC)` 索引。筛选还涉及 `subject_id`、`report_type` 和模糊日期搜索，因此分页查询需要兼顾稳定排序、计数和关联事项数量。报告数据仍由现有同步机制写入本地库，列表分页只读取本地权威数据。

## Goals / Non-Goals

**Goals:**

- 单次报告列表加载固定为 20 条，避免数据规模持续扩大首次加载成本。
- 主体、类型、搜索在后端完成，并让分页结果和总数量保持同一筛选口径。
- 复用当前左侧滚动列表，通过接近底部自动续载，保持现有界面结构。
- 对筛选切换、同步刷新和本地增删改建立明确的请求隔离与结果去重规则。
- 消除列表查询对每份报告执行一次完整详情加载的 N+1 查询。

**Non-Goals:**

- 不改变报告正文、模板、工资计算、生成或重新生成规则。
- 不改变报告同步实体、云端表结构或冲突处理协议。
- 不引入虚拟列表；每个筛选会话最多渲染用户已经滚动加载的结果。
- 不增加页码跳转、指定页输入或每页条数设置。

## Decisions

### 1. 使用页码式后端接口，界面表现为无限滚动

`ReportListRequest` 增加 `page` 和 `page_size`，后端校验页码大于等于 1，并把 `page_size` 限制在合理上限；前端固定传 20。返回值增加 `page`、`page_size`、`total` 和 `has_more`。

选择页码式接口是因为当前数据源是本地 SQLite，现有完成事项和时间历史已经采用页码模型，能够复用项目习惯。界面不展示页码，而是在滚动接近底部时请求 `page + 1`。备选的游标分页在大量并发变更时更稳定，但会增加复合游标、同步刷新和随机重置的复杂度；本变更通过筛选刷新和稳定排序控制页码漂移。

### 2. 使用 `updated_at DESC, id DESC` 作为稳定顺序

主排序继续满足“最近更新优先”，报告 ID 作为确定性次级排序。每次刷新从第一页重新建立基线；续载结果按 ID 去重，避免加载期间同步导致同一报告跨页移动后重复出现。

仅使用 `updated_at` 的备选方案无法保证相同毫秒内多条记录的顺序，会出现重复或遗漏。

### 3. 分页查询直接生成报告摘要

列表 SQL 一次返回报告基本字段、主体名称、模板名称/归档状态和 `report_tasks` 数量。报告 Markdown 仍包含在摘要 DTO 中，使用户选择列表项时无需再等待详情请求，并保持现有编辑器交互。关联事项 ID 通过单次聚合查询返回，或将列表 DTO 拆为 `task_count` 与按需详情；实现阶段优先采用单次聚合返回完整 `task_ids`，因为现有前端报告操作仍依赖这些 ID。

后端同时执行一条同条件 `COUNT(*)` 查询。两条有界查询替代“查全部 ID + 每条完整加载”的 N+1 方式。

### 4. store 持有当前筛选会话，而不是全量报告缓存

store 增加当前报告查询条件、页码、总数、`hasMore`、首次加载状态、续载状态和递增请求序号。

- `reset/load first page`：递增请求序号、替换查询条件、清空结果并加载第一页。
- `load more`：只在非加载且 `hasMore` 时读取下一页；返回时校验请求序号和查询条件。
- `refresh`：按当前条件重载第一页；若用户之前已加载多页，可选择重新加载到原已加载条数上限，确保刷新后可见范围不突然大幅缩短。实现优先采用“重载已加载页数”，上限为当前会话已加载页数。
- 合并结果按报告 ID 去重，并保持后端顺序。

页面筛选状态继续由报告工作区控制，但每次变化调用 store 的重置加载，不再对内存中的全量报告做最终筛选。搜索采用约 250 毫秒防抖。

### 5. 使用滚动容器阈值触发续载

在 `.report-record-list` 的滚动事件中，当剩余距离小于约 120px 时调用 `load more`。请求互斥由 store 负责，因此连续滚动事件不会重复加载。列表底部显示“加载中”“加载失败，点击重试”或“已显示全部”。

备选 `IntersectionObserver` 需要额外维护哨兵元素生命周期，对当前单一滚动容器收益有限；直接使用滚动距离更符合现有组件结构。

### 6. 列表刷新与选择态由报告 ID 协调

创建、删除、重新生成、保存以及全局同步触发的 `loadReports` 都转为刷新当前查询会话。刷新后：

- 原选中 ID 仍存在则保持；
- 原选中 ID 不在已加载结果但操作明确返回该报告时，将其作为目标并刷新到可见位置；
- 删除或筛选后不可见时选择第一条；
- 结果为空时清空选择。

报告计数标签使用后端总数。各类型标签需要准确数量时，可增加同主体、同搜索条件的类型计数聚合；为保持现有四个标签的数量语义，分页响应返回 `type_counts`，避免额外发起四次请求。

## Risks / Trade-offs

- [加载下一页期间报告被同步更新，导致页码边界漂移] → 使用稳定排序、按 ID 去重，并在同步完成后从第一页重载已加载页数。
- [搜索模糊匹配在报告量极大时变慢] → 当前仅匹配周期和主体名称，先保持既有语义；必要时后续增加专用索引或日期结构化搜索。
- [store 从全量缓存改为筛选会话，其他代码可能假设能找到任意报告] → 审计 `reports` 的所有读取点；具体操作返回的报告直接合并或触发当前范围刷新，不用全量缓存兜底。
- [同时返回 Markdown 和任务 ID 使单页载荷仍偏大] → 每批限定 20 条并消除 N+1；若实际测量仍过大，再独立设计摘要/详情接口。
- [页码式分页不具备游标分页的强一致快照] → 本地数据更新后主动重载基线，接受续载期间短暂变化，以更低实现复杂度换取足够稳定的桌面体验。

## Migration Plan

1. 扩展本地报告列表请求和响应 DTO，保留调用方未传分页参数时默认第一页 20 条。
2. 替换列表 SQL 并补充必要的本地 SQLite 复合索引迁移；不修改报告业务数据。
3. 接入前端服务、store 分页会话和报告页面滚动续载。
4. 将现有创建、删除、同步和报告编辑后的刷新路径切换到当前筛选会话刷新。
5. 通过大量报告数据验证首屏条数、搜索/切换竞态、连续续载、同步刷新和选择态。

回滚时可恢复旧的全量列表调用；新增索引可以保留，不影响旧版本读取。
