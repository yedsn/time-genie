# Design

## Context

见 `proposal.md` 与 `specs/plan-task-interactions/spec.md`。当前待办树由 `PlanListEditor.vue` 使用 SortableJS MultiDrag 把事项子树作为连续区块拖动；拖动结束后前端从渲染行反推 `beforeId`、`afterId` 和父级。`store.reorderTask` 随后仍使用移动前的 `moving.parentId` 选择兄弟，并把 `beforeId` 解释为“放到该项之后”，造成子事项拖到首位时计算成末位。Rust `task_reorder_subtree` 又明确拒绝父级变化，因此拖动无法完成一级/二级转换。

事项模型已经具有 `note` 和 `estimate_minutes`，按日预计保存在 `task_daily_estimates`；重复事项本体保持 open，规则与每日 occurrence 分离。前端当前同时展示整体/每次预计和今日预计，但备注没有行内入口，空白今日预计不会预填默认值，重复事项的按日预计也不会反向更新每次预计。

## Goals / Non-Goals

**Goals:**

- 让拖动结果由明确的目标父级和兄弟插入索引决定，而不是从 DOM 邻居猜测旧层级。
- 使用一次数据库事务原子保存父级和顺序，避免层级已变但顺序未变的中间状态。
- 将所有新入口复用到现有事项字段、版本检查和云端 outbox。
- 让相邻新增在本地立即出现并聚焦，同时持久化后仍保持准确位置。
- 使重复事项的每次预计成为后续日期默认值，而普通事项继续保留按日覆盖语义。

**Non-Goals:**

- 不支持三级及更深事项，也不引入任意深度树编辑。
- 不增加 Markdown/富文本备注、附件、提醒或备注搜索。
- 不重新设计已完成历史页；右键菜单和拖动只用于进行中事项树。
- 不实现跨主体拖动、批量右键操作或键盘菜单导航以外的完整快捷键系统。
- 不改变事项完成、重复轮次完成和计时选择规则。

## Decisions

### 1. 拖动结果统一为目标父级与目标兄弟索引

前端在拖动结束时先移除被拖子树，再根据实际落点计算 `targetParentId` 和 `targetIndex`：落在一级事项之间时父级为空；落在一级事项的子区域时父级为该一级事项；落在二级事项附近时父级取该二级事项的父级。最终请求不再传含义容易颠倒的 `beforeId/afterId` 组合，而是传父级及稳定的前后锚点或兄弟索引。

同一父级首位明确表示前锚点为空、后锚点为原第一项，排序值取后项之前。若相邻 `sort_order` 已无可用间隔，后端在同一事务内按固定步长重排目标兄弟，再放入移动项。这样刷新后不会因相同或反向 sort order 回到末尾。

备选方案是仅修正现有 `beforeId` 的正反判断。它可以修复首位 bug，但无法可靠表达跨父级落点，也继续让 DOM 顺序承担领域语义，因此不采用。

### 2. 后端提供原子的两级事项移动命令

扩展现有 reorder 命令或新增 `task_move`，在一个事务中完成：校验版本、主体、目标父级、循环和最大深度；必要时归一化目标兄弟排序；更新移动根事项的 `parent_id` 与 `sort_order`；提升 revision；云端模式下为更新后的事项镜像入队。移动的是根事项及其现有子树，子节点 `parent_id` 不变。

目标父级只能为空或一级事项。已有子事项的一级事项只能在一级层级内移动，因为把它挂到另一一级事项会让其子项成为三级。无子事项的一级事项可以降为二级；二级事项可以提升为一级。目标父事项继续沿用现有约束：必须同主体、不能是当前子树、不能是重复事项，也不能已有直接计时。

备选方案是前端依次调用 change-parent 和 reorder。两次版本提升会带来中间刷新、网络同步和失败回滚问题，无法保证原子性，因此不采用。

### 3. 拖动展示使用显式落点而非深度跟随

待办组件在拖动时展示三类可识别落点：一级间隙、某一级事项的子列表间隙、二级兄弟间隙。拖动元素的旧 `data-depth` 不再决定新父级。落到二级行时，只把该行作为同父级排序锚点，不把二级行本身作为父级。无效落点显示禁止状态，结束后重建列表恢复权威顺序。

继续保留整棵子树 MultiDrag，以避免父项与子项在视觉移动时分离。实现时将纯粹的“根据扁平行和落点计算移动意图”提取为无 DOM 依赖函数，用固定数据测试首位、末位、提升、降级和二级落点。

### 4. 备注使用行图标和独立轻量弹框

每行元信息区域增加备注图标。有非空 `task.note` 时使用 filled/highlight 状态；点击后打开复用的单实例弹框，草稿与事项对象分离，只有保存时才调用现有事项更新。空白或仅空格保存为 null。弹框取消不改变响应式事项对象，避免输入一半时被后台刷新同步。

右键菜单的“编辑备注”打开同一个弹框，不创建第二套保存逻辑。已完成历史继续使用现有编辑能力，本变更不强制增加相同图标。

### 5. 今日预计编辑区分显示值、草稿默认和持久值

普通事项打开空白今日预计时，仅在编辑草稿中填入一级 60、二级 30；Esc 或取消丢弃草稿，不直接修改 `task.todayEstimate`。保存后仍写 `task_daily_estimates`。已有值始终原样编辑。

重复事项的有效显示值按 `日期覆盖值 ?? task.estimate` 计算，其中 `task.estimate` 在重复语义下就是每次预计。保存重复事项今日预计时，在一个用户动作中同时更新事项 `estimate_minutes` 和当天 `task_daily_estimates`。为避免部分成功，优先增加一个后端事务命令；若复用通用事项更新，则必须由后端组合服务在同一 SQLite 事务和同一同步边界内完成。

后续日期没有 `task_daily_estimates` 行时不必预先批量生成记录，查询层直接返回或前端派生每次预计作为默认，从而避免无限创建未来 occurrence/estimate 数据。

备选方案是每天首次打开时写入一条按日预计。它会制造无用户操作的数据和大量未来/历史行，也无法清楚区分模板与覆盖，因此不采用。

### 6. 相邻新增先计算位置再持久化

为新增请求补充可选定位信息：目标父级和前后兄弟锚点。一级行“上方/下方新增”在根兄弟列表定位；二级行在其父级的子列表定位。后端创建事项时在事务内计算 sort order，必要时归一化兄弟顺序，避免先以末尾创建再二次移动。

前端仍保留乐观空白行和自动聚焦；空标题失焦继续删除临时行。右键菜单使用自定义定位层或 Element Plus 上下文菜单，挂载到 body 并根据窗口边界翻转，点击外部、Esc、滚动、拖动开始和命令执行时关闭。

### 7. 同步沿用完整事项镜像

备注、每次预计、父级和排序都已属于 task payload。原子移动、相邻创建和重复预计组合保存继续生成现有 task 与 task_daily_estimate outbox 操作，并使用依赖保证事项模板更新先于必要的日期预计更新。无需新增 Supabase 表；只需确保云端 apply 对 parent_id、sort_order、note 和 estimate_minutes 的现有校验与本地两级约束一致。

## Risks / Trade-offs

- [拖动落点在紧凑行中不够明确] → 使用明显的水平插入线和缩进后的子列表高亮，并为无效落点显示禁止反馈。
- [排序值长期插入后间隔耗尽] → 后端在目标兄弟范围内事务化归一化，不依赖无限可分的整数。
- [有子树的一级事项无法降级可能让用户困惑] → 拖动时将二级落点标为无效，并提示“包含子事项的事项不能变为二级”。
- [重复事项某日曾有旧覆盖值] → 当天优先显示日期覆盖；用户再次保存时同时刷新每次预计，未来日期使用新模板，历史覆盖不回写。
- [组合保存涉及 task 与 daily estimate 两个同步实体] → 在同一事务内入队并建立依赖，失败时整体回滚，避免本地只保存一半。
- [右键菜单与浏览器原生菜单冲突] → 仅在事项行阻止默认菜单，输入框需要文本复制粘贴时保留浏览器/系统编辑能力或提供等价菜单项。

## Migration Plan

1. 先增加两级移动、定位创建和重复预计组合保存的领域函数及后端测试，不改变现有 UI。
2. 提取并测试前端拖动意图计算，再切换 `PlanListEditor` 使用新移动请求和显式落点。
3. 接入备注弹框、今日预计草稿默认和重复事项继承。
4. 接入右键菜单及相邻新增，补充键盘关闭、窗口边缘定位和输入框原生菜单兼容验证。
5. 运行事项、重复事项、云同步、前端类型检查和构建，并手工验证本地与云端刷新后层级及顺序一致。

回滚时可让前端重新使用旧 reorder/change-parent 入口；新后端命令和可选创建定位参数保持向后兼容。本变更复用现有字段且不新增数据迁移，回滚不会丢失备注、预计或排序数据。
