# Design

## Context

见 `proposal.md` 与 `specs/timer-sync-authority/spec.md`。普通事项计时当前同时存在本地 `coordinate_active_timer` 和 Supabase `coordinate_timer_calendar_day_at` 两套协调逻辑。本地读取会在检测到超过 90 秒的连续性间隔时关闭旧分段、建立新分段并提升版本；云端每 30 秒租约获取或续期又通过 `unassigned_tick` 调用相同语义的云端协调函数，也可能提升同一 `time_entries.version`。

同步 outbox 对同一实体只阻止后续操作越过本地较早队列项，但云端租约写入不经过本机 outbox，因此可以在本机队列之前推进云端版本。历史故障已出现本地 `4 -> 5 -> 6 -> 7 -> 8` 操作链，而云端被租约协调推进到版本 6；旧 `4 -> 5` 操作随后成为冲突。此前仅轮换幂等标识的恢复方式不能判断云端是否已经应用等价变化，会把幂等冲突转化成版本冲突。

既有 `simplify-unassigned-time-sync` 已把未归属自然增长改为起点派生，但明确保留普通事项计时的中断恢复策略。本设计只统一普通事项计时的权威，不改变未归属锚点规则。

## Goals / Non-Goals

**Goals:**

- 让任何普通计时版本提升都能追溯到一条本地持久化业务操作。
- 保持本地优先：断网时计时、停止和分配立即写入 SQLite，联网后有序收敛。
- 自动处理同一设备的响应丢失、旧幂等冲突、陈旧中间快照和可压缩版本链。
- 保留租约对多设备写入权限的协调作用，并让真正竞争修改继续进入冲突处理。
- 在升级时安全修复现有异常队列，不丢失已结束和已分配的本地时间记录。

**Non-Goals:**

- 不移除通用 outbox、Realtime、增量拉取或设备授权。
- 不把正在运行的秒数持续上传到云端。
- 不改变 90 秒连续性判断、跨日切片或结算分钟的产品语义。
- 不允许任意本地最终快照无条件覆盖真正来自另一设备的用户操作。
- 不改变未归属时间的单一锚点和开始事项即清除规则。

## Decisions

### 1. 本地客户端是普通计时转换的唯一生产者

保留 SQLite `coordinate_active_timer` 作为普通计时中断与跨日转换的实现。`tracking_lease_acquire`、`tracking_lease_renew`、`tracking_lease_release` 和未归属协调不再调用会修改普通计时的云端协调函数。云端可以读取活动计时来决定是否建立未归属锚点，但不能借此修改计时实体。

这样每次版本提升都会同时产生本地实体变更和 outbox 操作，版本链可以完整审计和重放。替代方案是云端成为唯一计时状态机，但离线计时、即时停止和本地优先交互都需要改成在线 RPC 或双阶段提交，不符合现有架构。

### 2. 租约只授予写入资格，不隐式执行业务转换

本机执行普通计时写入前继续依据已获取的租约资格；后台维护器每 30 秒只延长租约并协调未归属日期边界。租约失效后，本机可以继续显示已持久化状态，但新的跨设备敏感操作应先重新取得租约并完成一次同步拉取。

另一设备接管时，先拉取云端活动计时，再以明确的 `timer_takeover_recover` 或现有等价转换恢复中断、跨日或结束状态。该转换具有独立 operation ID 和基础版本，不能隐藏在续租 RPC 内。

备选方案是在租约续期前先强制冲洗本机 outbox。它只能缩小竞态窗口，不能覆盖离线、响应丢失和续期成功但上传失败，因此不作为正确性机制。

### 3. 同一时间记录的队列以实体版本链为顺序边界

同一 `time_entry` 的操作按 `base_version`、`payload_version` 和创建顺序构成链。任何早期操作处于 pending、sending、failed 或 conflict 时，都阻塞该实体的后续操作。显式依赖字段继续用于跨实体/跨切片关系，但同实体版本顺序本身就是强制依赖，不要求每条都另写依赖 ID。

未尝试的连续操作仍可合并为一张最终快照，但合并后必须保留：最早基础版本、最终 payload 版本和被合并的版本跨度。已尝试操作是远端结果边界，不直接改写内容。

### 4. 幂等冲突先查证，不再直接轮换标识

为计时操作补充一个服务端可查询的 processed-operation 结果入口，或在计时补丁 RPC 内返回结构化分类。客户端遇到 `IDEMPOTENCY_CONFLICT` 时按以下顺序处理：

1. 使用原 operation ID、实体 ID、基础版本和 payload 摘要查询云端已处理记录。
2. 若已处理内容对应同一逻辑转换，采用其权威结果并确认本地操作。
3. 若 operation ID 确实属于不同转换，再为当前转换生成新的、由实体 ID、基础版本、目标版本和动作组成的稳定标识。
4. 重新提交前必须比较云端当前版本，不能仅更换 ID 原样重试。

这避免把“响应丢失”误判为新操作，也避免将幂等问题转换为版本冲突。查询接口只返回当前用户工作空间内必要的操作类型、请求摘要和结果，不暴露其他设备凭据。

### 5. 版本冲突按可证明的来源分三类处理

客户端拉取云端权威计时聚合和同实体本地队列后分类：

- **已经确认**：云端版本和内容包含队列前缀对应的转换。删除该前缀，必要时将剩余操作的基础版本对齐权威版本。
- **同机可压缩**：云端版本落在本地版本链中间，且从云端权威状态到本地最终快照的差异全部由本机后续离散操作解释。创建或复用一条 rebased 最终操作，以云端版本为基础、目标版本为云端版本加一；删除被覆盖的中间操作并重定向其跨实体依赖。
- **真正冲突**：云端内容或设备来源表明存在不能由本机操作链解释的用户修改，或者最终快照包含不能安全重放的副作用。保留冲突供用户选择。

计时完整镜像包含分段和分配。重放最终镜像时，服务端仍需验证实体身份、计时链、日期唯一性和租约权限。对于任务完成等跨实体副作用，只有其独立依赖操作仍在队列中且版本条件可重新计算时才允许自动压缩；否则进入真正冲突。

### 6. 自动 rebase 使用最终本地状态，而不是逐条重放陈旧快照

典型历史链 `4 -> 5 -> 6 -> 7 -> 8` 在云端已为 6 时，不再提交 4 -> 5，也不机械提交 5 -> 6。系统选择最新完整本地状态（版本 8 的已结束、已分配镜像），以云端版本 6 为基础生成一次新的最终状态写入。云端接受后版本变为 7；本地采用云端返回的版本 7 和权威快照。

因此版本号表示服务端接受的变更次数，不要求保留本地离线期间每一次中间版本。界面和业务只依赖顺序与乐观并发，不依赖本地版本号必须等于历史操作总数。

备选方案是把每个中间操作依次改写为 6 -> 7、7 -> 8 等。旧快照可能包含已经过时的运行状态和分段，逐条重放会制造短暂错误状态，也增加失败点。

### 7. 历史队列修复采用可重复的事务化归一化

升级或首次同步前扫描以下条件：`time_entry`、计时类 operation、存在 `IDEMPOTENCY_CONFLICT`/`SYNC_CONFLICT`，或同实体存在不连续/被云端越过的版本链。修复过程先只标记待协调，不立即删除记录；获取云端权威聚合后，在一个 SQLite 事务中完成：

- 保存诊断快照和修复原因；
- 确认或删除已被覆盖的队列前缀；
- 生成 rebased 最终操作；
- 更新 `depends_on_operation_id`；
- 清除可恢复错误或将无法证明安全的项标记为 conflict。

该过程必须幂等，应用在任意步骤退出后重新运行得到相同结果。现有“遇到幂等冲突立即随机换 operation ID”的逻辑应移除或限制为完成查证后的最后分支。

### 8. 云端返回结构化错误和权威上下文

计时 RPC 对版本不匹配返回机器可判定的信息，包括错误类别、当前版本、当前权威聚合或可查询引用、以及原 operation 是否已处理。客户端不再依赖英文错误字符串决定恢复路径。现有字符串错误保留兼容展示，但不能作为新逻辑的唯一判断条件。

## Risks / Trade-offs

- [移除云端心跳计时协调后，所有设备都离线时云端不会自行封口中断计时] → 计时本来是本地优先；下一台持租约设备恢复或接管时执行一次明确的恢复协调并上传权威边界。
- [自动压缩会让服务端版本号小于本地历史版本号] → 同步成功后始终采用服务端返回版本；版本只用于并发控制，不作为用户历史编号。
- [最终快照覆盖可能掩盖另一设备的真实修改] → 只有设备来源、已处理操作和本地链能证明安全时自动 rebase，否则保留冲突。
- [旧客户端仍可能通过租约 RPC 推进云端计时] → 先部署服务端兼容补丁，使租约 RPC 不再修改普通计时；新客户端随后发布。
- [队列修复涉及跨实体依赖] → 在同一事务中重定向依赖，并为任务完成、轮次完成等副作用增加专项回归测试。
- [网络中断发生在云端提交后、客户端确认前] → 依靠原 operation ID 查询/重试取得相同权威结果，不创建新业务转换。

## Migration Plan

1. 先部署 Supabase 兼容补丁：租约路径停止修改普通事项计时，计时补丁提供结构化权威上下文和 processed-operation 查证能力；保留现有 RPC 签名兼容旧客户端。
2. 发布客户端队列协调：同实体严格顺序、幂等查证、版本分类和最终快照 rebase。
3. 在客户端启动或同步前执行历史异常队列扫描，只标记候选；在线后事务化收敛，保留诊断信息。
4. 删除或收窄现有直接轮换计时 operation ID 的恢复逻辑，确保没有查证时不会原样重试陈旧内容。
5. 通过单机休眠、响应丢失、重复读取、离线多步操作、跨日以及双设备租约接管验收后发布。

回滚时客户端可停用自动 rebase 并保留修复前诊断，但服务端租约“不修改普通计时”的约束应继续保留，避免重新产生单机自冲突。
