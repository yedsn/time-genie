## Context

见 `proposal.md` 的 Why。当前 `tasks.status` 表示普通事项的全局完成状态，`task_status_events` 用于还原历史完成状态，`task_daily_estimates` 按事项和日期保存今日预计，实际用时通过 `time_entries.work_date` 与 `time_allocations.task_id` 归属事项。

重复事项需要同时表达“长期规则仍在生效”和“某一天已经完成”。如果每天修改同一条 `tasks.status`，昨天的完成与今天的待办会相互覆盖；如果每天复制完整事项，又会污染待办、排序、层级和搜索。因此需要把事项定义、重复规则和按日执行状态分开。

## Goals / Non-Goals

**Goals:**

- 普通待办中始终只有一条重复事项定义，今日视图按日期呈现上下文状态。
- 不依赖每日定时任务或应用持续运行，即可在查询时得到当天轮次。
- 未处理历史日期零写入、零补发；有业务行为的日期可完整还原完成、预计和实际用时。
- 复用现有事项层级、排序、计时分配和日报链路，普通事项保持兼容。
- 规则修改和关闭后仍能按历史日期正确生成或重新生成报告。

**Non-Goals:**

- 不支持有子事项的事项或整棵子树重复；无子事项不受层级限制。
- 不支持每月、每年、节假日排除、结束次数或复杂 RRULE。
- 不为无行为的跳过日期创建审计记录，也不提供补签或历史跳过列表。
- 不在本变更中扩展 Supabase 表、RPC 和实时同步；重复规则第一版只在本地存储模式开放。

## Decisions

### Decision: 事项定义、规则区间和执行轮次分离

保留 `tasks` 作为唯一事项定义和层级节点。新增：

```text
task_recurrence_rules
  id
  workspace_id
  task_id
  frequency          daily | weekdays | weekly
  weekdays_mask      weekly 时使用，周一到周日位图
  effective_start
  effective_end      可空，包含边界
  created_at / updated_at / version

task_occurrences
  workspace_id
  task_id
  occurrence_date
  origin             scheduled | manual
  status             open | done
  completed_at
  created_at / updated_at / version
  PRIMARY KEY(task_id, occurrence_date)
```

`tasks.estimate_minutes` 对普通事项仍表示整体预计，对启用重复的事项在 UI 中解释为每次预计。`task_daily_estimates` 继续保存指定日期的覆盖值，不复制字段。

重复规则使用有效区间而不是原地覆盖单行。修改规则时关闭当前区间并创建新规则区间，使历史日报重新生成时仍能判断当时是否为计划日。备选方案是只保存当前规则，但修改星期后会改变历史日期的计划判断，因此不采用。

### Decision: 到期轮次默认虚拟存在，有行为时才物化

查询今天时，根据工作空间时区和规则有效区间计算是否到期：

```text
规则今天到期 + 无 occurrence 记录 --> 虚拟 open 轮次
规则今天到期 + 有 occurrence 记录 --> 使用持久化状态
规则今天不到期 + 有今日行为     --> manual 轮次
规则今天不到期 + 无今日行为     --> 不显示
```

以下操作需要在同一事务中 `INSERT ... ON CONFLICT` 物化当天轮次：

- 完成或恢复当天轮次；
- 设置今日预计；
- 开始计时、创建手工工时或分配未归属时间；
- 非计划日主动选择重复事项执行。

纯查看不写入数据库。过去没有任何行为的日期没有 `task_occurrences`、今日预计或工时，因此自然视为跳过。备选方案是每天零点批量创建轮次，但应用可能未运行，并且会产生大量无价值记录，因此不采用。

### Decision: 重复事项不使用全局完成状态

启用重复期间，基础 `tasks.status` 保持 `open`，不得因某日完成改为 `done`。事项行的显示状态取决于查询上下文：

- 全部待办：显示规则定义，不展示全局完成圆圈，提供重复规则摘要和关闭重复入口；
- 今日工作台：使用 `task_occurrences.status`，无记录时为虚拟 `open`；
- 今日已完成：只查询今天状态为 `done` 的轮次；
- 历史日报：按报告日期读取对应轮次状态。

完成接口增加可选 `occurrence_date`。普通事项不传日期并沿用现有 `tasks.status`；重复事项必须传日期并更新 `task_occurrences`。计时分配中的 `complete_task` 使用时间记录的 `work_date` 作为轮次日期。

备选方案是每天完成后自动把 `tasks.status` 恢复为 `open`，但会产生状态事件歧义并破坏历史报告，因此不采用。

### Decision: 今日查询合并普通事项与重复轮次

今日查询分两部分后按现有层级顺序合并：

1. 普通事项继续采用预计开始日期、今日实际工时和今日临时创建规则；
2. 重复事项包含今天计划到期的虚拟或持久化轮次，以及今天有 occurrence、今日预计或实际工时的手工轮次。

重复资格只根据事项是否存在子项判断，不根据 `parent_id`、层级深度或是否为一级事项判断。重复叶子事项保持原有层级：一级叶子事项继续作为一级事项，嵌套叶子事项继续挂在原父事项下；轮次不得改变 `parent_id` 或产生额外层级。具有子项的事项只作为路径和实际用时汇总，不创建重复轮次。若父项本身已完成但后代要启用重复，设置规则时应拒绝或先恢复父项，避免今日层级中出现已完成父项包裹未完成轮次。

### Decision: 规则设置采用行内轻量弹层

事项行元信息区域增加重复图标，点击后使用 UI 库弹层设置：

- 不重复；
- 每天；
- 工作日；
- 每周，并用星期分段选择器多选；
- 开始日期，默认今天。

保存后行内只显示简短摘要，例如“每天”“工作日”“每周一、三、五”。重复事项的“整体预计”文案切换为“每次预计”，今日预计入口保持不变。任何有子事项的事项均不显示可用的重复设置入口；一级但无子事项的事项正常显示并允许使用重复入口。前端不得根据层级或 `parent_id` 隐藏入口。重复事项新增子项前必须先关闭重复。

### Decision: 规则修改从当天起生效

用户修改重复频率、星期或开始日期时，新规则从用户选择的开始日期生效；默认开始日期为今天。若生效日期早于今天则拒绝，以避免追溯生成或改变历史轮次。旧规则区间截止到新规则开始日期前一天。

关闭重复时，旧规则区间截止到当天；当天已有轮次仍可完成或恢复。从下一天起不再自动出现。基础事项立即按普通事项展示，状态初始化为 `open`，保留名称、主体、父级、排序和默认预计。

### Decision: 计时继续绑定 task_id，日期确定轮次

不修改 `time_allocations` 的外键结构。分配仍指向稳定的 `task_id`，轮次日期由所属 `time_entries.work_date` 决定。这样任务改名、规则修改或关闭后，历史工时仍能通过稳定事项身份查询。

保存一笔重复事项工时时，在同一事务中确保对应 `task_occurrences` 存在。跨午夜计时继续遵循现有时间记录工作日期规则，本变更不重新切分时间片。

### Decision: 报告按日期解释重复事项

日报查询报告日期对应的 occurrence、今日预计和实际工时：

- 有今日预计时优先作为“预计”；否则回退到每次预计；
- 当日完成显示绿色；有实际但未完成显示红色；
- 无完成、无实际的到期轮次不进入今日事项；
- 明日计划只包含明天符合规则的重复事项，以及现有普通未完成计划。

报告范围继续保存稳定 `task_id`，同一天同一重复事项只出现一次。周报/月报的实际分钟继续按日期汇总；若展示完成数量，应按已完成 occurrence 数量统计，不能只按唯一 task_id 计数。

### Decision: 本地模式先行并阻止无提示丢失

本变更不扩展 Supabase。云端存储模式下隐藏或禁用重复规则设置，并显示“重复事项暂仅支持本地模式”。本地存在有效重复规则时，切换到云端的迁移预览必须列出不受支持的数据并阻止确认，不能静默丢弃规则或轮次。后续接入云端时再同步新增表和事务接口。

## Risks / Trade-offs

- [同一 Task DTO 在全部待办和今日视图中的状态语义不同] → 增加明确的 recurrence 与 occurrence 字段，前端按视图选择状态，不覆盖基础事项缓存。
- [规则修改可能影响历史报告] → 使用有效区间保留规则历史，日报按报告日期选择规则版本。
- [完成与计时分属多个写入路径，可能漏建 occurrence] → 集中提供事务内的 `ensure_occurrence` 服务，并让完成、手工工时、计时停止、分配和未归属处理复用。
- [重复事项关闭后，基础事项与当天轮次看起来像同一行] → 使用同一 task_id 和当天 occurrence 状态渲染，不创建第二条 UI 行；次日起完全按普通事项处理。
- [工作日不包含法定节假日] → 第一版明确仅按周一至周五判断，后续再增加节假日日历。
- [稀疏模型无法列出所有跳过历史] → 跳过日期按需求不落库；如未来需要习惯追踪，应单独引入显式跳过记录。

## Migration Plan

1. 新增规则区间表和执行轮次表及唯一索引，不修改现有普通事项数据。
2. 扩展事项 DTO 和查询接口，普通事项默认 recurrence 为空，保证现有页面先兼容读取。
3. 上线重复设置和本地写接口，再接入今日查询、完成和计时事务。
4. 更新日报与明日计划查询，补充规则历史和 occurrence 测试。
5. 云端模式禁用重复设置；本地转云端时检测并阻止遗漏新增实体。

回滚时先隐藏重复设置入口并停止创建新规则，保留新增表避免丢失历史。若必须降级到旧版本，重复事项基础记录仍以普通未完成事项存在，但旧版本不会解释按日完成状态。
