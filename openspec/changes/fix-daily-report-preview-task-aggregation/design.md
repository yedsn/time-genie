# Design

## Context

见 `proposal.md`。报告创建弹窗通过 `report_preview` 获取预览，正式创建则通过 `report_create` 保存报告。本地路径的预览和创建都进入 Rust 的自动范围与 `render_report`，已经按稳定事项汇总实际分钟并在日报叶子事项展示用时。

Supabase 直连路径存在两代实现：旧的 `direct_cloud_report_preview` 独立查询所有进行中或本期相关事项，只输出标题；新的报告创建流程使用 `direct_cloud_report_scope_task_ids` 和 `direct_cloud_report_render`，已经处理稳定事项身份和自动范围，但渲染的事项行仍未附带每项实际分钟。两条路径因此会得到不同内容。

报告创建界面当前不在创建模式下展示人工事项勾选，提交空 `taskIds` 表示由服务端按周期记录自动选择；预览也应遵循同一语义。本变更不改变范围调整弹窗已有的人工选择能力。

## Goals / Non-Goals

**Goals:**

- 让直连模式的报告预览复用正式创建所使用的范围计算和渲染函数。
- 在服务端以稳定事项 ID 汇总时间分配和实际用时调整，避免重复事项实例或多条时间记录形成重复行。
- 让本地和直连日报都在叶子事项上显示合并后的实际用时。
- 用一致性测试锁定“相同输入且数据未变化时，预览 Markdown 等于创建 Markdown”。

**Non-Goals:**

- 不改变时间记录、工时分配、实际用时调整或报告表结构。
- 不重新设计报告模板、创建弹窗布局或范围调整交互。
- 不把原始计时片段逐条写入报告；报告仍只展示事项级汇总。
- 不改变周报、月报依赖已保存日报合集的既有总体结构。

## Decisions

### 1. 以正式创建的范围与渲染函数作为唯一口径

直连预览 SHALL 先通过 `direct_cloud_report_period` 归一化周期，再调用 `direct_cloud_report_scope_task_ids` 取得自动事项范围，并调用 `direct_cloud_report_render` 生成 Markdown。预览 RPC 只负责权限校验、组织响应和返回渲染结果，不再维护独立的候选 SQL 或模板替换逻辑。

选择该方案是因为创建、重新生成和预览共享相同服务端函数后，范围规则或模板占位符以后只需修改一处。备选方案是在旧预览函数中复制新的 SQL；它可以快速修正当前结果，但仍会继续产生逻辑漂移，因此不采用。

### 2. 在渲染阶段一次性计算事项级实际分钟

`direct_cloud_report_render` 将为所选稳定事项构造事项级实际分钟集合：时间分配按 `COALESCE(day_instance_source_task_id, task.id)` 归并，实际用时调整使用相同稳定身份后合并。日报事项行从这个集合读取合计值并格式化，而不是遍历原始时间记录输出多行。

聚合继续以整数分钟作为内部值，展示时读取共享设置 `report_duration_format`，并与本地 `format_report_duration` 的分钟/小时语义保持一致。父事项仅作为路径或层级上下文，不额外累加子事项分钟。

备选方案是在前端拿到时间记录后自行合并；这会让预览、保存、重新生成和其他设备产生不同权威结果，也会扩大前端数据依赖，因此不采用。

### 3. 自动事项范围继续以“有用时或本期完成”为准

空 `taskIds` 继续表示自动范围。自动范围只包含周期内聚合分钟大于零、普通事项在工作空间时区内完成，或重复事项存在本期完成轮次的稳定事项。当前为 `open` 但本期无执行与完成事实的事项不会因为其状态或主体归属进入报告。

人工传入非空 `taskIds` 时仍尊重用户选择，并验证事项属于当前主体且不是每日实例；未计时但人工选中的事项可进入范围，渲染时不虚构实际用时。

### 4. 通过新增可重复部署的 Supabase 迁移覆盖既有函数

实现时新增日期有序的 Supabase SQL 迁移，使用 `CREATE OR REPLACE FUNCTION` 更新预览 RPC 和共享渲染函数，并将迁移纳入 `supabase/schema.sql` 与 schema 集成测试入口。这样已部署的直连工作空间可通过增量迁移获得修复，新的完整部署也会得到相同行为。

不直接只改早期 SQL 文件，因为现有环境不会重新执行历史迁移；仅修改汇总 schema 又会让增量升级缺失。

### 5. 一致性测试比较完整 Markdown 和关键聚合结果

本地测试保留并扩充现有“预览不落库且等于创建结果”的断言，增加同一事项多条分配、实际用时调整和重复事项实例场景。Supabase schema 集成测试在相同输入下先调用预览，再调用创建，并断言完整 Markdown 相等、事项只出现一次、合计实际分钟正确且无关进行中事项不存在。

## Risks / Trade-offs

- [共享渲染函数改变后会影响重新生成的既有报告] → 只在用户创建或主动重新生成时产生新 Markdown，不批量改写已有报告；测试覆盖创建、预览和重新生成。
- [SQL 与 Rust 的时长格式可能再次漂移] → 为分钟和小时两种设置添加对照断言，并将格式化规则集中在各自后端的单一函数中。
- [重复事项的实例和原始事项同时被人工传入] → 范围验证只接受稳定事项，自动范围也统一输出稳定 ID，防止重复计数。
- [预览之后数据变化会导致创建结果不同] → 一致性承诺限定为底层数据与输入未变化；创建仍以提交时的权威数据重新计算，不保存预览快照。

## Migration Plan

1. 更新本地与直连报告生成测试，先覆盖聚合及预览一致性场景。
2. 扩展直连共享渲染函数的事项级实际分钟和时长格式输出。
3. 通过新 Supabase 迁移让预览 RPC 调用正式范围与渲染函数，并更新 schema 汇总入口。
4. 运行 Rust 报告测试、前端类型检查和 Supabase schema 集成测试。
5. 若部署后需要回滚，恢复前一版预览与渲染函数定义；现有报告数据结构和已保存 Markdown 无需迁移。
