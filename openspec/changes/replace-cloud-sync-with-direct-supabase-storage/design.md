# Design

## Context

见 `proposal.md` 与 `specs/direct-cloud-storage/spec.md`。当前所有主要业务命令都直接操作 SQLite；云端模式在同一事务中更新本地实体并写入 `sync_outbox`，后台协调器随后上传操作、接收 Realtime 通知、拉取增量并再次更新 SQLite。现有 Rust 代码有二十余个业务模块直接依赖 `Database`，因此不能通过简单替换几个前端接口完成直连。

Supabase 已具备工作空间、RLS、设备授权、版本字段、幂等操作、操作记录、云端快照、世代屏障、计时租约及多项复合 RPC，但现有读取契约主要面向增量同步和完整快照，并不适合作为页面查询 API。SQLite 仍需要承载本地模式业务数据，以及两种模式都需要的设备级配置和安全凭据引用。

## Goals / Non-Goals

**Goals:**

- 建立清晰的数据访问边界，使同一产品业务契约可以由 SQLite 本地实现或 Supabase 云端实现。
- 保证云端模式的业务实体只在 Supabase 中持久化，正常运行不依赖 SQLite 业务表、outbox 或云端缓存回填。
- 将跨实体一致性、版本校验、设备协调和幂等性放到云端事务边界。
- 允许分领域迁移和验证，但不允许同一用户操作同时经过新直连路径和旧同步路径双写。
- 为旧云端工作空间提供可恢复、可阻断旧客户端的升级流程。

**Non-Goals:**

- 不为云端模式提供离线编辑、后台稍后上传或跨空间自动合并。
- 不把前端改为直接持有 Supabase 客户端、access token 或数据库表写权限。
- 不在本变更中重新设计事项、计划、计时、报告或重复事项的产品语义。
- 不删除 SQLite 或取消本地模式。
- 不承诺在复制时自动识别和合并两边的逻辑同一实体。

## Decisions

### 1. 使用 Rust 存储端口统一业务契约，前端不区分具体数据库 API

在 Tauri 后端建立按业务领域划分的存储服务边界，例如事项、今日计划、计时、报告和共享设置。现有 Tauri 命令保留面向前端的稳定请求/响应 DTO，并根据当前存储模式将调用路由到 SQLite 实现或 Supabase 实现。领域服务负责输入校验、权限上下文、统一错误分类和刷新领域，存储实现负责各自的查询与事务。

不采用“让每个现有函数内部到处判断 storage_mode”，因为这会把二十余个模块变成两套分支交织的代码，难以证明云端路径没有意外写入 SQLite。也不采用前端直接访问 Supabase JS SDK，因为那会复制 Rust 中已有的安全、设备授权、复合操作和错误处理，并扩大 token 暴露面。

迁移期间可先从 Tauri 命令外层抽取端口，复用现有 SQLite 函数作为本地适配器；云端适配器必须只调用 Supabase 查询/RPC。每个领域完成直连验收后再从旧同步实体清单中移除，避免半迁移实体被双写。

### 2. 本地 SQLite 分为“本地业务库”和“设备元数据”，云端模式只允许后者

不要求立即拆成两个物理 SQLite 文件，但代码层必须建立访问约束：

- 本地业务域：subjects、tasks、plans、recurrence、time、reports、shared settings、integration bindings 等，仅本地模式和显式复制/救援流程可访问。
- 设备域：storage mode、Supabase 项目配置、当前 cloud workspace/device id、窗口和路径偏好、自动化设备配置、会话元数据引用等，两种模式可访问。
- 旧云端缓存、`sync_outbox`、`local_sync_state`、冲突和 deferred 表只允许升级兼容工具读取；启用直连协议后不得进入日常查询或写入。

为防回归，新增运行时守卫和测试：云端业务命令执行前后检查 SQLite 业务表及 outbox 无变化。最终清理阶段可删除只服务旧云端同步的表；是否物理拆库属于后续优化，不是正确性前提。

### 3. 云端读取使用面向页面的查询 RPC，而不是复用完整快照或逐表 REST

为现有页面补充粗粒度查询 RPC/只读函数，例如工作台初始数据、事项分页/树、今日计划、当前活动计时、时间历史、报告列表与详情、模板和共享设置。查询以工作空间、当前设备、过滤条件和游标为输入，在服务端统一执行 RLS、设备授权和字段投影。返回 DTO 应与现有前端所需结构接近，避免客户端为一次页面加载发出大量逐实体请求。

不复用 `cloud_full_snapshot` 作为日常读取，因为完整快照成本随数据量增长，且会让单页刷新下载无关领域。不让桌面端直接组合 PostgREST 多表请求，是为了把工作空间过滤、层级排序、归档规则、当前日期和兼容转换稳定地留在服务端契约内。

列表采用稳定游标分页；聚合工作台允许返回一个服务器时间和数据版本/变化序号，便于前端识别同一加载边界。所有响应携带可识别的 schema generation，旧客户端遇到不兼容版本时进入升级提示而不是猜测字段。

### 4. 云端写入全部使用业务 RPC，简单 CRUD 也不允许客户端直接写表

每个写 RPC 至少验证：Auth 用户、工作空间归属、当前设备授权、直连协议版本、工作空间世代、操作 ID、实体期望版本和业务约束。成功响应返回受影响实体的权威 DTO、当前版本、服务器时间、变化领域和必要的关联状态。

简单 CRUD 仍使用业务 RPC 而非客户端表写，是为了统一操作记录、幂等、软删除、父子事项约束和结构化并发错误。复合操作沿用或扩展现有原子 RPC，包括计时转换、批量计划、实际工时调整、重复事项推进、报告生成/更新和工作空间恢复。

响应丢失时客户端使用原 operation ID 重试或查询 processed operation，服务端返回同一结果。网络错误不产生本地业务写；只有收到明确成功结果后前端才采用返回数据。对于适合即时反馈的操作，可在内存中乐观展示，但失败时必须回滚并重新查询，不能落 SQLite。

### 5. Realtime 退化为领域失效信号，页面查询承担收敛

保留 `workspace_changes` 或建立更精简的领域通知流，payload 只需包含 workspace、change sequence、workspace epoch 和 domains。客户端收到通知后合并短时间内的重复领域，重新调用相应查询；当前不可见领域只标记 stale，在用户进入时加载。

断线和休眠恢复不补放每条实体变化，而是比较连接前后的 change sequence/epoch 并刷新当前页面、活动计时和全局摘要。工作空间恢复导致 epoch 变化时清空进程内页面缓存并重新查询。

不把 Realtime payload 当业务真相，避免通知丢失、乱序或重复影响正确性；Supabase 查询结果始终是权威状态。

### 6. 云端可写性使用统一状态机，断网时只保留进程内展示

云端连接状态收敛为：

```text
connecting --> online_writable
     |              |
     v              v
offline_readonly <- degraded_readonly
     |
     v
reauth_required
```

`online_writable` 需要会话有效、设备授权有效、协议兼容且最近一次必要查询成功。网络不可达、Supabase 5xx、查询超时进入 `offline_readonly` 或 `degraded_readonly`；明确 token/设备撤销进入 `reauth_required`。所有业务 mutation 在 Tauri 后端再次检查状态，不能只依赖按钮禁用。

内存中的 Vue 状态允许继续展示，并标记最近成功刷新时间和“可能不是最新”。应用退出后不持久化云端业务页面缓存；再次启动且无法连接时显示不可用空状态。这样牺牲离线浏览历史换取“不把陈旧本地内容误认为云端真相”的清晰边界。

### 7. 并发错误是即时业务结果，不再成为后台冲突对象

云端更新使用 expected version、workspace epoch 和必要的租约 token。服务端以结构化代码返回 `VERSION_CONFLICT`、`ENTITY_DELETED`、`LEASE_LOST`、`WORKSPACE_EPOCH_STALE`、`DEVICE_REVOKED` 等，并附带当前实体或刷新指令。客户端立即结束本次编辑、保留可复制的用户输入（适用时）并重新查询。

首期不实现字段级自动合并。它看似方便，但会重新引入难以解释的合并策略；同一实体发生真实并发时，以显式拒绝和最新状态为准。文本报告等用户输入可在内存中保留草稿，让用户人工复制，但不得自动覆盖新版本。

### 8. 一次性复制复用快照格式，但以 staging + 原子切换实现完整替换

定义稳定、版本化的数据包格式，覆盖所有共享业务实体与安全的共享设置，不包含凭据、设备授权、outbox、操作记录、自动化命令和本机路径。现有本地备份实体清单与云端快照实体清单应收敛为同一个可测试目录，防止后续新增表只进入一侧。

本地到云端：先从本地一致性事务导出并校验数据包；若云端非空，先创建并验证 `pre_replace` 安全快照；上传至服务端 staging，完成引用、计数、哈希和 schema generation 校验后，在恢复锁保护下单事务替换云端业务表、提升 epoch 并发布 reset 通知。

云端到本地：服务端从一致性边界导出数据包；客户端完整下载和校验，先创建本地安全备份，再在单个 SQLite 事务中替换本地业务空间。下载失败或校验失败不得打开替换事务。

复制默认保留当前模式，完成后让用户明确选择是否切换目标空间，避免把“复制”隐式变成“迁移并删除源”。源数据永不自动删除，两边不建立映射或同步关系。

### 9. 使用工作空间存储协议代际阻止旧客户端写入

在云端工作空间增加 `storage_protocol` 或等价代际字段，至少区分 `sync_v1` 与 `direct_v2`。所有旧同步写 RPC、增量补丁和租约入口在写入前检查协议；工作空间切到 `direct_v2` 后拒绝旧协议写入并返回 `CLIENT_UPGRADE_REQUIRED`。所有新直连 RPC 只接受 `direct_v2`。

不能只依靠桌面端版本判断，因为离线旧客户端可能在迁移完成后重新上线。服务端屏障是避免旧 outbox 覆盖直连数据的正确性条件。读取和显式升级/救援 RPC 可在受控范围兼容 `sync_v1`。

### 10. 升级采用“先清旧队列，再原子切协议”，不自动丢弃本机修改

升级检查当前工作空间所有已注册设备的协议状态，并至少严格检查当前设备的 pending/sending/failed/conflict outbox。当前设备旧队列非空时进入 migration blocked：

1. 在线完成旧队列并拉取最终权威状态；或
2. 导出带旧队列诊断和本地业务数据的救援备份，用户明确确认放弃；
3. 再次确认云端 epoch 和 change sequence；
4. 服务端事务切换 `direct_v2` 并写入协议变更记录；
5. 客户端停止旧协调器，清理仅用于云端缓存的本地业务数据或标记为隔离遗留，不再参与运行；
6. 使用新查询 API加载页面。

若其他设备仍为旧版本，切换前显示设备清单和影响，但不要求设备在线；协议切换后旧设备由服务端拒绝写入。它们升级时直接进入新查询路径，旧 outbox 只能导出救援，不得再上传。

### 11. 分领域实现，最终以工作空间级开关一次切换

开发阶段可以逐个完成 cloud repository 和 RPC，但生产工作空间不得在一部分领域直连、一部分领域同步。使用开发/测试特性开关验证各领域；只有事项、计划/重复、计时/未归属、报告/模板、共享设置/集成绑定、数据保护和复制全部达到直连契约后，才允许工作空间从 `sync_v1` 切到 `direct_v2`。

这样避免跨领域操作出现一半写云端、一半先写 SQLite。切换后的发布版本保留旧升级工具一段兼容期，但日常业务代码只运行直连路径。

### 12. 云端数据保护直接围绕权威库运行

现有操作记录、快照、恢复锁和 workspace epoch 继续保留。自动快照由云端调度或成功业务写触发的服务端逻辑创建，不依赖本机同步完成。恢复 commit 完成后通过 epoch/reset 通知所有在线客户端清空内存数据并重新查询。

本地备份组件仅对本地空间工作；云端模式如需文件导出，应调用云端一致性导出 API，而不是读取 SQLite。现有“本地缓存重置”能力删除，因为云端模式没有持久化业务缓存。

## Risks / Trade-offs

- [云端模式失去离线编辑与离线历史浏览] -> 在设置和首次切换时明确说明必须联网；断网统一只读，保留当前进程已加载内容和最近刷新时间。
- [大量现有业务逻辑与 SQL 绑定，双实现可能发生语义漂移] -> 先提取共享业务契约和 DTO，为 SQLite 与 Supabase 建立同一组契约测试；对关键复合操作只保留一个明确的领域规则来源。
- [一次性重构范围过大] -> 分领域建设和测试，但只允许工作空间级原子启用，避免生产混合架构。
- [页面查询 RPC 过粗会产生大响应，过细会产生请求瀑布] -> 按用户页面和领域设计聚合查询，使用游标分页、字段投影和可观测性能预算。
- [请求成功但响应丢失会让用户不确定] -> 所有 mutation 使用稳定 operation ID 和 processed operation 结果，允许查询/幂等重试，不回退到本地队列。
- [旧客户端或旧 outbox 在切换后覆盖数据] -> 服务端 `storage_protocol` 屏障拒绝全部旧写入口；切换前处理当前设备队列并提示其他设备影响。
- [显式完整替换可能造成误操作] -> 展示实体计数和替换影响，云端先建安全快照、本地先建安全备份，staging 完整校验后才原子提交。
- [Realtime 丢失导致页面陈旧] -> Realtime 只作为失效提示；重连、窗口重新激活和关键操作后根据 change sequence 执行权威重查。
- [Supabase 故障使云端用户完全不可写] -> 这是取消同步后的明确权衡；提供本地模式作为独立可离线空间，但不在故障时自动切换或合并。
- [继续保留同一个 SQLite 文件可能被未来代码误用] -> 云端路径增加访问守卫、数据库变化断言和静态/集成检查；待兼容迁移稳定后再删除遗留云端缓存表。

## Migration Plan

1. 在不改变现有生产行为的前提下建立领域存储端口、统一 DTO、结构化云端错误和双实现契约测试；现有 SQLite 实现继续服务全部用户。
2. 追加部署 Supabase `direct_v2` schema：工作空间协议字段、页面查询 RPC、直连写 RPC、processed operation 查询、复制 staging/替换接口和旧协议写屏障；默认现有工作空间仍为 `sync_v1`。
3. 逐领域实现并在隔离测试工作空间验证云端 repository，覆盖事项、计划与重复、计时与未归属、报告与模板、共享设置与集成绑定、数据保护。测试期间禁止同一操作同时进入 outbox。
4. 完成 Realtime 失效刷新、云端只读状态机和新数据存储设置页，移除新协议下的同步队列、冲突和缓存重置入口。
5. 完成双向一次性复制、完整性目录、安全快照/备份、哈希校验和失败回滚测试。
6. 为现有用户提供升级预检：设备列表、当前旧队列、救援备份和放弃确认；队列清空或明确放弃后由服务端事务把工作空间切换为 `direct_v2`。
7. 使用两个以上设备进行端到端验收：在线 CRUD、真实版本冲突、响应丢失幂等、计时接管、Realtime 断线、Supabase 故障只读、快照恢复、旧客户端拒绝和双向复制。
8. 发布直连版本并观察查询延迟、错误分类、旧协议拒绝和数据一致性；保留救援导出及只读诊断一段兼容期。
9. 确认所有活跃云端工作空间已迁移且无回滚需求后，删除日常 `cloud_sync` 协调、outbox 生成/拉取/冲突 UI 和仅服务云端缓存的代码与表；SQLite 本地模式保持不变。

回滚客户端版本时，已经切为 `direct_v2` 的工作空间不得降回 `sync_v1`，旧客户端只能被服务端拒绝并提示升级。若新直连客户端需要紧急停用，服务端关闭直连 mutation、保留只读查询与数据导出，修复后重新开放；不得通过重新启用旧 outbox 写入来回滚架构。
