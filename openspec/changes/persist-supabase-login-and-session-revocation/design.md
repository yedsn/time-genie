# Design

## Context

TimeGenie 已在 `src-tauri/src/supabase.rs` 中把 Supabase access/refresh token 序列化保存到 Windows Credential Manager，并在 token 临近过期时调用 refresh grant。当前 `cloud_session_get` 只对网络错误回退到已保存快照，其他凭据读取或刷新异常会被折叠成未登录；云端业务请求连续返回 `AUTH_FAILED`/`AUTH_REQUIRED` 时还会删除保存的会话。

Supabase schema 已有 `devices.revoked_at` 和 `is_registered_device`，部分写入 RPC 会检查设备，但设备列表/撤销命令尚未接通，普通数据读取也不能把一个仍然有效的用户 JWT 与具体设备可靠绑定。Supabase Auth 的当前会话注销和全局注销可由用户 JWT 发起；管理端能力只能留在 Supabase 受控环境，不能下发 service_role key。

项目同时正在进行应用标识迁移。旧凭据库 service 到新 `timegenie` service 的一次性重新登录属于迁移行为，本变更不承诺读取旧 service，但新 service 下成功登录后必须长期保持。

## Goals / Non-Goals

**Goals:**

- 用显式状态表达“在线已验证”“离线保留会话”“需要重新登录”，避免把所有异常映射成布尔值。
- 把会话删除限制在可证明的终止事件，并保留 refresh token 轮换后的原子更新。
- 在所有同步上传之前校验设备授权，使远程单设备撤销先于待同步数据上传生效。
- 用用户 JWT 完成普通退出和全设备退出，并用 RLS/安全定义 RPC 管理 TimeGenie 设备授权。
- 保持密码、refresh token、service_role key 不进入 SQLite、日志、前端状态或导出。

**Non-Goals:**

- 不实现管理员控制台或在桌面端嵌入 Supabase Studio。
- 不保存登录密码，也不增加“记住密码”选项。
- 不把 TimeGenie 设备授权替代为通用企业设备管理或多人工作空间权限系统。
- 不保证远程撤销能影响完全离线且尚未重新联网的进程；撤销在其下一次联网前置检查时生效。
- 不在本变更中自动迁移旧产品名对应的系统凭据。

## Decisions

### 1. 用结构化会话状态替代单一 `signedIn` 推断

后端会话快照增加状态枚举，例如 `authenticated`、`offline_saved`、`reauth_required`，并保留脱敏账号、过期时间和可展示的原因码。前端按状态决定账号标签、同步按钮和密码表单：只有 `reauth_required` 才展示重新登录。

备选方案是继续使用 `signedIn: boolean` 并增加错误文案，但布尔值无法区分“凭据存在但暂不可验证”和“凭据不存在”，容易再次出现误退出。为了兼容现有调用，可以在过渡期继续返回派生的 `signedIn` 字段，但状态枚举是判断依据。

### 2. 会话凭据继续保存在系统凭据库，写入采用完整替换

登录或刷新成功后，把 user id、email、access token、refresh token 和到期时间作为一个完整记录写入稳定账户键；refresh token 轮换时先获得完整响应，再一次性覆盖凭据。内存缓存只做进程内加速，不能成为持久化事实来源。

稳定账户键继续兼容当前 workspace 范围的旧键读取，完成读取后可回写稳定键。不会保存密码，也不会把完整 token 返回给前端。

### 3. 错误分类基于可证明的身份结果，而不是笼统的 HTTP 状态

会话刷新错误分为：

- `transient`：网络、超时、429、5xx、响应暂不可解析；保留凭据。
- `credential_unavailable`：系统凭据库暂时错误；不删除凭据，向界面暴露可恢复状态。
- `definitive_auth_invalid`：refresh token 无效/已撤销、用户禁用、明确的 Auth session missing；清除凭据。
- `application_error`：Schema、RLS、版本冲突、业务校验；保留凭据。

业务请求的 401/403 本身不作为删除依据。可克隆请求先强制刷新并重试一次；不可安全重放的请求只刷新认证状态并返回可重试提示。只有刷新端点给出明确失效结果，或设备授权检查确认撤销，才删除会话。

备选方案是根据所有 401/403 退出，逻辑简单但会把 anon key 配置、RLS 或短暂网关问题误判为用户会话失效，正是当前反复登录问题的来源。

### 4. TimeGenie 设备授权与 Supabase Auth 会话分层管理

`devices` 继续表示 TimeGenie 应用层设备授权，并补充/确认授权世代、最近校验时间和撤销审计所需字段。设备注册使用当前安装的稳定 `device_id`；重新登录已撤销设备时显式创建新的授权世代或重新授权并记录时间，不能依靠普通 upsert 静默清空 `revoked_at`。

设备列表和撤销通过受 RLS 保护的查询或安全定义 RPC 完成，RPC 根据 `auth.uid()` 校验工作空间所有者，禁止客户端传入任意用户身份。所有云端同步上传入口在处理 outbox 前调用设备授权检查；发现撤销后不上传任何记录，保留 outbox 和本地数据。

Auth 层负责 token 生命周期：

- 普通退出/撤销当前设备：调用 Supabase Auth logout 的当前会话范围，再清除本机凭据。
- 退出所有设备：先调用受控服务端操作把全部 TimeGenie 设备标记为撤销，再调用 Supabase Auth global logout 撤销该用户全部 refresh token。
- 撤销其他单台设备：立即撤销 TimeGenie 设备授权；目标客户端在下次联网前置检查时调用当前会话 logout 并清除本机凭据。

Supabase 的普通用户 API不保证能够从一台设备直接精确删除另一台设备的某一个 Auth session，因此单设备远程撤销以应用层授权为强制边界，并在目标客户端上线时完成 Auth logout。若部署环境提供受保护的 Edge Function/Admin API，可额外即时撤销对应 Auth session，但它是增强项，不能成为正确性的唯一依赖。

### 5. 全设备退出按“先封禁应用访问，再撤销 Auth”排序

执行顺序为：二次确认 -> 云端事务撤销全部 `devices` 并释放设备租约 -> 请求 Supabase Auth global logout -> 清除当前设备凭据和缓存 -> 切换到安全本地状态。这样即使 Auth logout 请求的响应中断，设备授权也已阻止后续同步上传；客户端再次联网会识别撤销。

如果设备授权事务失败，则不发起 global logout，并返回失败，避免出现部分设备表状态未更新但当前设备已经退出的不可解释结果。若授权事务成功而 global logout 返回不确定的网络结果，当前设备仍清除本地会话并提示用户后台注销结果待确认。

### 6. 离线撤销遵循“先校验、后上传”

远程撤销无法被完全离线的设备即时感知。离线设备仍按现有本地优先机制把修改写入 SQLite/outbox；恢复网络后同步流程必须先刷新/验证 Auth，再验证当前 `device_id` 的授权，最后才允许上传 outbox。若发现撤销，outbox 保留且进入受阻状态，用户重新登录后需明确选择审阅、继续同步或转为本地数据，不能静默上传。

这比“云端模式离线一律只读”更符合项目已有本地优先目标，同时保证撤销一旦可被观察就不会继续向云端写入。

### 7. 后台撤销使用两条明确路径

管理员撤销指定设备时更新受控的 `devices.revoked_at`（优先通过项目提供的 SQL/RPC/管理工具，而不是修改客户端凭据）；管理员撤销账号全部 Auth 会话时使用 Supabase Auth 管理能力。客户端不需要知道操作来源，只根据设备授权检查或 Auth 刷新结果收敛到 `reauth_required`。

项目文档将给出后台操作说明及安全边界，但不会在仓库中存放 service_role key。

## Risks / Trade-offs

- [远程单设备撤销不能让完全离线进程即时退出] -> 明确下一次联网生效，并强制同步前先校验授权，防止撤销后上传。
- [应用层撤销后，旧 JWT 在到期前理论上仍是有效 Auth JWT] -> 所有 TimeGenie 写入口和同步 RPC检查设备授权；敏感读取逐步收敛到带设备校验的 RPC/快照接口，并可在部署具备安全服务端能力时追加精确 Auth session 撤销。
- [全局注销与设备撤销跨两个系统，无法形成单个数据库事务] -> 先撤销设备授权，再执行 global logout；记录阶段结果并采用安全失败策略。
- [错误分类依赖 Supabase Auth 返回码与消息] -> 优先使用稳定错误码，消息匹配仅作兼容；为已知无效、网络故障、限流、5xx 和未知 401/403 建立回归测试。
- [凭据库暂时不可用时无法取得 token] -> 保留账号上下文并暂停云端操作，不删除或覆盖凭据；后续重试读取。
- [重新授权设备后存在撤销期间产生的 outbox] -> 默认阻止自动上传，要求用户明确处理，避免把撤销后的未知修改带回云端。
- [现有工作区存在大量未提交云端同步改动] -> 实施时只触碰会话生命周期相关区域，按文件和测试边界合并，避免覆盖正在进行的同步改造。

## Migration Plan

1. 先部署 Supabase schema 增量：设备撤销 RPC、授权检查与必要审计字段，并验证旧客户端仍可读取现有数据。
2. 发布兼容型客户端：能够读取现有凭据格式，新增结构化状态和严格错误分类；保持现有 `signedIn` 派生字段供旧前端路径过渡。
3. 接入同步前设备授权检查、设备列表、单设备撤销、当前设备 logout 和全设备 logout。
4. 更新界面状态与设备管理交互，最后启用撤销后 outbox 受阻处理。
5. 用两个独立安装实例验证长期恢复、离线重连、单设备撤销、全设备退出和后台撤销。

回滚时可回退客户端到旧版本；新增 schema 字段和 RPC 保留但不调用。若必须回滚 schema，先确认没有设备处于仅由新授权世代表示的状态，避免错误恢复已撤销设备。
