# Design

## Context

参见 [proposal.md](./proposal.md) 的动机。现有 `obsidian.rs` 已经具备日报文件读取、导入批次、候选确认和来源引用，`tasks.rs` 已有只解析“明日计划”的 Markdown 解析器；前端 `MainWorkbench.vue` 和 `PlanListEditor.vue` 已有“导入昨日计划”预览入口。另一方面，当前 Obsidian 根目录与日报路径规则是全设备共用设置，主体实体本身没有本机路径字段；今日实例、完成状态以及实际用时调整已经具有独立的数据与同步语义。

此次变化横跨设备设置、主体设置、Markdown 解析、两类事项创建、实际调整、云同步和备份，因此需要明确统一事务边界和来源身份。

## Goals / Non-Goals

**Goals:**

- 最大限度复用既有事项、今日实例、完成和实际调整模型，不引入第二套工时口径。
- 对真实日报格式提供确定、可预览的解析结果，并使重复确认安全幂等。
- 保持绝对文件路径仅在当前设备，业务导入结果继续参与既有同步与数据保护。
- 让待办和今日入口共享同一预览与解析契约，仅在确认阶段选择不同写入目标。

**Non-Goals:**

- 不再解析或导入“明日计划”“下周计划”区域。
- 不双向修改 Markdown，不根据应用内事项更新源日报。
- 不把日报实际用时伪装成计时区间，也不改变未分配时间。
- 不做基于标题的全库去重；幂等只针对可追溯的同一源事项和目标。
- 不在本变更中重新设计主体实体、通用文件集成框架或现有报告写入流程。

## Decisions

### 1. 主体日报目录使用动态设备设置键

使用类似 `subject_daily_report_directory:<subject_id>` 的 `device_settings` 键保存绝对目录，并在设置校验中只允许合法 UUID 后缀。主体 DTO 不增加路径字段，主体设置弹框通过设置快照读写对应键。

选择该方案是因为路径属于设备环境而不是主体业务数据；沿用 `device_settings` 可天然避免进入云端共享设置。备选方案是在 `subjects` 表加字段，但会把 Windows 绝对路径错误同步到其他设备；另一个备选是继续使用全局 Obsidian 根目录，无法满足多主体目录。

目录选择通过现有 Tauri dialog 插件完成，仍允许手动输入和清空。文件名规则固定为 `YYYYMMDD.md`，不继续复用旧的 `{date}` 路径规则，减少新流程的配置组合。现有报告写入仍使用旧 Obsidian 根目录和路径规则。

### 2. 新增面向顶部事项的独立解析模式

把 Markdown 列表词法处理、缩进栈和时长解析抽为可复用内部函数，新导入模式的范围状态机如下：

```text
文件开始
   |
   v
等待首个 Markdown 标题
   | 找到
   v
解析顶部列表项 ---------------------+
   |                                |
   | 遇到明日/下周/下一工作日计划标题 | 文件结束
   v                                v
停止解析                         停止解析
```

候选记录扩展为：标题、父候选、层级顺序、源行、规范化源文本、状态标记、预计分钟、原始实际分钟、可导入实际分钟、警告和幂等指纹。状态图标只从清理前标题的开头识别；时长元数据从标题尾部的尖括号块识别。绿色候选的“可导入实际”取解析值，其他状态即使有实际字段也置空，且预览不显示原始实际或忽略提示。

时长使用十进制定点换算并按最接近整数分钟取整，避免浮点误差；支持大小写不敏感的 `h` 和 `min`，允许中文全角冒号及可选空格。无效或负数只产生字段告警，不阻断其他候选。

不修改旧解析器来改变原有语义，而是让旧入口在 UI 中被新流程替代后保留兼容代码，待确认无调用后再在实现阶段安全删除。这样降低对历史测试和其他潜在调用的回归风险。

### 3. 预览批次记录文件快照与目标类型

扩展或新建日报导入批次模型，至少保存：

- `subject_id`、`device_id`、`source_date`、规范化 `source_path`。
- `target_kind`：`backlog` 或 `day_instance`。
- 文件内容哈希与修改时间、原始 Markdown、解析警告、批次状态和版本。
- 候选的状态、预计、原始/可导入实际、层级位置、源指纹及已确认目标 ID。

预览不写业务事项。确认前重新检查当前文件的哈希和修改时间；文件已变化时拒绝旧预览，要求重新读取，避免用户确认的内容与实际文件不一致。前端日期切换直接创建新预览批次，不复用旧候选选择。

备选方案是仅由前端解析并提交标题列表，但这会丢失可信文件快照与幂等来源，不采用。

### 4. 来源身份按主体、设备、源文件、目标和候选指纹区分

每个候选生成 `source_item_fingerprint`：对规范化源路径、源日期、层级序号路径、清理后的标题、状态及解析时长做规范序列化后哈希。确认记录以 `(subject_id, device_id, source_path, source_date, target_kind, source_item_fingerprint)` 保持唯一。

这能保证未修改日报的重复预览稳定跳过，并允许同一来源分别导入长期待办和今日实例。若用户修改了源事项文本或时长，指纹变化后会被视为新候选；系统不会隐式更新先前导入的事项，预览中应显示相似标题可能已经存在的提示，但最终选择权留给用户。基于全库标题去重会误伤合法同名事项，因此不采用。

确认请求另带 `client_request_id`，用于处理双击和网络重试；同一请求返回已保存结果。

### 5. 两类目标共享一个原子确认服务

确认服务按父级优先、同层顺序依次处理选中候选，并自动补齐被选子项所需的祖先。整个批次使用单个数据库事务：

1. 锁定并验证预览批次、版本、文件快照和请求幂等键。
2. 读取已确认来源身份，过滤已经导入的候选。
3. 创建目标事项树。
4. 为绿色候选设置完成状态和日报日期内的完成时间。
5. 写入符合规则的实际调整。
6. 写入来源映射、批次结果和云端操作队列。
7. 提交后按既有策略触发云端 flush。

任一步失败均回滚业务数据、调整和来源映射。现有“预览后确认”接口可演进为新的日报导入 DTO；旧接口如仍有测试依赖，可暂时作为适配层。

### 6. 长期待办和今日实例使用各自既有模型

`backlog` 目标创建普通长期事项：无 `day_instance_date`，预计写入 `estimate_minutes`，不创建 `task_day_plans` 或今日来源链接。

`day_instance` 目标创建所选日报日期的 `member` 实例：`day_instance_date` 为源日期、无长期 `day_instance_source_task_id`；父级若只是为选中子项补齐且没有被显式选择，可使用 `context`，显式选择的父级使用 `member`。预计同时初始化整体预计与该日期的 `task_daily_estimates`。

完成时间必须落在源日期。为避免导入时刻和夏令时边界造成跨日，后端使用工作空间时区把源日期的本地 12:00 转为时间戳；这是一条确定的“日期归属”时间，不声称是实际完成时刻。

### 7. 日报实际写入现有实际用时调整模型

只有绿色候选且解析出有效实际分钟时才处理实际。创建目标事项后读取该事项在源日期的最终实际基线，以日报分钟为目标，写入 `delta = target - baseline` 的调整，`note` 标识“从 Obsidian 日报导入”，并使用专门的来源类型或批次引用保存审计关系。差额为零时不创建调整，但仍记录来源候选已完成，避免重复确认。

这种做法沿用“最终实际 = 分配 + 调整”的现有口径，可以表达已有实际基线，也不产生虚假起止时间。直接新增全额调整会在已有分配时重复累计；创建时间片会污染原始工时和待分配分钟，均不采用。

### 8. UI 复用一个导入弹框并明确目标

`PlanListEditor` 的进行中工具区和今日工具区均发出带 `targetKind` 的日报导入事件；今日概览如存在独立入口，也调用同一打开方法。弹框顶部显示主体、目标类型、日期和源路径，主体跟随当前页面选择，日期默认当前工作日期。

候选使用树形列表展示勾选、状态、预计、绿色事项的可导入实际和已导入标记；未完成事项不显示源实际字段或忽略提示。今日实例预览同时读取同一主体、所选日期的今日列表，用标题严格相等判断已有事项并将对应候选默认取消勾选，但不禁用复选框、不改变来源幂等规则，也不做模糊去重。解析告警紧邻对应行。确认成功后刷新工作数据：长期目标保持当前标签，今日目标仅在源日期等于当前工作日时立即出现在当前今日列表；历史日期成功后用消息说明已写入历史日期。

### 9. 同步、备份和兼容边界

导入产生的普通事项、今日实例、日预计和实际调整继续使用现有云端实体与版本机制。新增来源映射需要纳入本地备份/恢复；如果来源映射不需要跨设备阻止导入，则保持设备本地并通过 `device_id` 区分。由于远端设备没有源路径，也不会主动读取该文件。

冲突处理选择“以本地为准”时不能只把冲突操作改回待同步。后端需要以云端快照中的最新版本重设基线，合并同一实体后续操作，立即排空队列完成覆盖，再拉取本次云端写入形成的权威版本。本机只有在冲突数和待同步数都归零后才返回成功，避免本地仍持有旧版本并在下一次编辑时再次冲突。

立即覆盖过程中如果会话失效，前端需要重新读取会话、同步状态和本地冲突列表，并识别被覆盖失败信息包裹的 `AUTH_*` 错误。认证错误可能发生在冲突处理开始前，也可能发生在本地最终版本已经从冲突转为待同步操作之后：前一种情况保留冲突并在恢复连接后让用户再次确认，后一种情况移除已处理的陈旧冲突展示，恢复同步即可，不得要求再次处理同一冲突。确实需要重新验证时引导到登录区；如果本机仍保存有效账号但网络不可用，则只提示恢复网络后继续。所有情况都不得丢弃本地版本、冲突或待同步内容，也不得提前显示覆盖成功。

为了让恢复后的同一设备仍能识别已导入来源，备份包含来源映射但不必包含绝对目录设置；恢复到不同设备时目录仍需重新配置。普通工作数据导出和云快照不得泄露绝对路径。若备份格式当前整库复制包含 `device_settings`，恢复流程必须继续执行其既有敏感/设备设置过滤规则。

## Risks / Trade-offs

- [源文件修改会产生新指纹并可能形成业务重复项] → 预览显示来源变更和相似标题提示，不自动更新旧事项，也不使用高风险标题级强去重。
- [Markdown 缩进可能混用 Tab 和空格] → 解析器将 Tab 规范化为固定缩进层级并为跳级缩进产生警告，仍尽可能保留最近合法父项。
- [历史完成时间不是实际完成时刻] → 使用源日期中午作为稳定日期归属，并在审计来源中明确它来自日报导入。
- [导入大量历史事项会产生较多同步操作] → 单批事务写入并复用批量云端操作封装；UI 在确认期间禁用重复提交。
- [旧“导入昨日计划”代码和数据表可能暂时共存] → 首期通过适配或新批次类型保持兼容，完成回归后再删除无调用分支，不在迁移中破坏既有批次。
- [设备本地来源映射无法阻止另一设备手动导入同一文件副本] → 绝对路径和文件访问本来就是设备特定行为；业务同步冲突仍按既有事项规则处理，首期不引入跨设备文件身份。

## Migration Plan

1. 增加设备主体日报目录键校验，并新增或扩展日报导入批次、候选与来源映射字段；迁移保持旧 Obsidian 导入记录可读。
2. 发布后主体日报目录默认为空，不自动把旧全局 Obsidian 根目录映射到所有主体，避免猜错目录。
3. 上线新解析和确认接口，再切换待办/今日 UI 入口；报告写入继续使用旧设置。
4. 通过本地与云端模式验证后，移除或隐藏旧“导入昨日计划”入口，但保留数据兼容读取。
5. 回滚应用版本时，新建业务事项仍是普通兼容数据；旧版本忽略新来源映射和设备设置。数据库迁移本身不降级，必要时只回滚 UI 入口。
