# Design

## Context

参见 [proposal.md](proposal.md) 的动机。当前普通待办和今日待办共享一个 `savingTaskIds` 集合：保存开始时加入事项 ID，保存期间再次调用会直接返回 `false`。这能避免并发请求，却会丢弃后续保存意图。

待办字段编辑由 `PlanListEditor.vue` 在标题失焦、日期变化和预计时长编辑结束时触发；实际持久化集中在 `store.ts` 的 `saveTask` 与 `saveTodayTask`。完成、删除、移动、缩进、重复规则和计时等操作使用乐观版本号，因此必须与字段保存共享有序边界。新建事项还存在临时 ID 被后端返回 ID 替换的身份迁移。

## Goals / Non-Goals

**Goals:**

- 为普通待办与今日待办提供统一、可测试的按事项提交协调语义。
- 保证最后一次字段编辑落盘，并避免同一事项的并发版本请求。
- 让版本敏感操作能够显式冲刷待保存编辑。
- 保留不同事项间的并行度与现有本地优先写入链路。

**Non-Goals:**

- 不修改 Tauri 命令、Rust 数据模型、SQLite 迁移或 Supabase 协议。
- 不替代后端乐观版本控制，也不自动解决来自其他设备的真实数据冲突。
- 不把完成、删除、排序等离散操作做成可合并的防抖操作。
- 不新增全局“保存中”交互或重做云同步状态展示。

## Decisions

### 1. 采用按逻辑事项的 single-flight 尾随提交，而不是经典节流

每个逻辑事项维护独立槽位，槽位包含当前运行请求、最新待提交快照、短合并定时器以及等待该槽位稳定的调用方。一次请求执行时不启动同事项的第二个请求；如果执行期间出现新快照，则在当前请求成功并更新版本后继续执行一次尾随提交。

选择理由：经典节流只限制频率，不能天然保证最后一次修改落盘；若节流窗口允许并发，多个请求可能携带相同版本。纯尾触发防抖也无法覆盖请求已经发出后再次修改的情况。

备选方案：

- 保留 `savingTaskIds` 并让调用方重试：重试责任分散，容易遗漏。
- 全局串行队列：实现简单，但会让互不相关的事项互相阻塞。
- 每个字段独立队列：会增加版本协调复杂度，也难以形成完整最新状态。

### 2. 队列保存完整可持久化快照，并在请求发起时冻结

调度保存时从当前响应式事项生成包含标题、预计日期、预计时长、备注和项目名的快照。等待窗口中的新保存覆盖待提交快照。请求发起后冻结该次快照，后端返回时只更新权威字段与版本，不覆盖请求期间用户已经修改的新值；若检测到待提交快照，则用新的版本继续提交。

该设计避免异步响应把界面中较新的编辑回滚为旧请求内容。快照比较同时用于判断是否确实需要尾随请求。

### 3. 短合并窗口默认约 250ms，但正确性不依赖具体时长

普通字段保存使用尾触发短窗口合并相邻保存意图。250ms 与当前基于失焦/变化的交互相匹配，足以吸收连续字段切换，又不会让自动保存产生明显延迟。实现应把窗口作为内部常量，测试不得依赖精确墙钟时序，而应通过可控调度或显式冲刷验证。

即时操作调用 `flush(logicalTaskId)`：取消等待定时器、立即推进最新快照，并等待槽位没有运行或待提交工作。

### 4. 以逻辑提交键处理临时 ID 到持久化 ID 的迁移

新建草稿首次调度时创建稳定提交键。创建成功后更新该键关联的当前事项 ID，而不是把队列从旧 ID 拷贝到新 ID。尾随保存和等待中的即时操作都通过提交键解析最新持久化 ID。队列稳定后清理旧 ID 别名，避免长期累积。

普通待办与今日实例可以复用同一协调核心，但分别提供查找事项、创建/更新、应用权威记录和刷新派生数据的适配函数。

### 5. 只在版本敏感边界冲刷，避免扩大提交范围

以下操作在读取版本或调用后端前冲刷目标事项：完成/恢复、删除、复制、重复规则变更、排序/移动、缩进/减少缩进、备注等独立更新，以及计时开始/切换所需的事项持久化。涉及父子结构的操作还应冲刷其直接依赖的目标事项；无需冲刷整个列表。

快速批量计划等已有原子批处理保持独立，不通过字段保存队列拆分执行。

### 6. 失败终止当前槽位链并交由现有界面反馈

任一请求失败时，协调器拒绝当前调度 promise 与 `flush` 等待者，不继续执行依赖成功版本的尾随请求或即时操作。最新界面值不被旧响应覆盖；现有 `MainWorkbench.vue` 错误提示链继续向用户反馈。之后新的保存意图可重新建立调度，或页面刷新可恢复权威状态。

不在协调器内部无限自动重试，避免持续失败时隐藏问题或制造请求风暴。

## Risks / Trade-offs

- [尾随保存与权威响应合并不当可能回滚新编辑] → 请求发起时冻结快照，应用响应前比较当前界面快照，并用最新本地字段覆盖旧响应对应字段。
- [临时 ID 切换导致队列悬空或重复创建] → 使用稳定逻辑提交键和可更新的当前 ID 映射，并增加创建期间继续编辑的专项测试。
- [结构操作冲刷范围不足仍会出现旧版本] → 为每类版本敏感操作列出依赖事项，并在核心路径加入冲刷验证。
- [过度冲刷增加交互等待] → 只冲刷目标及直接依赖事项，不做全局等待；不同事项仍可并行。
- [失败后界面值与后端值暂时不一致] → 保留用户输入以便重试，同时复用现有错误提示；需要权威恢复的流程继续调用现有重新加载逻辑。
- [250ms 窗口增加轻微保存延迟] → 即时操作显式冲刷，窗口仅作用于普通字段自动保存。

## Migration Plan

1. 增加无框架依赖的提交协调核心及确定性单元测试。
2. 先接入普通待办保存，替换 `savingTaskIds` 的拒绝逻辑并验证版本更新。
3. 接入今日待办及重复事项“仅今天/今后全部”的分支，保持作用域确认发生在调度前。
4. 为版本敏感操作加入目标事项冲刷，并补充 UI/源码边界验证。
5. 运行前端类型检查、相关待办交互测试和新增协调测试。

回滚时可恢复原有 `savingTaskIds` 互斥路径；该变更不包含数据迁移或后端协议变化。
