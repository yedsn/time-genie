# Proposal

## Why

待办编辑目前使用“正在保存则拒绝后续保存”的互斥方式；当用户连续修改同一事项，或编辑后立即完成、删除、排序时，后续修改可能被丢弃，结构操作也可能携带旧版本提交。需要建立以事项为粒度的可靠提交机制，保证最后一次编辑必定落盘，同时减少短时间重复写入。

## What Changes

- 为普通待办与今日待办建立按事项隔离的提交协调机制，同一事项最多只有一个持久化请求在执行。
- 将等待提交的多次编辑合并为最新完整状态，并在请求执行期间再次发生修改时，于当前请求完成后使用最新版本补交。
- 对可合并的字段编辑采用短尾触发窗口，减少标题、预计日期、预计时长等相邻修改造成的重复持久化；该窗口仅用于优化写入次数，不承担正确性。
- 完成、删除、排序、缩进、重复规则、开始计时等依赖事项版本或身份的操作，在执行前冲刷相关待提交编辑，然后立即执行。
- 保证新建草稿由临时 ID 替换为持久化 ID 后，尚未提交的编辑继续归属于同一逻辑事项。
- 增加针对合并、尾随补交、串行执行、冲刷边界、失败恢复和临时 ID 切换的自动化验证。

## Capabilities

### New Capabilities

- `task-submission-coordination`: 规定待办编辑的按事项串行提交、最新状态合并、结构操作冲刷及失败处理行为。

### Modified Capabilities

无。

## Impact

- 主要影响 `src-ui/src/store.ts` 中普通待办、今日待办及相关版本敏感操作的保存流程。
- 可能新增独立的前端提交协调核心模块和对应验证脚本，不引入新的运行时依赖。
- Tauri 命令和 SQLite/Supabase 数据结构保持不变；现有乐观版本控制继续作为最终并发保护。
- 用户可见行为保持自动保存，但快速连续操作不再丢失最后一次修改，版本冲突提示应显著减少。
