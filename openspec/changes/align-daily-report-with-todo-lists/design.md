# Design

## Context

见 proposal.md。今日列表使用独立 day_instance_date 实例树，报告旧逻辑使用稳定来源事项树；因此不能仅放宽旧执行筛选。进行中列表只取未完成且无实例日期的来源事项。

## Goals / Non-Goals

**Goals:** 本地与云端按今日实例身份选取并渲染日报；保留既有命令和数据表，刷新日报关联范围。

**Non-Goals:** 不修改待办交互、不部署线上 SQL、不自动重写历史报告、不改周月报合集语义。

## Decisions

1. 以今日成员及上下文实例树作为日报输入，不用来源标题替换实例内容。本地复用今日列表幂等准备机制；云端与现有今日列表一样读取已存在实例，保持 PostgREST 查询只读。若已有实例则保留其独立编辑，不在预览中保存报告。
2. 日报关联使用实例 ID，允许保存及校验当前主体和日期的实例；来源记录工时仅在存在对应成员时补充，避免实例和来源重复计入。周月报保留稳定身份聚合。
3. 明日计划只检查来源 status=open，不检查次日轮次或规则；两个区块独立。
4. 重新生成日报重新计算成员并替换 report_tasks，其他报告保留原有关联范围。手工范围调整不改变日报按列表生成的事实；界面需说明日报来源。
5. Supabase 使用新增日期迁移覆盖相关函数并纳入 schema；使用隔离数据库测试，不操作真实账户。

## Risks / Trade-offs

- [旧测试按执行记录断言] → 更新冲突断言，并补齐未执行、独立实例、移出今日、重复计划和重新生成回归。
- [预览准备实例属于幂等业务写入] → 与今日列表一致，仅准备缺失实例，不落报告，不覆盖已编辑实例。
- [历史日期进行中列表没有快照] → 明日计划反映生成时进行中来源事项，保存后保持原 Markdown，主动重新生成才刷新。

## Migration Plan

新增可重复部署 SQL，不修改业务表。先运行本地和隔离 PostgreSQL 回归，再由用户部署增量 SQL；回滚恢复旧函数，已保存报告不受影响。

部署文件：`supabase/20261103_timegenie_daily_report_todo_lists.sql`。该迁移保留今日独立实例的来源校验规则，替换报告函数并通知 PostgREST 刷新；已接入 `supabase/schema.sql`，本次未部署到真实 Supabase。旧日报需主动重新生成才更新正文和关联范围。
