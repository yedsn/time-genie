# Design

## Context

事项同时存在于本地 SQLite 与 Supabase，`tasks` 行通过直接云存储、增量变更、工作空间快照和备份恢复流转。后端 `TaskDto` 及多个创建、更新、复制、今日实例查询负责形成前端 `TaskRecord`，前端再映射为共享 `Task` 类型并在待办编辑器、今日列表、执行弹框和完成历史中展示。

当前排序由 `sort_order`、父子范围和手动拖拽共同决定；优先级不得进入排序表达式或拖拽计算。当前全局主题已提供红、橙、蓝及中性色变量，可以在不同主题下复用，而无需引入新的视觉依赖。参见 `proposal.md` 和 `specs/task-priority-indicators/spec.md`。

## Goals / Non-Goals

**Goals:**

- 让优先级成为事项行上的受约束、版本化、可同步字段。
- 保证所有创建和衍生路径产生确定的默认值或继承值。
- 在主要事项界面复用同一份优先级标签、颜色和可访问语义。
- 使数据库升级、云端部署、备份恢复和旧客户端回滚保持可控。

**Non-Goals:**

- 不按优先级自动排序，也不修改现有 `sort_order` 语义。
- 不增加优先级筛选、批量设置、智能推荐或截止日期联动。
- 不让父子事项或来源事项与今日实例持续联动优先级。
- 不把优先级写入历史报告快照或用它改变报告生成顺序。

## Decisions

### 1. 在事项行上保存受约束的字符串枚举

本地与云端 `tasks` 表增加非空 `priority` 字段，允许值为 `urgent`、`high`、`normal`、`low`，默认 `normal`。本地新增下一号迁移，Supabase 同时更新 `schema.sql` 并增加可重复执行的部署补丁；两端都使用约束阻止非法值。

字符串值便于快照、JSON、SQL 调试和向后兼容，也与现有 `status`、`source_type` 等字段风格一致。备选方案是整数等级，但它降低数据可读性，并容易把数值大小误用成排序依据，因此不采用。

### 2. 将优先级并入现有事项版本边界

`TaskDto`、前端 `TaskRecord`/`Task`、创建请求和更新请求增加优先级。更新继续要求 `expected_version`，成功时与其他事项字段一样递增版本并返回权威事项；不增加独立优先级表或单独版本号。

这样可以直接复用现有冲突处理、直接云写入和界面状态替换逻辑。独立表能够减少事项行更新，但会引入额外同步实体、快照顺序和冲突边界，对单字段没有收益。

### 3. 所有创建路径显式决定默认值或继承值

- 普通手动创建、快速创建和批量文本新增：未指定时写入 `normal`。
- 复制事项树：逐节点复制来源节点的 `priority`。
- 今日实例及其必要上下文节点：创建时复制对应来源事项的 `priority`。
- 其他导入路径：有合法来源优先级时保留，否则使用 `normal`。

实例生成后只是普通的独立事项行，不建立动态回退到来源优先级的读取逻辑。动态回退会让历史今日计划随来源修改而变化，也会使离线和同步结果更难判断，因此不采用。

### 4. 排序查询和拖拽协议完全忽略优先级

现有查询继续按主体、父级范围、`sort_order`、创建时间等规则排列；优先级字段只加入选取和映射，不加入任何 `ORDER BY`、重新编号或树构建比较器。更新优先级的 SQL 只更新 `priority`、更新时间和版本。

这条边界应由后端测试验证：在记录修改前后比较 `sort_order`、`parent_id` 以及返回列表 ID 顺序。只在前端保持数组位置不够可靠，因为重新加载或另一设备同步后仍可能暴露后端误排序。

### 5. 集中定义展示元数据，界面使用紧凑标识

前端建立共享的优先级元数据映射，集中提供中文标签、CSS 类和可访问名称。界面使用小圆点或紧凑标签，不使用整行背景：

- `urgent`：红色；
- `high`：橙色；
- `normal`：蓝色；
- `low`：灰色。

完整待办编辑器和执行弹框的“更多/设置”区域提供选择控件；待办、今日计划、执行弹框和完成历史的标题附近显示标识。控件和只读标识提供文字、`title` 或 `aria-label`，确保颜色不是唯一信息来源。

备选方案是在每行铺设不同底色，但它会与选中、逾期、完成和活动计时状态争夺同一视觉通道，也会显著增加列表噪声，因此不采用。

### 6. 复用现有任务行同步与快照机制

优先级随完整 `tasks` 行进入直接云写入、增量读取、云快照、本地备份和恢复。需要检查所有显式任务列清单、JSON 构造和行转换，避免某一条旧路径遗漏字段；通用 `select *`/整行 JSON 路径在表结构升级后自然携带该字段。

不创建单独同步事件类型。这样优先级与事项版本原子更新，跨设备冲突也不会出现“标题是新版但优先级是旧版”的拆分状态。

## Risks / Trade-offs

- [显式 SQL 列清单遗漏 `priority`] → 枚举所有事项读取、创建、复制、今日实例、云映射和测试夹具，增加往返测试覆盖主要路径。
- [颜色在不同主题下对比度不足] → 基于现有主题变量生成颜色，并在浅色、深色及柔和主题中检查；始终提供文字或可访问名称。
- [新云列尚未部署时客户端写入失败] → 先部署兼容的 Supabase 补丁，再发布依赖该列的客户端；补丁使用默认值回填旧数据。
- [旧客户端忽略新字段] → 云端默认值和行级版本仍保证数据合法；旧客户端更新事项时必须确认现有通用补丁逻辑不会用缺失字段覆盖 `priority`。
- [实例继承语义被误解为持续联动] → 界面只描述当前事项优先级，测试明确实例创建后与来源独立。

## Migration Plan

1. 在测试 Supabase 环境执行新增列、默认值和约束补丁，验证旧任务均为 `normal`，现有 RPC、快照和恢复函数可处理扩展后的行类型。
2. 发布包含本地 SQLite 迁移和新字段兼容读取的客户端；本地迁移将已有事项回填为 `normal`。
3. 启用优先级编辑与各入口标识，执行本地、云端双设备、备份恢复和主题视觉验证。
4. 若需要回滚客户端，可保留本地及云端 `priority` 列；旧版本会忽略额外字段，避免破坏数据。待所有客户端稳定后再决定是否清理无用补丁函数，回滚期间不删除列。
