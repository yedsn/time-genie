# Design

## Context

见 `proposal.md` 的问题说明和 `specs/cloud-task-planning-parity/spec.md` 的行为要求。当前本地实现已经完整支持 `task_daily_estimates`、`task_recurrence_rules` 与 `task_occurrences`，Supabase schema、迁移导入和全量快照也已包含三张表。缺口集中在日常写入链路：按日预估和重复规则命令在云端模式主动拒绝执行，`cloud_apply_patch` 与客户端 outbox 只支持 `task_occurrence`，前端还会禁用重复入口。

当前同步系统以本地 SQLite 为云端模式的离线缓存和 outbox 来源。`reduce-timer-sync-conflicts` 正在补充同实体顺序、依赖、重试和快照覆盖保护，本变更必须复用这些通用机制，不能另建直接从 Vue 写 Supabase 的旁路。

按日预估以 `(task_id, work_date)` 为业务身份，可设置也可删除；重复规则使用有效区间，修改一次规则可能关闭旧区间、创建新区间并递增事项版本。因此两者不能完全照搬只有单行 upsert 的普通实体模型。

## Goals / Non-Goals

**Goals:**

- 让现有按日预估和重复设置命令在云端模式保持本地优先、离线可写。
- 为按日预估提供按复合键寻址的 upsert/delete、幂等和版本冲突语义。
- 为重复规则提供以“事项的一次规则变更”为边界的原子云端操作，保留规则历史且避免重叠活动区间。
- 让三类规划数据共同参与增量拉取、快照保护、冲突展示和迁移验证。
- 复用现有 outbox 顺序与依赖模型，并保持旧客户端可升级。

**Non-Goals:**

- 不改变重复事项现有的频率、叶子事项限制、虚拟轮次、历史跳过、完成、计时和报告语义。
- 不增加月度、年度、节假日或复杂 RRULE。
- 不把设备级设置、凭据或本机文件路径改成工作空间同步数据。
- 不采用最后写入胜出，也不增加多人共享工作空间能力。
- 不重做通用同步界面；只补充新实体需要的标签、内容对比和错误信息。

## Decisions

### 1. 云端命令继续执行本地事务，再由 outbox 上传

移除 `ensure_daily_estimates_supported_in_storage_mode` 和 `ensure_recurring_supported_in_storage_mode` 的云端拒绝逻辑，但保留统一的 Repository 写入守卫。命令根据当前模式决定是否在同一本地事务中追加 outbox：

- 本地模式只提交 SQLite 事务。
- 云端模式提交 SQLite 业务数据与 outbox 后立即返回，再调用现有在线 flush。
- 离线、暂时性网络错误和认证刷新不回滚已提交的本地规划结果。

备选方案是云端模式直接调用 Supabase RPC，成功后再刷新缓存。该方案会失去离线写入并形成与其他业务不同的双路径，因此不采用。

### 2. 按日预估作为复合键版本实体同步

新增云端实体类型 `task_daily_estimate`，实体 ID 使用稳定字符串 `task_id|work_date`，payload 包含完整行和显式动作语义。

- 设置或修改：本地 upsert 后入队，`base_version` 为修改前版本；首次创建为 `NULL`。
- 清空：本地删除前读取旧版本，outbox 保存 tombstone payload `{ task_id, work_date, deleted: true }` 与旧版本。
- 云端应用时校验工作空间、事项存在性、复合 ID 与 payload 一致性，再执行 upsert 或 delete。
- 删除成功也写入 `workspace_changes`，使其他设备能够观察清空事件；结果返回删除后的实体版本标记或明确 tombstone 结果。

单纯依赖完整快照无法可靠表示删除，因为接收端看不到“这一行曾经存在但已清空”，因此必须把删除作为增量操作。

### 3. 重复规则以事项级复合操作同步

新增云端实体类型 `task_recurrence_rule`，但同步边界不是任意单行写入，而是“一次事项规则变更”。实体 ID 使用 `task_id`，payload 包含：

- 动作：`save` 或 `close`；
- 事项 ID、事项基线版本和规则基线版本；
- 目标频率、星期位图、生效日期，或关闭日期；
- 本地事务完成后该事项全部相关规则区间的规范化快照；
- 操作完成后的事项与活动规则版本。

Supabase 在单个事务函数中重新执行与本地一致的资格、版本和日期约束，然后原子地关闭旧区间、创建或更新新区间，并触碰事项版本。RPC 不直接盲目覆盖客户端传来的全部规则历史；规范化快照用于结果核验、冲突展示和幂等返回。

备选方案是把旧规则更新、新规则创建和事项更新拆成三个 outbox 实体。任何一步失败都会暴露半完成规则，依赖恢复和冲突处理也更复杂，因此不采用。

### 4. 规则操作使用服务端生成或验证规则标识

本地首次创建规则时已经生成 UUID。云端 RPC 接受该 ID，并在相同 operation ID 重试时返回首次结果；若 ID 已被其他工作空间或不相容规则占用则拒绝。修改产生新区间时同样传递本地新规则 ID，以保证本地与云端快照可对齐。

服务端仍以事项当前活动规则和版本作为并发保护，不能仅因规则 ID 未出现就接受写入。这样可以同时保证幂等创建和多设备冲突检测。

### 5. 按日预估与轮次在同一本地事务中分别入队

为重复事项设置按日预估时，现有逻辑可能先物化 `task_occurrence`。云端模式在同一本地事务中：

1. 创建或读取轮次；
2. 保存或清空按日预估；
3. 仅在轮次确实新建或发生变化时入队 `task_occurrence`；
4. 入队 `task_daily_estimate`。

若按日预估依赖新建轮次存在，则估算操作通过 outbox 的 `depends_on_operation_id` 指向轮次操作；若轮次已存在，两者可独立同步。服务端设置预估时仍允许轮次已由其他设备提前创建，依赖用于顺序而不是重复创建保护。

清空按日预估不删除轮次，因为轮次可能还承载完成状态、工时或手工执行历史。

### 6. 增量拉取按表名更新缓存并保护本机脏实体

`workspace_changes` 已能记录三张表，但客户端需要把复合表名映射到可比较的同步实体键：

- `task_daily_estimates` -> `task_daily_estimate` / `task_id|work_date`；
- `task_recurrence_rules` -> `task_recurrence_rule` / `task_id`，同一事项任一规则行变化都刷新该事项的规则集合；
- `task_occurrences` -> 现有 `task_occurrence` / `task_id|occurrence_date`。

若对应键存在 pending、sending、failed 或 conflict outbox，快照导入跳过该本机实体或整组规则，避免覆盖本地修改。队列清空后再拉取权威快照完成确认。

对规则采用事项级保护，而不是只保护单个规则 ID，因为一次修改会同时改变多个区间。

### 7. 冲突处理复用现有“使用云端 / 保留本地”流程

按日预估冲突展示事项、日期、本机值和云端值；清空操作显示本机目标为“未设置”。重复规则冲突展示规则摘要、有效区间和相关事项版本。

- 使用云端：删除该实体或事项规则组的本地冲突及后续依赖操作，拉取云端权威数据。
- 保留本地：以最新云端版本作为新基线，生成新的 operation ID 并重新提交当前本机规范化结果。
- 同一实体较早冲突未解决时，后续操作不得越过它发送。

这与现有同步协调规则一致，避免为规划数据增加新的冲突交互。

### 8. Supabase schema 先兼容部署，再开放客户端入口

更新 `schema.sql` 并提供可重复执行的增量补丁，为 `cloud_apply_patch` 增加两个实体类型、复合键版本检查、删除语义和对应权限。客户端只有在 schema 能力检查确认支持这些实体后才开放云端写入；旧 schema 返回明确升级提示，不把缺少 RPC 分支误判为登录失效。

前端不做额外模式开关。能力可用后，重复设置和今日预估入口在两种模式一致；同步问题使用现有全局状态和错误反馈呈现。

### 9. 设备级设置明确排除在对齐范围外

功能对齐判断以业务数据所有权为准，而不是“本地数据库里存在就必须上传”。`device_settings`、凭据库、`local_report_outputs` 等仍保持本机边界；本变更只扩展已经属于工作空间模型的三张事项规划表。

## Risks / Trade-offs

- [规则修改同时影响多行和事项版本，客户端与服务端算法可能漂移] -> 抽取可对照的规则转换测试，Supabase 集成测试覆盖创建、同日修改、跨日修改、关闭和版本冲突。
- [按日预估删除后旧设备通过快照恢复旧值] -> 使用显式删除操作和 `workspace_changes`，并验证删除后的增量拉取与全量快照都保持无记录。
- [规则表的变更日志以行 ID 表示，客户端需要事项级合并] -> 拉取变更后读取行的 `task_id`，统一映射到事项级同步键；删除时在变更日志中保留可解析的事项身份。
- [离线设置预估同时新建轮次，发送顺序错误] -> 在单个本地事务中创建两个 outbox 操作并建立依赖；服务端保持幂等 upsert。
- [与正在进行的 outbox 协调改造冲突] -> 先完成或基于 `reduce-timer-sync-conflicts` 的最终字段与领取规则开发，规划实体只接入通用接口，不复制队列实现。
- [云端 schema 未升级就发布客户端] -> 增加 schema 能力检查和可识别错误；发布顺序固定为先 SQL、后客户端。
- [旧 OpenSpec 仍写着云端不支持重复事项] -> 本变更作为后续能力明确覆盖该限制，实施完成后归档形成新的主规格。

## Migration Plan

1. 等待或合并 `reduce-timer-sync-conflicts` 的 outbox 顺序、依赖和快照保护基础，确认规划实体可复用其公共入口。
2. 更新 `supabase/schema.sql`、schema 验证脚本和集成测试，并生成可重复执行的规划功能补丁 SQL；先部署到 Supabase。
3. 扩展 Rust 云端实体映射、复合 payload、删除语义、冲突读取和快照保护，但暂时保留前端云端限制。
4. 改造按日预估与重复规则本地事务，使云端模式原子写入业务数据和 outbox；通过 Rust 测试后移除后端拒绝守卫。
5. 移除前端禁用和提示，执行本地/云端、在线/离线、双设备、迁移与报告回归验证。
6. 回滚客户端时保留 Supabase 新函数和表能力，旧客户端忽略新增分支；不得删除未同步的本地 outbox。若必须暂时关闭入口，只隐藏新写入，不删除已同步的规划数据。
