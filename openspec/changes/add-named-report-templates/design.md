# Design

## Context

见 `proposal.md` 和 `specs/report-template-library/spec.md`。现有 SQLite 与 Supabase `report_templates` 以 `(workspace_id, report_type, subject_id)` 保证每个范围只有一份模板，前端只能从已选报告打开模板设置。报告表已经保存 `template_id`，但创建和重新生成接口由后端按主体自动查找有效模板，调用方不能显式选择。

模板与报告均已进入本地优先 outbox、Supabase 快照和 Realtime 增量同步，因此结构变更必须同时覆盖 SQLite、Supabase、聚合 payload、增量适配器和兼容部署 SQL。

## Goals / Non-Goals

**Goals:**

- 把模板从“类型加主体的单例配置”升级为“按类型分类的全局命名资源”。
- 保证每种报告类型始终存在唯一有效默认模板，并在离线、多设备和乱序消息下收敛。
- 让报告创建、范围调整和重新生成显式使用并持久化模板 ID。
- 无损迁移现有内置模板、主体专属模板、历史报告引用和手工编辑内容。
- 沿用现有本地优先后台同步，不新增同步通道或前台阻塞请求。

**Non-Goals:**

- 不支持跨工作空间共享、在线模板市场、导入导出模板包或多人实时共同编辑模板正文。
- 不允许日报使用周报模板等跨类型绑定。
- 不在模板修改时自动重写任何已有报告。
- 不新增任意表达式、条件语句或用户自定义占位符执行引擎。

## Decisions

### 1. 在现有 `report_templates` 上增加命名资源字段

新增 `name TEXT NOT NULL`、`description TEXT`、`is_default INTEGER/BOOLEAN NOT NULL DEFAULT 0` 和 `sort_order INTEGER NOT NULL DEFAULT 0`。保留 `is_builtin`、版本、软删除和时间字段。`subject_id` 在兼容期保留但迁移后全部置空，新写入必须为 NULL，后续代码不得按主体查询模板。

移除现有“每类型一个全局模板”和“每类型每主体一个模板”的唯一索引，改为：

- 有效模板名称在 `(workspace_id, report_type, normalized_name)` 内唯一；名称写入前去除首尾空白并以应用统一大小写规则检查重复。
- 每种类型通过部分唯一索引保证 `(workspace_id, report_type)` 仅一条 `is_default = true AND deleted_at IS NULL`。
- 业务事务额外保证每种类型至少一条有效模板以及恰好一个默认模板。

选择扩展现有表而非新建版本表，可保留已有 UUID 和 `reports.template_id`，减少历史引用迁移风险。

### 2. 模板接口改为资源式 CRUD 和原子默认切换

后端提供模板列表、按 ID 读取、新建、更新、复制、删除和设置默认操作。写操作携带 expected version；默认切换在单个事务中先锁定或验证目标模板，再取消同类型旧默认并设置目标默认。删除默认模板必须在同一请求中提供替代模板 ID，避免暴露无默认中间状态。

模板删除继续使用软删除。已被报告引用的软删除模板可按 ID 读取并用于该报告重新生成，但不会出现在模板库有效列表或新建报告选择器中。这样同时满足历史可重现与用户删除后不再复用。

备选方案是禁止删除被引用模板；这会让模板库长期无法整理，因此不采用。另一备选方案是删除后让历史报告切换默认模板，会破坏报告的明确绑定，也不采用。

### 3. 报告创建与范围更新显式携带 `template_id`

`ReportCreateRequest` 和 `ReportScopeUpdateRequest` 增加 `template_id`。后端验证模板属于当前工作空间、未删除且类型与报告类型一致。为兼容升级期间的旧客户端，请求未携带模板 ID 时回退到同类型默认模板；新前端始终显式提交。

`ReportDto` 增加 `template_id` 和可展示的 `template_name`。报告创建保存模板 ID；范围更新只有在用户明确选择时才更换。报告类型改变时必须选择新类型模板。

重新生成不再调用“按主体查有效模板”，而是按报告已保存的模板 ID读取，包括软删除模板。若历史异常数据缺少模板 ID，则只在该兼容场景回退到当前同类型默认模板并补写绑定。

### 4. 默认模板只影响新建时的初始选择

默认模板不是动态继承关系。创建界面切换报告类型时加载该类型有效模板并选中默认项；用户临时改选不会改变默认。已有报告不会因默认变化而更新绑定。

这比“报告始终跟随当前默认模板”更可预测，也能让重新生成保持格式连续性。

### 5. 模板管理成为报告页独立区域

报告页增加固定“模板管理”入口，不依赖是否已有报告。模板管理界面按日报、周报、月报筛选，左侧展示模板列表和默认/内置标记，右侧编辑名称、说明和 Markdown，提供复制、删除、排序、设置默认及实时预览。

创建报告对话框在范围区和事项区之间增加模板选择区，展示模板名称、说明、默认标记和预览。调整报告范围同样显示模板选择；若只调整事项或日期则保留原模板。

占位符定义集中在一个前后端一致的清单中，每个占位符声明适用报告类型、说明和示例。前端按类型过滤并在 textarea 光标处插入，后端仍以允许列表作为最终校验。

### 6. 迁移保留 ID，并将主体模板展开为全局命名模板

SQLite 与 Supabase 使用同一确定性规则：

1. 为三份内置全局模板补名称“标准日报”“标准周报”“标准月报”、默认状态和排序，保留原 ID。
2. 对每种类型若内置全局模板缺失，选择最早有效模板作为默认；若完全没有模板则补建标准内置模板。
3. 将主体专属模板名称生成为“<原主体名称> - <日报/周报/月报>”；发生重名时按模板 ID 稳定排序并追加“(2)”“(3)”等序号。
4. 把所有迁移模板的 `subject_id` 置空，建立新索引。
5. 不修改 `reports.template_id`、Markdown、内容来源、生成次数和版本。
6. 清理同类型多默认状态并保证最终唯一默认。

迁移必须可重复执行；部署 SQL 在约束创建前检查和修复已有数据。

### 7. 云端同步把默认切换视为一个业务操作

模板实体 payload 增加名称、说明、默认状态和排序。普通模板增删改沿用 `report_template` 聚合实体；“设置默认”使用单一 operation ID 和服务端事务 RPC，同时更新目标与原默认模板并返回权威版本。客户端应用增量时先按版本 upsert，再执行工作空间加类型的默认归一化，防止乱序消息短暂留下两个默认。

报告 payload 已包含 `template_id`，需要在本地/云端序列化、增量 upsert 和 DTO 中完整保留，并验证模板类型引用。同步在既有后台协调器中执行，不新增前台等待。

### 8. 内置模板可编辑，但最后模板和默认约束不可破坏

内置标记用于识别迁移来源和界面提示，不把模板正文设为只读。用户可直接编辑，也可复制后编辑。系统不提供“物理删除内置模板”的特殊路径；所有删除都是软删除且受每类型至少一份、唯一默认规则约束。

## Risks / Trade-offs

- [并发默认切换可能产生多个默认] → 使用数据库部分唯一索引、服务端事务 RPC、版本检查和增量归一化四层保护。
- [软删除模板仍被历史报告使用，用户可能误以为已彻底删除] → 删除确认中说明历史报告仍可重现，界面将其标记为“已归档模板”。
- [旧客户端仍按主体保存模板] → 云端应用旧 payload 时忽略主体作用域并把写入归一为全局命名模板；名称冲突返回可重试冲突，防止覆盖。
- [迁移主体模板产生难读名称] → 使用主体名称生成初始名称并稳定追加序号，迁移后用户可自由重命名。
- [模板更新后重新生成结果变化] → 报告绑定模板 ID但不冻结模板版本；界面重新生成前明确提示将使用模板最新内容。若未来需要严格审计，可另行增加模板版本快照。
- [占位符前后端清单漂移] → 后端保持权威校验，前端以共享常量或测试夹具验证所有展示 token 均可被后端接受。

## Migration Plan

1. 新增 SQLite 迁移，补字段、迁移名称与默认状态、归一主体模板、替换索引并验证报告引用。
2. 更新 `supabase/schema.sql` 和可重复部署补丁，在事务中迁移远端数据并创建新约束/RPC；部署前备份数据库并刷新 PostgREST schema。
3. 发布兼容后端：支持新模板 CRUD 和显式模板 ID，同时接受旧创建报告请求并回退默认模板。
4. 更新云端快照、outbox、Realtime 增量与双设备测试，确认默认模板和报告绑定收敛。
5. 发布新前端模板管理与报告创建选择器，移除旧的“当前主体模板”文案和入口行为。
6. 运行本地升级、旧客户端兼容、双设备并发与回滚演练。

回滚时保留新增字段和迁移后的全局模板。旧代码依赖旧唯一约束且无法安全表示多模板，因此数据库结构不回退到旧约束；应用回滚版本只能读取每类型默认模板，并不得删除其他模板或改写历史报告。
