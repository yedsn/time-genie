# Design

## Context

参见 `proposal.md` 的动机。本项目已经具备两套可复用基础：云端操作记录使用 `(occurred_at, id)` 游标倒序查询并保存脱敏字段差异；云端快照使用完整实体目录、JSONB 分块、SHA-256 校验、保护/过期策略和工作空间世代完成全量恢复。

目前操作记录前端以筛选器和“加载更多”追加列表为主；后端列表 RPC 虽支持游标和筛选，但没有面向页码的回退状态。快照 SQL 已识别 `automatic` 类型，并能限制同一天一份，但没有工作空间级调度设置，也没有服务端定时入口。部署实例已通过 `shared_preload_libraries` 预加载 `pg_cron`，但尚未启用扩展，也没有任何定时任务。

## Goals / Non-Goals

**Goals:**

- 用稳定、可回退的游标分页呈现全部操作记录，每页固定 50 条。
- 让云端在每天固定时刻（按工作区时区）自动形成一个完整恢复点，不需要客户端参与，也不占用同步路径。
- 以“工作空间 + 工作区本地日”原子判重，避免同一日期创建重复自动快照。
- 保持快照全量、一致、可校验、可完整恢复，并沿用现有大小及保留信息。

**Non-Goals:**

- 不提供操作记录搜索、筛选、单条撤销或单实体恢复。
- 不提供部分内容快照、差分快照、增量链或局部恢复。
- 不在客户端关闭时补建历史日期快照，也不引入新的常驻服务或后台进程；调度复用数据库自带的 `pg_cron`。
- 不让快照创建参与、阻塞或影响客户端同步。
- 不改变手动快照、恢复前安全快照、工作空间世代和恢复锁的核心协议。

## Decisions

### 1. 操作记录使用游标栈实现页码体验

保留后端 `(occurred_at desc, id desc)` 的 keyset pagination，不改成 `OFFSET`。前端维护“每一页起始游标”的栈：第一页没有游标；进入下一页时保存当前请求游标和响应的 `nextCursor`；返回上一页时重新使用栈中的前一游标请求。页面展示 `第 N 页`，而不是声称未知总页数。

每次请求 51 条，响应只返回前 50 条，并用额外一条判断是否存在下一页；也可沿用当前 `limit + 1` 的 SQL 实现，只需把默认值调整为 50。进入页面和手动刷新将清空游标栈并回到第一页，避免新写入导致跨页边界混乱。

选择 keyset 而非 `OFFSET` 的原因是记录表持续增长，时间索引可保持稳定性能，而且新记录插入不会使当前向后浏览出现重复行。代价是无法直接跳转到任意页或可靠计算总页数，本次需求只需要上一页/下一页。

### 2. 保持记录数据模型，移除前端筛选入口而非删除兼容参数

前端不再提交搜索、来源、设备和业务类型参数。Rust 请求模型与 SQL RPC 可先保留这些可选参数以兼容旧客户端，但新的页面只使用工作空间、页大小和游标。文档和测试按“无筛选直接看全部”作为正式行为。

保留现有日志表和详情表，不把每个字段拆成顶层记录。列表仍是一条成功业务对象写入，详情是该对象的安全字段差异。这避免数据量和保留成本显著膨胀，也不改变已记录历史。

### 3. 每日固定时间存入工作空间历史设置

在 `workspace_history_settings` 增加：

- `automatic_snapshot_enabled`（默认 `true`）
- `automatic_snapshot_time`（`time`，默认 `03:00`）

时区直接复用 `workspaces.timezone`（默认 `Asia/Shanghai`）。工作区日期边界、计时和统计已经使用同一字段，因此不再引入第二个时区来源。

由 Supabase 提供读取和更新设置的 RPC，并继续以工作空间所有者和已注册设备做授权。Rust 暴露类型安全的读取/保存命令；快照页面加载时读取，保存后覆盖后续调度。设置读取同时返回下次执行时间、最近一次自动快照时间和调度器是否可用。

选择“每天一个固定时刻”而不是“每 6 小时/每 3 天”这类频率，是因为用户关心的是“每天在不工作的时候自动留一个恢复点”：固定时刻可预期、每天上限一份、存储成本稳定。旧的 `automatic_snapshot_frequency` 字段在迁移时转换为启用状态后删除，避免两套调度语义并存。

### 4. 按工作区本地日原子判重

`workspace_snapshots.schedule_slot_key` 继续使用部分唯一索引判重（`workspace_id + snapshot_type=automatic + schedule_slot_key`），但键值改为工作区本地日，例如 `daily:2026-10-18`，由 `workspaces.timezone` 计算。手动和恢复前安全快照不使用此键。

判重检查覆盖该键的任意状态记录（`creating`/`ready`/`failed`/`corrupt`），因此同一本地日最多尝试一次；失败不会在后续每分钟被反复重试，只能等下一个本地日。只有 `ready` 状态算作可用恢复点。

本地日键能正确处理“凌晨 03:00 仍属于前一个 UTC 日期”的情况，也避免切换每天执行时刻后同一天生成第二份快照。

### 5. 数据库定时任务驱动，不再挂在同步路径

新增 `timegenie.workspace_snapshot_run_scheduled(p_at)`，由 `pg_cron` 每分钟调用一次。它只做轻量判断：工作区是否启用、工作区本地时间是否已过设定时刻、当天是否已有槽记录；满足条件时才复用现有完整快照创建、校验和清理流程。执行期间使用事务级 advisory lock 防止重叠运行。

### 6. 快照详情只读取创建时摘要

快照创建完成时已经保存 `entity_counts`、`group_hashes`、`content_hash`、实际大小、分块数、基准变更序号和工作空间世代。详情 RPC 只读取这些不可变元数据并计算简单的分组数量，不再重新组合整份快照，也不再读取当前工作空间做逐条新增、修改、删除比较。

恢复准备与查看详情分离：用户明确点击恢复后，服务端校验每个分块的哈希、行数、总大小和实体总数；恢复提交时仍重新组合目标快照并核对整体哈希。这样避免详情查询超时，同时保持恢复前后的双重完整性保障。

调度任务在数据库内运行，必须临时假定工作空间所有者身份（`request.jwt.claim.sub`），因为所有云端 RPC 都通过 `auth.uid()` 校验归属；函数结束时还原原值。快照记录为工作空间最近活跃的已注册设备创建；没有活跃设备时跳过该工作空间并返回原因。

客户端不再调用任何自动快照 RPC，同步轮次不会请求快照相关接口。`workspace_snapshot_ensure_automatic` 和 UTC 频次时间槽函数在补丁中删除，避免两套调度并存。

应用未运行的时段同样按点创建：定时任务与客户端无关，这正是把快照移出同步路径的原因——完整快照创建耗时数十秒，放在同步路径上会拖慢用户感知的同步速度。

`pg_cron` 不可用时补丁不会失败：扩展安装和任务注册被包裹在异常处理中；`workspace_snapshot_settings_get` 返回 `schedulerActive`，页面据此提示自动快照不会执行。

### 6. 全量快照和大小口径保持不变

快照实体目录继续包含计划、时间记录、报告和共享设置的全部受保护实体，继续按实体分块并保存 `size_bytes`、`chunk_count` 和 `entity_counts`。界面展示服务端返回的实际大小与所有快照的总和；不增加内容勾选和局部恢复分支。

现有数据实测完整业务 JSON 约 643 KB、压缩等效约 94 KB，因此默认每日、保留 30 天的量级约为数 MB。实现仍保留单份 100 MiB 上限和现有自动清理策略，避免异常工作空间无限增长。

### 7. 术语统一为快照和恢复时点

前端标题由“云端历史镜像”调整为“云端快照”，类型仍显示手动、自动、恢复前安全；主动作由“回滚到此镜像”调整为“恢复到此时点”。底层 API 和数据库对象可继续使用 `snapshot` 命名，不做无收益的重命名迁移。

## Risks / Trade-offs

- [新记录插入后返回第一页可能与先前第一页内容不同] → 翻页期间依赖游标栈保持稳定；刷新明确重置到最新第一页。
- [无法显示准确总页数或跳到任意页] → 页面只显示当前页，符合上一页/下一页需求；避免昂贵总数查询和不稳定 OFFSET。
- [定时任务与客户端同步同时运行] → 调度在数据库内独立执行，同步只承担正常数据库负载；事务级 advisory lock 避免调度重叠。
- [定时快照创建失败] → 保留当天失败记录供诊断，不阻塞同步，下一个本地日重新尝试；页面显示最近一次自动快照时间。
- [每天一份会增加存储] → 沿用 30 天保留、每天一份、单份 100 MiB 上限和手动快照数量上限，设置页展示总占用。
- [工作区时区变更可能与本地日判断冲突] → 槽键按工作区时区计算；同一天切换时区最多再创建一份，不回补历史日期。
- [旧客户端仍调用已删除的自动确保 RPC] → 部署顺序为先 SQL 后客户端；旧客户端只会记录一次可忽略的错误日志，不影响同步。

## Migration Plan

1. 先备份数据库结构，再部署幂等补丁：启用 `pg_cron`、注册每分钟调度任务、新增 `automatic_snapshot_enabled`/`automatic_snapshot_time`、删除 `automatic_snapshot_frequency` 和客户端自动确保 RPC；已有快照和业务数据不变。
2. 同步更新 `supabase/schema.sql` 和集成测试（重复加载补丁两次证明幂等），运行结构校验和定时器时间模拟测试。
3. 发布客户端：设置改为“启用 + 每天时间”，同步路径移除自动快照调用；旧客户端仍可使用手动快照和列表 RPC。
4. 更新文档与页面文案后运行类型检查、构建和后端测试。
5. 回滚时先停用调度任务（`cron.unschedule`）或把 `automatic_snapshot_enabled` 置为 `false`；数据库新增字段可安全保留，已生成快照不删除。
