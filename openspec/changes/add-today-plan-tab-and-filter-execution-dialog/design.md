# Design

## Context

见 proposal.md 与 specs/today-task-planning/spec.md。当前今日计划使用“同一个事项 ID + task_day_plans 成员关系”表达：

```text
长期事项 A (task_id = T)
    |
    +-- task_day_plans: T + work_date
            |
            +-- 今日页和执行弹框继续引用 T

结果：今日页与进行中页共享标题、备注、预计、完成状态、实际用时和层级。
```

本变更需要把第二层改成一份拥有独立 task_id 的实例：

```text
长期事项 A (task_id = T)
    |
    +-- 来源日期映射: T + work_date --> I
            |
            +-- 今日实例 I（独立标题、备注、预计、层级、完成、实际、删除状态）
```

现有时间记录、时间分配、实际调整和报告都通过事项 ID 关联。继续把独立实例保存在同一个 tasks 域中，可以复用这些外键和报告口径，不必再造一套平行的今日事项表。

## Goals / Non-Goals

**Goals:**

- 让加入今日后的每一步用户可见修改都只落在今日实例上。
- 保留来源事项到今日实例的单向追溯和当天防重复创建能力。
- 让今日页、进行中页、执行弹框、未归属时间和报告各自使用明确、可测试的事项范围。
- 让重复事项、删除、移出今日和再次加入都有确定且可恢复的数据生命周期。
- 让本地 SQLite、Supabase、增量同步、快照和备份恢复使用同一套实例语义。

**Non-Goals:**

- 不把今日页扩展为任意未来日期的日历计划。
- 不改变计时状态机、唯一活动计时、停止确认、未归属分配或报告的时间计算规则。
- 不为今日实例复制加入之前已经记录在来源事项上的时间。
- 不在本变更中删除 task_occurrences；它继续作为重复规则生成账本，但不再作为今日实例完成状态的权威来源。

## Decisions

### 1. 今日实例继续存放在 tasks 域，并增加实例元数据

tasks 增加以下可空字段：

- day_instance_date：实例所属工作空间自然日；普通长期事项为空。
- day_instance_kind：member 或 context；前者是可规划、可完成的今日事项，后者只为保留父子结构。
- day_instance_source_task_id：来源长期事项 ID，可为空；只用于追溯，不得触发字段回写。

约束与索引：

- day_instance_date、day_instance_kind 同时为空或同时非空。
- day_instance_source_task_id 非空时，day_instance_date 必须非空。
- 普通进行中和已完成查询排除 day_instance_date 非空的事项。
- 按 workspace、subject、day_instance_date、parent_id、sort_order 建立查询索引。
- 对非删除且来源非空的实例建立 (workspace_id, day_instance_source_task_id, day_instance_date) 唯一索引，防止并发重复创建；归档旧实例不占用该唯一位置，因此再次加入可以创建新 ID。
- 今日实例的 parent_id 只能指向同主体、同 day_instance_date 的实例，禁止跨今日实例和长期事项组成父子树。

备选方案是新建独立的 daily_tasks 表。那样时间记录、实际调整、报告、搜索和父子关系都需要双外键或跨表联合，容易产生重复统计；因此选择在同一事项域中显式区分实例。

### 2. task_day_plans 改为“来源事项 + 日期 -> 当前实例”的映射账本

task_day_plans 保留 task_id 和 work_date，表示来源事项和日期；新增 instance_task_id，指向当前实例。state 语义为：

- included：该来源在这个日期已经物化，instance_task_id 指向当前实例。
- excluded：该来源在这个日期已被用户移出或当前实例已删除，不得由重复规则自动重建。

每个来源事项和日期最多一条映射。映射的存在本身就是“这个日期已经处理过”的标记：

- 首次加入或重复规则自动生成时创建实例并写 included。
- 移出或删除时软删除实例，并把映射改为 excluded。旧实例 ID 可保留用于审计，但视图必须以实例未删除且映射为 included 为准。
- 再次加入时沿用同一映射行，state 改回 included，instance_task_id 指向刚创建的新实例。旧实例仍为归档状态，不会恢复旧标题、完成状态或实际时间。
- 直接在今日页新建的事项没有来源映射，只存在自己的实例行。

映射版本和实例事项版本相互独立。修改今日标题、完成或实际时间只增加实例 version，不增加来源事项或映射 version；加入、移出和再次加入增加映射 version。

### 3. 创建实例时复制当时可见内容，之后彻底解耦

创建今日实例时从来源事项复制：

- 标题、备注、项目、方案和整体预计；
- 在来源树中的父子位置和相对顺序；
- 当前日期可用的首次完成状态；
- 如果来源已有该日按日预计，则把该预计结转/迁移到今日实例名下，来源不再保留同一天的有效预计，避免报告重复统计。
- 如果来源是当前日期有效的重复事项、没有单独按日预计且配置了“每次预计”，则以该值创建实例的初始今日预计。该动作只发生在实例首次物化时，之后修改来源每次预计不得回写已有实例。

创建前的实际用时、时间分配和实际调整继续归属于来源事项，不迁移、不复制。创建后的计时、分配和实际调整必须写入今日实例 ID。这样既避免报告重复计数，也符合“加入前的工作属于来源事项，加入后的工作属于今日实例”的边界。

仅加入一个子事项时，为其来源祖先在今日树中创建 context 实例。context 实例保留标题和层级用于识别，但不计入预计/实际合计、不可执行、不可完成，并且不因自身存在而算作今日成员。最后一个子实例被移出后，自动归档已经孤立的 context 实例。

在今日页直接新建事项只创建 member 实例，不创建长期事项。复制事项菜单也只复制今日实例当前行，不复制子树、来源链接、完成状态、重复规则或历史时间。

### 4. 所有今日内容修改都以实例 ID 为写入目标

标题、备注、整体预计、今日预计、父子关系、排序、完成/恢复、实际调整和删除命令都必须接收实例 ID，并在后端验证该 ID 属于目标工作空间、主体和当前工作日的实例域。

- 今日树拖动只更新 day_instance_date 相同的 member/context 实例。
- 今日完成/恢复只更新实例 status 和 completed_at；来源事项保持不变。
- 今日实际调整和计时分配只关联实例 ID；来源事项实际分钟保持不变。
- 删除今日实例不删除来源事项；删除来源事项不删除已经存在的今日实例。
- 编辑来源事项不批量更新已有实例，只在以后创建新实例时使用最新来源内容。

今日页和进行中页的共享组件使用不同的 ID 域。前端不得再通过“同一 task ID 在不同 tab 中附加 todayMember 字段”的方式模拟独立性。

### 5. 移出、删除和再次加入使用明确的归档生命周期

- 移出今日：软删除当前 member 实例，映射改为 excluded；保留时间记录和实际调整，清理孤立 context。
- 删除今日事项：对今日实例执行同样的软删除和映射排除；来源事项保持原状态。删除一级实例时，其今日子实例一并归档，避免悬挂父子关系。
- 再次加入：创建全新实例，不做恢复；新实例复制来源事项的当前内容，实际时间从零开始。
- 删除来源事项：只软删除来源及其长期子树；已有今日实例继续可查看、执行和报告。
- 删除进行中事项时不得连带删除同名今日实例，也不得因来源消失而清理今日实例的来源链接文本之外的用户内容。

软删除是必须的，因为时间分配、实际调整和审计记录都引用事项外键；硬删除会让历史报告失去关联。

### 6. 重复事项按日期生成独立实例，模板与实例单向复制

进入某个工作空间自然日时，系统按有效重复规则为尚未映射的到期来源事项创建当日实例。task_day_plans 的 included/excluded 记录保证同一来源同一天最多生成一次；已 excluded 的来源当天不会被自动重建。

- 今日实例完成只改变实例，不改变重复模板 status，也不改变 task_occurrences 中的模板状态语义。
- 今日实例改名、备注或整体预计默认只影响当天实例；对于来自重复模板的实例，用户可显式选择“修改今后全部”，此时同步更新来源模板，历史实例不回写。层级、排序、完成、今日预计、实际用时或删除始终只影响当天实例。
- 修改重复模板后，未来新实例复制最新模板；当天和过去实例保持原内容。
- 删除今天实例后手动再次加入，创建新实例；旧实例和旧实际时间保持归档。
- task_occurrences 如继续保留，只用于重复规则生成和历史兼容，不得覆盖已有今日实例的标题、层级、完成或实际字段。

### 7. 查询范围和界面职责按实例域拆分

后端提供明确范围：

- 进行中 / 已完成：只返回 day_instance_date 为空的长期事项。
- 今日计划：只返回 day_instance_date 等于当前工作日的事项，包含 member、context 和当天已完成 member。
- 执行模式：只返回今日实例，包含已完成实例及必要 context；当前跨日运行事项只显示在计时状态区。
- 未归属时间、停止确认和历史归属：返回长期事项与今日实例的完整合法集合，保持既有分配范围。
- 报告、今日概览、搜索和备份：包含今日实例及其实际时间，不能因待办标签过滤而丢失。

待办今日标签和执行弹框继续复用进行中列表的视觉与操作：底部“+”新增、行内编辑、子事项、树形拖动、右键行菜单、二级 17px 缩进、常显拖动柄、非叶子父项禁用勾选框、空状态和首次骨架加载。今日完成项保持原顺序并灰显，不额外显示“今日已完成”文字。进行中列表只展示整体预计或重复事项的每次预计，不展示今日预计编辑入口。

“配置今日事项”保持原有单列表布局，只展示当前 member/context、今日预计和今日实际；改名、拖动、右键新增、复制和实际调整都只作用于今日实例。工具区在“新增事项”旁提供“从进行中导入”，点击后在同一弹框内切换到来源选择步骤，避免叠加弹框或同时铺开两份列表。

来源选择步骤只展示进行中事项树、全选和逐项勾选，不展示搜索、预计时间输入或时长统计；勾选只发起复制实例，不修改来源顺序或字段。导入成功后在同一弹框内回到配置列表，由配置列表展示最新的今日实例树；重复来源已有每次预计时自动显示为初始今日预计，其余事项仍由用户填写。失败时保留选择草稿并展示权威错误。配置弹框中的今日预计继续提供 30、60、90、120、150 分钟常用项，以及每次 15 分钟的加减。

快速编辑计划也按范围拆分：今日页只编辑当前工作日实例树；进行中页只编辑长期事项树。两边不再把过滤结果合并回同一套完整计划基线。

今日顶部合计只累计 member 叶子实例的今日预计与已确认实际，排除 context 和已完成折叠之外的父级重复统计。

### 8. 同步、迁移与兼容性

今日实例仍是 tasks 实体，因此标题、层级、完成和实际相关字段沿用现有事项同步。需要同步新增的实例元数据，并在 task_day_plans 实体中同步 instance_task_id 和 excluded/included 状态。

迁移采用“保留历史、当前日懒物化”的方式：

- 旧 task_daily_estimates 与 task_day_plans 历史记录不删除。
- 首次读取某个工作空间当前工作日时，把仍为 included 或存在当日预计的来源计划转换为独立实例，把当前日预计迁移到实例并写入映射。
- 过去日期保留原按日预计和实际记录供报告使用，不批量复制成今日实例。
- 转换完成后，当前日后续所有今日写入只使用实例 ID。

Supabase schema 增加 tasks 实例字段、约束、索引、任务变更触发内容和 task_day_plans.instance_task_id。完整快照和备份恢复必须同时包含实例事项、来源日期映射、按日预计、时间分配和 actual_time_adjustments；缺少 actual_time_adjustments 时继续拒绝覆盖本地数据。

旧客户端会把新实例误当成普通事项，且会继续按同一 ID 修改两边，因此云工作空间必须设置最低客户端版本或明确升级门禁。回滚应用版本不能安全恢复旧语义，只能使用迁移前备份恢复。

## Risks / Trade-offs

- [实例增多导致长期事项列表误混入今日项] → 所有列表、搜索、报告和执行范围都显式声明 day_instance_date 过滤，并用数据库查询测试覆盖。
- [迁移前实际时间留来源、迁移后留实例，用户看到当天分成两段] → 在升级说明中明确边界；这是避免报告重复计数和历史重写的唯一一致规则。
- [重复模板和实例出现双重状态] → task_occurrences 仅作生成账本；已有实例时以实例为唯一可见完成和内容权威。
- [移出后重复规则再次自动生成] → 来源/日期映射保留 excluded，自动生成必须先检查映射是否存在。
- [context 实例残留成空父级] → 移出或删除后执行孤立 context 清理，并用树级测试验证。
- [旧客户端写入共享工作空间破坏实例元数据] → 发布时强制最低版本；快照恢复和双设备测试验证升级顺序。
- [原地复制层级后来源改名造成用户困惑] → 今日实例从创建起就是独立事项；界面只通过来源追溯说明来源，不暗示持续同步。

## Migration Plan

1. 新增本地 SQLite 迁移：为 tasks 增加实例字段和索引，为 task_day_plans 增加 instance_task_id；用约束测试覆盖普通事项、member、context 和归档后再加入。
2. 实现来源日期映射、实例创建、context 补齐、按日预计复制和当前日懒物化；验证重复执行迁移不会生成重复实例。
3. 将事项、今日计划、执行快照和报告查询切换到明确范围；先在测试中固定进行中与今日 ID 不同、互相修改不传播。
4. 接入前端 store 和待办列表，再改造“配置今日事项”、执行弹框、未归属时间和快速编辑计划。
5. 更新 Supabase schema、增量同步、outbox、快照、备份恢复、冲突展示和最低客户端版本说明。
6. 完成本地升级、双设备、重复事项、删除/再次加入、时间分配和真实 Supabase 验证后发布。

回滚策略：应用代码回滚前必须恢复迁移前本地数据库或云端快照。因为旧版本无法识别实例元数据，不能直接与升级后的工作空间混用。
