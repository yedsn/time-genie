# Design

## Context

见 `proposal.md` 和 `specs/time-entry-history/spec.md`。当前 `time_entry_list` 要求传入单个 `work_date`，SQLite 查询只返回当天记录；Pinia 的 `entries` 同时承担计时页列表、运行中记录、今日分钟和今日完成事项计算。`TimeTrackingWorkspace.vue` 因而直接把 `store.entries` 排序后展示为“今日时间记录”。

历史 `time_entries` 已持久化在本地 SQLite，云端模式也会将权威快照和增量写入本地缓存。表上已有 `(workspace_id, work_date, started_at)` 索引，因此本变更不需要数据迁移或 Supabase schema 变更，但必须避免把全量历史塞进现有 `entries` 后污染今日业务状态。

## Goals / Non-Goals

**Goals:**

- 后端以有记录日期为分页单位返回完整日期组及当日汇总。
- 前端将今日业务状态与历史分页状态拆分，同时复用现有记录编辑组件和写入接口。
- 记录修改、同步增量和日期组消失后，页码与汇总能够稳定刷新。
- 本地和云端读取路径保持只读、即时且不触发网络等待或同步写入。

**Non-Goals:**

- 不增加任意日期范围筛选、关键词搜索、主体筛选或无限滚动。
- 不改变时间记录、分配、计时链或跨日切片的数据模型。
- 不恢复已经删除或标记为无效的记录。
- 不允许手动补录选择历史日期；补录仍默认发生在工作空间今天。
- 不改变报告、今日概览和计时结算的日期口径。

## Decisions

### 1. 新增日期分页接口，保留现有单日接口

新增独立的历史查询请求，例如 `page`、固定 `page_size=7` 和 `include_breaks`，返回：

```text
page
page_size
total_days
total_pages
groups[]
  work_date
  entry_count
  raw_minutes
  allocated_minutes
  pending_minutes
  break_minutes
  entries[]
revision
```

查询先从 `time_entries` 中取得倒序去重的有记录日期并执行 `LIMIT 7 OFFSET ...`，再一次读取这些日期的记录，按 `work_date DESC, started_at DESC, id DESC` 排序并组装 DTO。这样分页边界由日期决定，不会因为某天记录很多而拆页。现有 `time_entry_list(work_date)` 继续服务今日加载和兼容调用，避免扩大对计时状态与今日统计的改造。

备选方案是一次读取所有历史记录后由前端分页。该方案启动和每 5 秒刷新会随历史量增长，并把所有记录加载与序列化到前台，因此不采用。按记录条数分页会拆开同一天，也不采用。

### 2. Pinia 拆分今日条目与历史页面状态

保留现有 `entries` 作为今天及当前运行状态的数据源，继续供 `runningEntry`、`todayMinutes`、`pendingMinutes`、今日完成统计和停止确认流程使用。新增独立状态：

```text
timeHistoryGroups
timeHistoryPage
timeHistoryTotalDays
timeHistoryTotalPages
timeHistoryLoading
```

计时页面列表改读 `timeHistoryGroups`，顶部计时控制仍读 `runningEntry`。首次进入计时页默认加载第一页；用户翻页只刷新历史状态。全局的 5 秒计时刷新不应重复拉取所有历史页，历史第一页或当前页只在时间领域 revision 变化、用户操作完成、页面重新进入或用户主动翻页时刷新。

备选方案是把历史记录全部加入 `entries`，再为每个今日计算增加日期过滤。该方案容易遗漏现有和未来的计算消费者，也可能让运行状态与选中记录被翻页覆盖，因此不采用。

### 3. 编辑操作按 ID 写入，成功后刷新相关数据域

现有修正、分配和处置接口已经按记录 ID 工作，可继续编辑历史记录。历史列表展开时仍构建相同的分配与修正草稿。写入成功后：

1. 更新或移除今日 `entries` 中的同 ID 记录（如果存在）；
2. 重新加载当前历史页，以服务端/SQLite 汇总重新计算日期组；
3. 若 `total_pages` 缩小且当前页越界，则切换到最后一个有效页并再读取一次；
4. 继续刷新事项、今日概览和报告等现有受影响域。

停止计时或手动补录产生今天记录时，历史视图若在第一页则立即刷新；若用户正在更早页，保留当前页位置，只更新分页总数，并在用户回到第一页时看到新记录。调整归属入口定位刚结束记录时，应切换到计时页第一页并展开对应记录，保证现有停止确认路径仍然可达。

### 4. 日期汇总由后端统一计算

每组的工作分钟使用工作记录的 `settlement_minutes`，已归属分钟使用 allocation 汇总，待确认分钟为 `max(0, raw - allocated)`，休息分钟只统计 `kind='break'`。这些计算沿用现有单日列表语义，并在后端组装，避免前端对跨日计时链的分钟分配规则产生第二套实现。

日期显示文本由前端结合 `workspaceToday` 和工作空间时区上下文生成：今天、昨天附带明确日期，其他日期显示明确日期及星期。业务分组键始终使用后端 `work_date`，不使用设备本地时区重新推导。

### 5. 本地优先读取，不增加云端历史 RPC

新查询直接读取本地 SQLite。云端模式继续依靠现有快照、增量和 outbox 把 `time_entries`、segments 与 allocations 收敛到本地缓存；翻页不直接请求 Supabase，不设置保存中状态。旧的 `cloud_time_entry_list` 保持兼容，但新 UI 不需要另建网络分页 RPC。

这符合应用现有本地优先原则，也避免分页期间阻塞前台。远端增量到达后通过时间领域刷新信号使当前历史页重新查询本地缓存。

### 6. 查询性能依赖现有日期索引，并避免 N+1 扩散

日期页选择可使用现有 `idx_time_entries_date(workspace_id, work_date, started_at)`。实现初期可以复用 `load_entry` 保持计时链结算分钟与 allocation 语义一致，但必须增加覆盖多日、多记录的性能测试，并确认每次只加载 7 个日期。若测试显示逐条加载 allocation 成为瓶颈，应在同一任务内改为批量加载该页 entries、allocations 和必要链信息，而不是增加新表或缓存镜像。

## Risks / Trade-offs

- [当前页在删除最后一组后越界] → 后端返回总页数，前端检测越界并自动回到最后有效页。
- [历史页编辑后旧草稿仍存在] → 写入成功或记录消失时清理该 ID 的分配与修正草稿，并重新加载当前页。
- [全局 5 秒刷新导致历史查询频繁] → 保留今日轻量刷新；历史页仅在 revision/领域变化、页面进入、写入成功或翻页时加载。
- [跨日计时链的结算分钟汇总复杂] → 后端继续复用现有 `load_entry` 与计时链分钟分配规则，前端不自行重算。
- [一天包含大量记录使单页仍然很长] → 这是保证同日完整性的明确取舍；本变更不增加组内二次分页，可通过折叠日期组作为后续独立增强。
- [云端缓存尚未拉到全部历史时结果暂不完整] → 页面展示当前本地权威缓存，后台同步到达后刷新；不让读取等待网络。

## Migration Plan

1. 增加 Rust 历史日期分页 DTO、只读查询和单元测试，不改变现有单日接口。
2. 增加 Tauri 前端类型与调用，并在 Pinia 中建立独立历史状态和加载动作。
3. 将计时页面列表切换为日期分组与分页，复用现有记录编辑区域。
4. 接入写入后刷新、停止确认定位、远端时间领域变化刷新和越界页校正。
5. 运行本地/云端模式、跨日切片、大量历史和今日统计隔离验收后发布。

回滚客户端时保留新增只读命令不会改变数据；旧界面仍可使用现有单日接口显示今天记录。
