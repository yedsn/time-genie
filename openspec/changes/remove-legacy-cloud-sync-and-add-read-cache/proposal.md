# Proposal

## Why

当前客户端虽然已经支持 Supabase 直连，但仍保留 SQLite 云端业务副本、outbox、增量拉取、冲突处理、协议升级与旧世代救援等完整旧同步链路，导致用户继续遇到“待同步、冲突、旧队列、版本升级”等不再符合目标架构的状态，并显著增加维护和排障成本。需要将存储模型收敛为本地 SQLite 与 Supabase 直连两种模式，同时为云端模式提供不参与同步的只读缓存，以兼顾交互速度、重启后的快速展示和短暂离线查看。

## What Changes

- **BREAKING**：删除客户端 `LegacySyncSqlite` / `sync_v1` 运行路径，以及 SQLite 业务副本到 Supabase 的 outbox、增量拉取、冲突处理、旧世代阻塞、队列救援和协议升级流程。
- 将业务存储路由收敛为两种模式：本地模式只读写本地 SQLite；云端模式只通过 Supabase 查询与 mutation RPC 读写权威数据。
- 删除界面中的待同步数量、同步冲突、手动同步、旧协议升级和“重新下载本地云端副本”等入口；云端状态只表达连接、认证、只读缓存和请求失败。
- 保留用户显式发起的“本地完整复制到云端”和“云端完整复制到本地”，但复制完成后不建立持续同步关系。
- 为直连云端保留现有进程内查询缓存，并新增隔离的持久化只读缓存；缓存不得产生 outbox、不得接受离线编辑、不得成为业务权威。
- 云端不可用时允许展示明确标记的只读缓存；所有 mutation 继续直接提交 Supabase，失败时不得先写入缓存伪装成成功。
- 提供“强制刷新云端数据”入口：忽略本机缓存和旧 workspace epoch，重新读取 Supabase 权威上下文并刷新当前界面的云端数据，但不执行上传或双向同步。
- 通过新的 SQLite 清理迁移移除旧同步运行时表；已发布历史迁移继续保留，后续新基线可再压缩。
- Supabase 旧同步 RPC 分阶段退役：先撤销执行权限并保留明确拒绝旧客户端的兼容屏障，兼容窗口结束后再删除旧函数和协议代际字段。
- 清理旧同步测试、验证脚本和未使用的 npm 自依赖，改为覆盖双模式边界、直连幂等、缓存失效、离线只读和显式完整复制。

## Capabilities

### New Capabilities

- `dual-storage-architecture`: 规定本地 SQLite 与 Supabase 直连两种互斥存储模式、业务读写边界、显式完整复制和旧同步体系退役行为。
- `direct-cloud-read-cache`: 规定直连云端的进程内缓存和持久化只读缓存、失效边界、离线展示与安全隔离要求。

### Modified Capabilities

无。当前项目尚未归档主规格，本变更以新 capability 固化最终目标行为。

## Impact

- Rust 后端：`storage_contract.rs`、`cloud_sync.rs`、`supabase.rs`、`data_protection.rs`、`database.rs`、`lib.rs`，以及仍调用旧入队/flush 钩子的业务模块。
- Vue 前端：存储状态模型、云端状态展示、旧协议升级入口、右下角同步入口、查询缓存协调器和退出/切换工作区时的缓存清理。
- SQLite：新增最终清理迁移；旧同步表退出运行时，云端只读缓存使用与本地业务表隔离的缓存存储。
- Supabase：旧 sync RPC 的权限和退役迁移、直连查询/mutation、Realtime 失效通知以及 workspace 恢复边界。
- 测试与脚本：删除旧同步、冲突收敛、离线重试和协议升级测试，补充双模式隔离、直连幂等、缓存生命周期和旧客户端拒绝测试。
- 依赖：移除未使用的 `timegenie: file:` npm 自依赖；预计不会引入新的第三方运行时依赖。
