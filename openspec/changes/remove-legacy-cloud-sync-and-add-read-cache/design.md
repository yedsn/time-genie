# Design

## Context

参见 `proposal.md` 的 Why。当前存储路由同时包含 `LocalSqlite`、`LegacySyncSqlite` 和 `DirectSupabase`；旧同步模块仍负责 outbox、增量拉取、冲突、epoch 阻塞、后台协调、旧计时接口和 SQLite 云端副本重建。与此同时，直连路径已经具备按查询键合并请求、短时新鲜度复用、按业务域失效和 Supabase mutation RPC，因此旧同步不再是日常业务能力的必要依赖。

本应用仍需要一个本地 SQLite 数据库保存本地模式业务数据和设备级元数据。云端模式也需要在本机保存 Supabase 配置、会话元数据、设备信息和备份历史，但这些内容不能被误认为云端业务副本。当前工作树存在正在进行的未归属时间修复，实施时必须保留并在其基础上重构。

## Goals / Non-Goals

**Goals:**

- 将业务路由收敛为本地 SQLite 和直连 Supabase 两种后端。
- 删除旧同步生产路径、公开命令、界面状态、SQLite 运行时表和不再适用的测试。
- 让云端重复读取主要命中内存缓存，并用独立的持久只读快照改善冷启动和短暂离线查看。
- 保持本地数据、云端数据和云端缓存三者边界清楚，任何缓存故障都不能改变权威数据。
- 继续支持显式完整复制、云端快照恢复、认证和设备撤销。

**Non-Goals:**

- 不支持云端离线编辑、后台补传或多主合并。
- 不把本地模式 SQLite 改造成通用缓存数据库。
- 不保证旧版 `sync_v1` 客户端继续工作；只保证其请求不能再修改云端数据。
- 不重写现有 Supabase 业务 RPC 的业务规则，也不移除服务端内部必要的幂等键和并发保护。
- 不在本变更中引入通用客户端查询框架或新的第三方缓存依赖。

## Decisions

### 1. 存储路由只保留两个业务后端

`StorageBackend` 最终只保留 `LocalSqlite` 与 `DirectSupabase`。所有业务命令继续通过统一的领域路由选择适配器，但本地适配器只操作本地业务表，云端适配器只操作 Supabase。切换模式不会自动合并或覆盖另一模式的数据：用户切回本地时看到此前的本地数据，只有显式完整复制才能替换目标。

选择该方式是因为它保留现有领域边界，并能用自动化检查证明云端命令没有落入 SQLite。直接在各命令中读取字符串模式会减少一个文件，但会分散边界判断，容易再次出现混合写入。

### 2. 删除旧协调器，仅保留小型 Realtime 失效服务

从 `cloud_sync.rs` 提取仍有价值的 Supabase Realtime 连接、重连和领域失效通知，形成职责单一的基础设施模块。删除后台同步 round、outbox claim/push、增量 pull/apply、冲突解决、旧 tracking lease、本地云端副本重建和旧 Tauri 命令。计时与未归属时间只调用已有 direct mutation 与 query。

不保留“空实现”兼容层。空实现虽然能减少一次性改动，但会让业务模块继续依赖已经不存在的语义，并使以后误用 `enqueue_entity` 仍能编译。

### 3. 旧本地同步数据采用一次性备份后清理

新增最后一个 SQLite 迁移。迁移前的应用启动流程检测旧同步表是否包含待处理数据：若有，则生成一次本地救援备份和脱敏诊断摘要；无论是否存在旧队列，都不尝试上传或合并。随后迁移删除旧同步表和相关索引。已发布的历史迁移文件继续保留，确保旧数据库可以先走完旧迁移再执行最终清理；全新安装仍按完整迁移链创建后再删除旧表，待未来建立新 baseline 时再压缩。

本地模式的业务表不因清理而删除。云端模式中遗留的本地业务数据也不自动解释为云端缓存；它只可能作为用户此前的本地模式数据或救援备份来源。

相比继续保留隔离队列表，此方案避免运行时代码为不可恢复的同步语义永久付出复杂度。

### 4. Supabase 旧接口以“拒绝优先、最终删除”方式退役

部署顺序如下：

1. 先部署 SQL，使旧 patch、增量拉取和协议升级入口无法由普通客户端成功执行；在需要兼容诊断的发布窗口内，可用同签名 tombstone 返回明确的 `LEGACY_SYNC_UNSUPPORTED`。
2. 发布只包含直连路径的新客户端，并把所有现有 workspace 固定到直连语义。
3. 兼容窗口为零或结束后，删除旧 RPC、grant、触发器和仅服务旧协议的状态；`schema.sql` 以直连最终结构为准。

TimeGenie 当前为个人项目，默认可以采用零兼容窗口：客户端和 SQL 在同一发布批次升级，旧客户端之后收到函数不存在或明确不支持错误，但绝不能继续写入。若部署环境要求观察窗口，则保留的只能是拒绝型 tombstone，不能保留实际同步实现。

### 5. 进程内缓存继续承担主要性能优化

复用现有查询协调器的缓存键、新鲜期、in-flight 合并、generation 和 change sequence 失效逻辑。各页面通过领域键读取；本机 mutation 成功和 Realtime 事件都只失效受影响领域，避免全量刷新。工作台 bootstrap 与高频计时状态可以使用短新鲜期，稳定列表使用更长新鲜期，但权威刷新仍由业务事件驱动。

不引入通用状态管理或 HTTP 缓存库，因为现有机制已经覆盖本应用需要的请求预算控制。

### 6. 持久缓存使用独立 SQLite 文件，只保存查询快照

新增独立的 `cloud-read-cache.sqlite3`，不与本地业务数据库共用表。使用现有 SQLite 依赖，核心表按以下逻辑字段组织：

```text
account_id
workspace_id
domain
query_key
payload_json
workspace_epoch
change_seq
fetched_at
expires_at
cache_schema_version
```

联合身份与查询键唯一定位记录。缓存层只暴露读取快照、保存成功查询、按领域删除、按身份删除、容量清理和完整重置，不提供实体级 insert/update/delete API。payload 使用与直连 query DTO 一致的 JSON，解析失败或 schema version 不匹配时直接丢弃。

默认保留上限为 64 MiB 或 30 天，以先达到者为准；按最近使用时间清理。该数值作为集中常量，可以后续调整而不改变规格。缓存文件不得保存会话 token、认证头、集成密钥或密码字段。

选择独立文件而不是复用本地业务表，是为了让“删除云端缓存”天然不会影响本地模式数据，并能通过文件级和 API 级边界阻止缓存演变成另一个业务副本。

### 7. 缓存采用 stale-while-revalidate，但离线强制只读

云端启动流程在确认当前账号和 workspace 后读取匹配快照并快速填充界面，同时发起权威查询。在线查询成功后替换内存数据并异步刷新磁盘快照；写缓存失败仅记录诊断。Supabase 不可访问时，只能展示快照和最后更新时间，所有 mutation 入口依据云端可写状态禁用或在后端再次拒绝。

mutation 成功后不做复杂本地乐观重放：优先采用 RPC 返回值更新当前页面，并删除或标记相关持久快照为过期，再按领域刷新。这样可避免在客户端复制服务端业务规则。

### 8. 缓存失效以身份、epoch 和业务域为边界

- Realtime 事件：按 domain 删除对应持久快照，并将内存键标记为 stale。
- 本机 mutation：按 mutation 影响域执行同样失效。
- workspace 恢复或 epoch 改变：删除该 workspace 全部缓存并重新 bootstrap。
- 退出登录、设备被撤销、切换账号：立即清空内存数据，并删除或隔离原身份缓存；默认直接删除以减少隐私风险。
- 切换 workspace：清空当前内存 generation，只读取新 workspace 身份范围内的缓存。
- 缓存损坏：关闭并删除缓存文件后重新创建，不影响主数据库或云端操作。

### 9. 精简存储状态契约和界面

`StorageModeSnapshot` 不再返回 `pendingOperations`、`conflictCount`、`syncState`、`epochBlocked` 或 `configuredCloudProtocol`。保留或新增：存储模式、后端类型、online、cloud access state、cloud writable、read-only reason、workspace 标识，以及当前展示是否来自缓存和缓存获取时间。

右下角同步按钮改为普通云端状态入口或删除；不会再触发 catch-up/save。SeaTable 导入的重复检测属于导入业务，不受此变更影响。

### 10. 拆分 Supabase 巨型模块以匹配保留职责

在删除 legacy 段后，将剩余代码至少按认证与设备、直连业务请求、显式完整复制、快照与恢复拆分。拆分目标是让依赖方向可验证，而不是建立新的抽象框架：业务领域模块可以调用 direct API，缓存与 Realtime 不能调用本地业务仓库，数据保护模块只能在显式用户流程中跨越存储边界。

## Risks / Trade-offs

- [旧队列中可能有从未上传的数据] → 清理前自动创建本机救援备份和诊断摘要，并明确这份数据不会自动合并；用户仍可通过显式导入/复制恢复。
- [旧客户端在服务端清理后不可用] → 发布前先部署拒绝型屏障或同步发布新客户端；旧调用必须失败且不得修改数据。
- [只读缓存展示陈旧数据] → 始终显示缓存标识和最后更新时间，在线后立即 revalidate，mutation 在不可写时禁止。
- [缓存包含敏感业务内容] → 按账号/workspace 隔离，退出时清除，排除所有认证和集成秘密，并沿用应用数据目录权限。
- [独立缓存增加一个 SQLite 文件和生命周期逻辑] → API 严格限制为 query snapshot，损坏即可整体丢弃，不提供迁移式业务写入。
- [一次性删除大量代码可能产生回归] → 按“边界测试先行、业务 hook 清除、协调器删除、数据库清理、UI 清理”的顺序实施，每阶段运行本地与云端验收。
- [Supabase 模块拆分与旧逻辑删除交叉导致 diff 过大] → 先锁定 direct 行为测试，再以职责搬迁保持行为，最后删除无引用 legacy 代码。

## Migration Plan

1. 增加自动化边界检查，保证云端业务路径不写本地业务表或旧同步表，并记录现有 direct 测试基线。
2. 部署 Supabase 旧接口拒绝迁移，确认 direct RPC、快照恢复和显式完整复制仍可用。
3. 将所有领域适配器移除 enqueue/flush 调用，删除旧前端命令调用，使新版本不再生成 outbox。
4. 在首次运行新版本且执行破坏性本地清理前，若发现旧队列数据则创建救援备份；随后执行 SQLite 最终清理迁移。
5. 提取 Realtime 服务并删除旧协调器、冲突、升级和队列救援代码。
6. 上线精简后的存储状态和 UI，验证本地模式、本地↔云端显式复制、登录恢复和设备撤销。
7. 接入持久只读缓存，先只用于读取和离线展示，再启用领域失效与容量清理。
8. 更新 Supabase 最终 schema，按部署策略删除 tombstone 和旧协议字段；执行完整 schema 与双设备直连验收。

回滚时不得重新启用 outbox 上传。应用代码可以回滚到“无持久缓存的直连版本”，缓存文件可直接删除；SQLite 清理前生成的救援备份用于人工恢复本地数据。Supabase 若需回滚，只能恢复 direct RPC 与数据结构，不能恢复旧客户端写权限。
