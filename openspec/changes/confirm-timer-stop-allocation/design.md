# Design

## Context

当前本地停止计时由 `time_tracking` 负责结束记录，并通过 `create_default_allocation` 控制是否立即写入默认分配；前端 store 的 `stopTimer`、系统托盘菜单和原生兜底托盘都把该参数设为立即创建默认分配。计时页已经具备已结束记录的归属编辑器、分配拆分和“同时完成”能力，但快速结束入口没有复用这套确认流程。

云端模式通过 Supabase `timer_stop` RPC 完成停止，并在数据库函数内部根据 `default_task_id` 自动创建分配。托盘菜单在 Rust 后台线程执行，不具备直接展示 Vue 对话框的能力；它需要通过统一事件让主窗口接管后续确认。现有 `selectedEntryId`、计时页展开状态和 `navigate-page`/窗口打开机制可以作为定位刚结束记录的基础。

## Goals / Non-Goals

**Goals:**

- 统一所有结束入口的“停止、确认归属、调整归属、同时完成”语义。
- 让停止操作本身幂等，归属确认成为独立且可重试的操作。
- 复用计时页已有的分配编辑能力，避免快速确认与完整编辑器产生两套规则。
- 保持 `timer.stopped` 和 `task.completed` 的事件边界清晰，并覆盖本地、云端和托盘路径。

**Non-Goals:**

- 不重新设计现有计时记录的数据库结构或历史记录展示方式，除非为了表达待确认状态确实需要最小字段调整。
- 不改变未归属时间会话的处理流程；它仍由现有未归属时间对话框负责。
- 不改变手动补录和已有已结束记录的归属编辑交互，只让结束后的新记录复用它。
- 不增加新的任务完成规则；“同时完成”继续遵守现有事项版本校验和重复事项轮次规则。

## Decisions

### 1. 停止阶段不自动写入默认分配

本地 `timer_stop` 和云端 `timer_stop` 都改为只结束计时、关闭当前时间片并返回已结束记录，不再在停止事务中写入默认 `time_allocations`。默认事项仍保留在时间记录上，作为后续确认的初始草稿来源。

这样可以保证停止和归属是两个可独立重试的业务操作，也避免用户尚未确认时误触发分配或事项完成。历史上由其他内部测试、Obsidian 写入流程或已有业务调用显式要求默认分配的路径需要保留原有参数语义，不能用全局字符串替换破坏这些调用；应将面向用户的计时停止路径与内部兼容路径区分清楚。

备选方案是停止时继续写默认分配，再在确认时覆盖分配。该方案会导致“尚未确认”的记录实际上已经归属，云端和 Hook 的状态也难以准确表达，因此不采用。

### 2. 前端使用统一的待确认状态

store 在成功停止后保存刚结束的记录 ID，并将其设置为待确认记录；所有 Vue 结束按钮调用同一个结束动作。确认界面可以是共享组件，至少需要支持：

- 显示本段时长、默认事项和默认分钟数。
- 默认事项全部归属的快速确认。
- 每条分配的“同时完成”。
- “调整归属”入口。
- 无有效默认事项时选择事项、休息时间或无效时间。

归属确认最终仍调用现有的分配替换服务，以保持分钟校验、拆分规则、事项版本检查和完成事件逻辑一致。为了防止重复创建，确认操作使用当前记录版本；成功后清理待确认标记并刷新工作区。

备选方案是只在计时页展示待确认状态，让右上角和托盘结束后只弹一个“请去计时页处理”的提示。该方案无法满足默认配置一键保存，也会让托盘操作体验不完整，因此不采用。

### 3. 调整归属通过主窗口接管并定位记录

当结束动作发生在右上角或悬浮托盘面板，用户选择“调整归属”时，前端打开主窗口，切换到 `timer` 页面，将 `selectedEntryId` 设置为刚结束记录 ID，并让 `TimeTrackingWorkspace` 监听该选择变化后展开对应记录。计时页原有的 `ensureDraft` 负责初始化默认分配草稿。

当结束动作来自系统托盘或原生兜底托盘，Rust 后台只负责结束计时并发出包含记录 ID和来源的事件；主窗口收到事件后刷新数据并展示确认入口。若主窗口尚未打开，则先打开主窗口，再由前端接管确认。

不在 Rust 托盘线程中实现第二套分配编辑器，因为托盘菜单无法承载完整的事项选择和多行分钟编辑，也会造成与 Vue 计时页不一致。

### 4. 托盘结束动作发出“待确认”结果，而不是静默完成

Tauri 托盘菜单和 Windows 原生兜底托盘继续使用后台动作，但停止动作的返回数据必须包含已结束记录及其 ID。Rust 发出统一的计时状态/工作数据事件，同时增加或扩展一个可携带记录 ID 的“需要确认归属”通知。主窗口、悬浮窗口和其他窗口只通过该通知刷新并进入前端确认流程。

托盘菜单的启用状态仍只根据 running/paused 判断；待确认记录不影响开始下一段计时的单例约束，但在用户确认前不应被再次自动分配。若产品现有云端约束要求未完成同步时禁止新计时，则沿用该约束。

### 5. 云端把结束和归属拆成两个 RPC 事务

Supabase `timer_stop` 删除自动插入默认分配的逻辑，只更新计时状态和时间片。`time_allocation_replace` 继续负责保存归属并处理“同时完成”，由本次变更补齐云端操作幂等和版本检查所需的参数传递，使其与本地 `time_allocation_replace` 具备相同的外部语义。

云端停止成功后，客户端拉取最新快照并保留记录 ID；用户确认时才提交归属。若归属提交失败，前端保留已结束记录和草稿，允许重新加载后重试。重复停止请求依靠现有 operation ID 缓存，重复归属确认也必须使用稳定 operation ID 或等价的版本幂等策略，避免重复分配和重复完成事件。

### 6. Hook 事件按业务提交边界发布

`timer.stopped` 在停止事务成功提交后发布，事件载荷标明记录已结束但可能仍待归属；它不携带“已分配”结论。`task.completed` 继续由归属确认中实际发生的事项状态跃迁产生。停止事务不提前完成事项，归属确认失败也不能回滚已经成功的停止。

## Risks / Trade-offs

- [旧数据和内部调用依赖停止时自动分配] -> 清点所有 `TimerStopRequest` 调用，明确面向用户的路径使用“暂不分配”，内部测试或兼容场景显式保留旧参数；增加本地回归测试。
- [主窗口未打开时托盘事件无人接收] -> 事件通知与工作数据刷新同时发送；主窗口启动时主动读取当前已结束待确认记录，避免只依赖瞬时事件。
- [云端 schema 与本地代码版本不一致] -> 先更新 `supabase/schema.sql` 和云端集成测试，再接入客户端调用；对旧 RPC 返回错误给出可识别提示，不静默回退到本地自动归属。
- [停止成功但归属确认失败导致待确认记录积累] -> 在计时页明确显示“待确认”状态，允许随时重新打开记录；不将待确认记录误计入已归属分钟。
- [多窗口或多设备同时确认] -> 所有停止和归属写入都携带 expected version，遇到冲突时刷新记录并提示用户，不覆盖另一端已经提交的分配。
- [同时完成事件重复触发] -> 完成事项前比较当前状态并使用现有事务内版本校验；补充重复确认、网络重试和托盘重放测试。

## Migration Plan

1. 先发布本地和云端停止接口的兼容实现，保证旧参数仍能被非用户路径识别。
2. 发布前端统一结束确认流程，并让所有入口停止时显式使用“暂不创建默认分配”。
3. 对升级前已经自动归属的历史记录不做迁移；它们继续按已归属记录展示。
4. 对升级后未确认的已结束记录，启动或刷新工作区时通过记录状态和归属分钟数识别并展示待确认状态。
5. 回滚时保留已结束记录和已提交归属，不删除用户已经确认的数据；必要时恢复停止接口的默认分配开关，但不回滚数据库历史。
