# Design

## Context

见 `proposal.md` 与 `specs/task-status-tabs/spec.md`。当前 `task_list` 默认返回进行中与已完成事项，`loadWorkspaceData` 将全部记录放入同一个前端数组，`PlanListEditor` 再分成待办列表与底部折叠的已完成列表。该方式没有利用数据库已有的 `tasks.completed_at` 与 `idx_tasks_completed_at`，历史数据增长后仍会全部加载。

普通事项完成时会写入 `tasks.completed_at`；重复事项则把每日状态写入 `task_occurrences.completed_at`，事项本体保持 `open`。因此普通事项完成历史可以直接以 `tasks.status = 'done'` 为边界，而无需新增状态或数据迁移。

## Goals / Non-Goals

**Goals:**

- 让主体工作台默认只加载和渲染进行中事项树。
- 提供按主体、完成时间倒序的普通已完成事项后端分页。
- 保持已完成记录的路径、累计用时、编辑、删除与恢复能力。
- 在恢复或删除后修正总数和页码，不留下空白无效页。
- 复用现有 SQLite、Supabase 和事项状态同步语义。

**Non-Goals:**

- 不把重复事项每日轮次做成历史列表，也不新增“完成记录”页面。
- 不新增独立“归档”状态或归档动作。
- 不改变事项树排序、父子关系或完成/恢复的业务语义。
- 不为完成历史引入无限滚动、全文搜索或跨主体汇总。

## Decisions

### 1. 进行中树与已完成历史使用独立查询

工作台初始加载调用现有事项查询的未完成模式，只返回 `status = 'open'` 所需的完整树。另增一个已完成分页查询，参数包含 `subjectId`、`page` 和 `pageSize`，返回记录、总数、当前页和总页数。

这比继续使用 `includeCompleted: true` 后在前端切片更能控制数据库读取、序列化和前端响应式成本。备选方案是保留全量查询只增加 Tab，它实现较少，但无法解决完成历史持续增长的问题，因此不采用。

### 2. 已完成分页查询只读取普通任务表

查询条件固定为当前工作区、当前主体、`tasks.status = 'done'` 且未删除，排序使用 `completed_at DESC, id DESC`，默认每页 20 条。查询不联接 `task_occurrences`，因此重复事项每日完成轮次天然排除。

事项 DTO 增加可选 `completedAt`，普通完成历史必须返回该值。现有主事项查询也可携带该字段以保持类型一致，但进行中列表不依赖它。

备选方案是从 `task_status_events` 重建最近完成时间。该表适合审计，但恢复后可能存在多个完成事件；当前 `tasks.completed_at` 已表达事项当前完成状态及最近一次完成时间，且已有索引，因此直接使用更明确。

### 3. 已完成历史采用平铺记录而非分页树

已完成页按单条事项展示，并携带持久化时可重建的完整路径标签。分页不会尝试保持完整父子树，因为父子记录可能分布在不同页，强行补齐祖先会导致页大小不稳定。

累计用时沿用现有事项汇总逻辑；路径应基于所有未删除同主体事项构建，而不是仅基于当前页，确保子事项即使父项不在该页仍显示正确上下文。

备选方案是按根事项整棵树分页。它能保留视觉层级，但一棵树可能包含大量节点，无法保证每页大小，排序也难以严格按单项完成时间，因此不采用。

### 4. Tab 与分页状态归主体管理

待办页面维护当前标签；切换主体时默认回到“进行中”。已完成分页状态至少包含 `items`、`page`、`pageSize`、`total`、`totalPages`、`loading` 和请求序号。请求序号用于避免快速切换主体或页码时旧响应覆盖新内容。

首次点击“已完成”时加载第 1 页；之后完成、恢复、删除或工作数据变化时，将相应主体的历史缓存标记为过期。正在查看已完成页时立即刷新，否则等下次进入再加载。

### 5. 已完成操作复用现有事项命令

恢复、编辑和删除继续调用现有状态切换、保存和删除命令，不增加第二套 mutation API。操作成功后先更新或失效完成历史，再刷新进行中树与主体未完成计数。

恢复或删除使当前页为空且页码大于 1 时，将页码减 1 后重新查询；第 1 页为空则展示空状态。恢复后的事项按现有树排序规则重新出现在进行中列表。

### 6. 完成计数使用轻量聚合而非完成明细

Tab 上的“已完成”数量来自分页结果的 `total`，或独立的主体状态计数聚合；不得为了展示数量加载所有完成记录。主体侧栏现有 `openTaskCount` 继续表示未完成数量。

首次尚未查询完成历史时，可以延迟显示数量或通过轻量计数一并返回。实现时优先让主体列表接口返回普通已完成总数，避免每个主体各发一次请求；如果这会扩大主体接口职责，则只在当前主体打开已完成页后展示精确总数。无论采用哪一种，不能加载完成明细来计算数量。

## Risks / Trade-offs

- [普通事项的父项被删除或路径发生变化] → 历史记录展示当前可重建路径；父项不存在时退化为现有可用标题，不阻塞分页。
- [完成后立即切换标签发生请求竞态] → 使用主体 ID、页码和请求序号校验响应，只接纳最新请求。
- [恢复或删除改变总页数] → 操作后根据新总数归一化页码，空页自动回退并重新加载。
- [完成历史累计用时计算成本较高] → 只对当前页事项聚合用时，并依赖现有分配表索引；避免为所有已完成事项预计算。
- [父子任务状态混合导致路径可见但层级不可操作] → 已完成页明确采用平铺历史，路径只用于识别，不提供拖拽和缩进。
- [重复事项本体长期保持 open] → 这是预期边界；当日轮次仍由今日视图和报告承担，不进入普通完成历史。

## Migration Plan

1. 扩展事项 DTO 与分页查询，复用现有 `completed_at` 和索引，并添加后端排序、主体隔离及重复轮次排除测试。
2. 将主工作台事项加载改为只取进行中树，增加已完成分页状态和服务接口。
3. 将 `PlanListEditor` 的底部完成折叠区拆为独立 Tab/历史视图，接入分页和操作后的页码修正。
4. 验证本地与云端模式下完成、恢复、编辑、删除、跨窗口刷新和主体切换。

回滚时可恢复原来的 `includeCompleted: true` 与底部折叠区域；本变更没有数据迁移，回滚不会改变已有事项状态或历史数据。
