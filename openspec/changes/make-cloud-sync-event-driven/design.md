# Design

## Context

见 `proposal.md` 的问题说明。当前实现已经具备本地 outbox、`flush_if_online` 唤醒、Supabase Realtime 订阅、变更序号和冲突保护，但同步调度仍由三条路径直接执行：前端每 15 秒调用完整刷新、Rust 后台每 15 秒轮询，以及 Realtime 回调直接拉取。网络层使用阻塞式 HTTP；日常增量只用于判断“是否有变化”，一旦有变化便拉取完整快照，并在 `TransactionBehavior::Immediate` 事务内清空、重插大部分业务表。同步完成后，前端忽略事件中的领域信息并全量重载多个 store。

现有 `reduce-timer-sync-conflicts` 负责 outbox 版本链、依赖和真实冲突边界；`align-cloud-task-planning-features` 已把按日预估、重复规则和每日轮次接入云端实体范围。本设计复用这些契约，不建立第二套上传或冲突模型。

## Goals / Non-Goals

**Goals:**

- 建立单一事件驱动同步协调器，统一本地写入、Realtime、重连补齐和手动重试。
- 让所有阻塞网络和同步数据库工作与窗口事件、Tokio async worker 隔离。
- 用有序增量批次替代日常完整快照，支持更新、删除、断线补齐和本地 dirty 实体延迟协调。
- 将前端刷新范围缩小到实际变化领域，并避免通知风暴。
- 保留现有 outbox 幂等、版本校验、设备撤销、认证和冲突处理语义。

**Non-Goals:**

- 不把业务写入改成通过 WebSocket 直接提交；Realtime 只负责变化通知和连接状态。
- 不要求应用进程完全退出后继续同步，也不新增系统服务。
- 不取消 Socket 心跳、断线重连退避、认证续期或计时设备租约续期。
- 不改变按日预估、重复事项、计时、报告等业务规则。
- 不移除完整快照能力；它继续用于首次初始化、显式重置、迁移和增量历史失效后的受控恢复。

## Decisions

### 1. 使用单一后台协调器消费同步信号

新增一个进程内协调器，持有工作空间级状态和信号通道。信号至少区分：本地 outbox 已变化、Realtime 观察到远端序号、连接/登录已就绪、手动异常重试，以及独立的租约维护。发送信号只更新“仍需处理”的状态并唤醒协调器；同步正在执行时到达的信号不会再启动任务，而是在当前轮结束后继续收敛到稳定状态。

协调轮次遵循：恢复未知 `sending` 状态 → 上传可发送 outbox → 处理冲突/认证结果 → 从最后确认序号拉取远端增量 → 应用可安全实体 → 再检查本轮中新产生的信号。上传和拉取共用同一串行边界，避免当前 `CLOUD_SYNC_OPERATION_LOCK` 只保护部分入口而 Realtime、前端命令仍从旁路进入。

备选方案是为上传和拉取各建一个任务。它吞吐更高，但会重新引入快照/增量与本地写入竞态，并使 dirty 实体保护复杂化，因此不采用。

### 2. Realtime 只发送提示，不在 Socket 回调中做阻塞同步

Realtime listener 保持 async WebSocket 和心跳；收到 `postgres_changes` 后只解析工作空间与观察到的 `change_seq`，然后向协调器发送远端变化信号。连接订阅成功时同样发送“补齐”信号。回调不得直接执行阻塞 HTTP、SQLite 事务或前端刷新。

实际上传继续使用现有鉴权 RPC/HTTP，因为它提供响应确认、幂等操作和版本冲突结果。直接把业务载荷通过 Socket Broadcast 提交需要另建确认、重放和权限协议，不如现有 RPC 可靠。

### 3. 将阻塞同步放入专用执行环境

协调器的网络、JSON 和 SQLite 工作在专用阻塞 worker 中执行；async 任务只负责连接、信号转发和等待结果。第一阶段可使用单一长期 worker 线程或受控 `spawn_blocking`，但必须保证不会为每个通知无限创建阻塞任务，并能在工作空间切换或退出时安全停止。

网络获取与 JSON 校验在 SQLite 写事务外完成。增量应用按有界批次使用短事务；批次间重新检查本地 revision/outbox，使前台写入不必等待一次大规模补齐全部完成。

备选方案是把全部 Supabase 客户端改为 async。长期看可行，但不能自动解决长 SQLite 事务、重复调度和全量前端刷新；本次先以执行环境隔离配合增量事务解决用户可见卡顿。

### 4. 增加原子增量读取 RPC

保留 `workspace_changes` 作为有序游标。增加一个受 RLS/设备授权保护的增量读取 RPC，输入工作空间、`after_change_seq` 和批量上限，返回：

- 有序 change 元数据和批次最高序号；
- 本批涉及实体的最终当前表示，或明确 tombstone；
- 本批结束时的云端最新序号和 `has_more`；
- 增量历史不可用或协议不兼容时的显式 `reset_required`。

RPC 在一个数据库快照中收集变更集合和实体当前表示，客户端不需要对每条 change 发一次请求。对同一实体在批次内多次变化可折叠为最终表示，但游标仍推进到已覆盖的最高序号。复合身份沿用现有编码：按日预估为事项加日期、每日轮次为事项加日期、重复规则以事项为聚合根。

备选方案是在 `workspace_changes` 永久保存每次完整行镜像。它能精确重放历史，但会复制大量 JSON、放大写入和保留敏感设置历史；TimeGenie 需要同步当前状态而非审计事件，因此采用“有序 change + 批次最终实体表示”。

### 5. 用实体适配器增量落地

为每种云端实体建立统一的读取键、版本、删除语义、本地表映射和前端领域映射。批次先规范化并按依赖排序，再在短事务中 upsert/delete：

1. 主体、工作日和工作空间设置；
2. 事项、事项状态事件；
3. 按日预估、重复规则、每日轮次；
4. 工时记录、分段和分配；
5. 报告模板、报告和报告事项；
6. 集成配置与外部绑定。

父子事项、工时子表、报告子表等聚合实体由一个适配器原子应用，避免中间暴露孤儿数据。删除遵守现有软删除/历史保留规则，不通过通用物理删除猜测业务语义。

完整快照函数与 `clear_snapshot_cache` 不再被日常 pull 调用，只保留给明确恢复流程。

### 6. 对 dirty 实体记录延迟远端协调

拉取批次遇到本机相同实体存在 pending、sending、failed 或 conflict outbox 时，不覆盖本地业务表。客户端记录 `entity_type + entity_id + observed_remote_version/change_seq` 的延迟协调项，并可继续应用批次中的其他实体、推进全局游标。

当相关 outbox 成功、被用户采用云端、保留本地重提或被删除后，协调器重新请求该实体的最新表示并执行版本判断。这样不会因为一个 dirty 实体阻塞所有远端变化，也不会因推进游标永久丢失该实体的远端更新。

延迟表属于本地同步元数据，可通过 SQLite 迁移新增；它不进入业务快照或云端同步。

### 7. 区分连接维护、自动重试和业务轮询

删除前端与 Rust 的 15 秒业务数据同步。以下定时机制保留但职责收窄：

- Realtime 心跳仅维持 Socket；
- 断线重连使用带抖动的指数退避，订阅成功后发送一次补齐信号；
- 临时上传失败依据 outbox 的 `next_retry_at`/退避状态安排一次性唤醒，不周期扫描云端；
- 计时设备租约按租约到期时间提前续期，不顺带 push、pull 或刷新全部业务数据。

网络恢复检测、应用重新获得焦点或系统从休眠恢复可以发送连接/补齐信号，但不得直接调用完整快照。

### 8. 前端按领域合并刷新

后端增量结果产生精确领域集合，例如 `subjects`、`tasks`、`time`、`reports`、`settings`。按日预估、重复规则和每日轮次归入 `tasks`，工时分段和分配归入 `time`。事件还携带已应用的最高变更序号和来源。

前端监听器在短窗口内合并领域，并维护单飞刷新：已有同领域刷新时只标记再刷新一次。`App.vue` 不再无条件调用四组加载；MainWorkbench 的 15 秒 `runCloudSync` 定时器删除。前台本地操作自身已有的精确/乐观更新可以保留，不因本机上传成功重复全量刷新。

### 9. 手动命令改为后台唤醒语义

状态读取保持只读。正常状态不展示日常“同步”动作；存在积压或错误时的“重试同步”只向协调器发送强制重试信号并立即返回当前状态，后续进展通过状态事件更新。冲突和重新登录继续进入专门流程。

为诊断和自动化可保留一个显式“等待协调器稳定”的内部测试接口，但用户界面不得依赖它阻塞等待完整同步。

## Risks / Trade-offs

- [Realtime 通知可能丢失或重复] → 所有通知只作提示，以持久化变更序号补齐；启动和重连必做 catch-up，应用按实体版本幂等。
- [批次读取到实体比某条 change 更新的版本] → 把批次视为当前状态收敛而非事件回放，按最高实体版本应用，并将游标推进到 RPC 声明已覆盖的序号。
- [dirty 实体推进游标后遗漏远端状态] → 持久化延迟协调项，outbox 状态变化后显式重取该实体。
- [大批离线变化仍造成写锁压力] → 限制批次大小、事务外解析、按聚合边界短事务应用，并在批次间让出执行机会。
- [旧客户端仍会定时拉完整快照] → 服务端 RPC 采用新增接口并保持旧接口兼容；客户端发布后再评估清理旧兼容路径。
- [精确领域映射遗漏派生页面] → 建立实体到领域的集中映射和测试，必要时一个实体可声明多个领域，但不得默认广播全部领域。
- [租约续期从原循环拆出后失效] → 独立按到期时间调度并增加前后台、休眠恢复和多设备租约测试。

## Migration Plan

1. 先在 Supabase 增加兼容的增量读取 RPC、权限和测试，不删除现有 `cloud_snapshot_get` 或 `cloud_apply_patch`。
2. 增加本地延迟协调元数据迁移和实体增量适配器；在测试中与完整快照结果做等价对照。
3. 引入单一后台协调器和专用阻塞执行环境，让 Realtime、本地 outbox 和连接恢复只发信号。
4. 切换日常 pull 到增量 RPC，保留显式首次初始化/重置的完整快照路径。
5. 更新前端领域刷新和异常恢复按钮，最后删除前端及 Rust 的固定业务同步定时器。
6. 在测试 Supabase 环境完成双设备、断线重连、慢网、大批补齐和规划实体验证后发布客户端。
7. 如需回滚客户端，服务端新增 RPC 和本地新增表可安全保留；旧客户端仍可使用原快照接口。不得回滚或删除尚未上传的 outbox 与延迟协调记录。
