# Design

## Context

见 `proposal.md` 与 `specs/tray-hover-workbench/spec.md`。当前主窗口与托盘悬浮面板是两个独立 WebView，各自创建 Pinia store。托盘页面初始化时会加载工作台与计时数据，但因 `startClock(false)` 明确跳过未归属状态；本地事项写命令只更新调用窗口的 store，后端没有统一广播，因此另一个 WebView 可能保留旧列表。

事项候选层虽然传送到 WebView 的 `body`，仍无法越过操作系统窗口边界。当前托盘窗口为 `420x360`，任何仅靠 CSS 的加宽都会受到该物理边界裁切。Rust 侧同时缓存悬浮窗口边界用于三秒移出关闭和外部点击关闭，动态改变窗口尺寸后必须同步更新该边界。

## Goals / Non-Goals

**Goals:**

- 复用现有未归属状态与处理弹框，不复制分配业务。
- 让托盘面板在每次显示和跨窗口变更后获得最新数据。
- 通过单一 WebView 的动态扩展解决候选层物理裁切，并保持当前托盘生命周期规则。
- 将窗口显示、刷新、扩展和恢复建模为可验证的显式事件。

**Non-Goals:**

- 不改变开始事项时清除当前未归属时间的既有语义。
- 不在托盘面板内重做完整的未归属多事项分配编辑器。
- 不创建新的事项选择 WebView 或原生窗口。
- 不改变 SQLite、Supabase 或未归属同步数据结构。
- 不让托盘窗口因候选列表获得更高的系统焦点优先级。

## Decisions

### 1. 托盘空闲状态同时展示未归属摘要和快速计时选择

托盘 store 在初始化时也加载未归属状态，并使用现有 `unassignedSeconds` 随本地时钟更新。空闲布局分为未归属摘要、主体/事项选择和动作区。存在未归属时间时展示累计值及“处理未归属时间”；无未归属时间时展示空状态。

“处理未归属时间”不在托盘直接提交分配，而是调用新的主窗口导航命令：先隐藏托盘窗口，再显示主窗口并向主窗口发送一个强制打开未归属弹框的事件。主窗口收到后刷新未归属状态，确认仍有有效时间，再执行 `promptUnassignedResolution(true)`。这样完整复用多事项拆分、休息、丢弃和完成事项逻辑。

备选方案是在托盘直接把全部时间分给所选事项。它会弱化现有多分配能力并使“开始计时”产生隐含历史写入，因此不采用。

### 2. 显示事件驱动刷新，跨窗口广播保证一致性

Rust 在悬浮窗口成功显示后向该窗口发送 `tray-hover-shown` 事件。托盘前端收到事件后并行刷新工作台、计时和未归属状态；首次挂载也执行相同刷新。标题栏手动刷新按钮复用这一协调函数，通过单一 `refreshing` 状态合并重复请求并展示旋转图标。

主体和事项的所有本地写命令成功后，由 Rust 发出 `work-data-changed`，domains 精确标记为 `subjects` 或 `tasks`；或者由统一的前端写后通知帮助函数发出等价事件。优先选择 Rust 命令成功后广播，因为它覆盖来自任意 WebView 的调用并只在持久化成功后通知。既有 Realtime/poll 事件继续复用 `workDataRefreshPlan`。

刷新协调保留原有 request sequence 防止旧请求覆盖新结果。托盘组件维护本地 `selectedTaskId`，刷新后若目标仍存在且可选择则保留，否则清空。加载失败保留 store 中最后一次成功数据，并由手动刷新路径显示错误提示；后台自动刷新只显示非阻塞状态。

备选方案是只加手动刷新按钮。它不能解决用户不知道数据已过期的问题，因此仅作为兜底。

### 3. 用单一预置 WebView 表面与原生区域裁剪替代运行中缩放

用户可见的紧凑面板继续使用 `420x360`。Rust 在窗口显示前就计算并设置完整表面尺寸（目标约 `720x520`，受当前显示器工作区限制），让完整表面向左和向上延伸，并保持右下角 `420x360` 主体面板锚点稳定。完整表面在可见期间始终保持相同位置和尺寸；紧凑状态通过 Windows 原生裁剪只开放主体区域，事项 autocomplete 打开时开放完整预置区域。窗口本身不隐藏、不重新显示、不移动也不缩放，避免影响悬停触发可靠性。

候选 Popper 仍位于同一 WebView 中，但使用接近扩展窗口宽度的列表；每个候选采用单行网格，主体、完整路径、用时和状态分别占列。路径只在扩展宽度仍不足时省略，并保留 `title` 或等价完整内容提示。

动态扩展事件由 `TaskSelectControl` 的托盘专用 variant 对外发出 open/close，而非把通用选择器与 Tauri API 强耦合。`HoverPanel` 负责调用窗口命令并在卸载、选择完成、打开主窗口及关闭面板前恢复模式。

备选方案一是使用 `overflow: visible` 或更宽 Popper，无法跨越 WebView 物理边界。备选方案二是创建第二个选择窗口，焦点、外部点击、多显示器定位和跨窗口状态复杂度更高，当前不采用。

### 4. Rust 使用当前可见原生区域作为唯一命中区域

窗口物理外框在显示期间保持为完整候选表面，但紧凑模式的有效交互区域只能是右下角主体面板，不能把被裁掉的透明区域算作面板内部。模式命令因此只切换原生裁剪区域，并同步把 `HoverState.window_bounds` 更新为紧凑主体 bounds 或完整表面 bounds；普通轮询只读取当前有效 bounds。不得再通过窗口子类命中穿透作为显示前置条件，因为安装失败会直接阻断悬停面板显示。

`HoverState` 保存当前托盘物理 bounds、紧凑主体 bounds、完整表面 bounds、当前有效交互 bounds、显示 generation 与模式。区域命令在不持锁的情况下调用原生裁剪 API，成功后再写入有效 bounds。外部点击和三秒离开判断使用最新有效 bounds。隐藏、Esc、托盘左右键及菜单动作都恢复紧凑裁剪，下一次显示始终只暴露紧凑主体。

### 5. 预置表面继续按目标显示器 DPI 计算

Rust 使用保存的托盘锚点确定目标 monitor，将紧凑主体与完整表面的逻辑尺寸转换为目标 monitor 的物理尺寸，再通过工作区 bounds 夹紧。完整表面优先保持右下角主体接近原托盘锚点，让候选空间向左、向上生长。

扩展前后都不调用 `set_focus()`。Element Plus 输入控件仍可在用户点击后获得 WebView 内部焦点，但窗口显示本身不抢占当前应用焦点。

## Risks / Trade-offs

- [完整表面物理外框覆盖更多桌面区域] → 紧凑状态使用原生窗口区域裁掉额外部分，被裁区域不可见且不接收鼠标命中；完整表面仍限制在目标 monitor 工作区。
- [区域切换成功但状态边界未更新会导致误关] → 专用命令以 generation 校验模式切换，并在成功后同步当前有效 bounds。
- [自动刷新与用户正在输入临时事项竞争] → 候选打开或输入为 dirty 时不重置输入文本；仅在已选事项失效时清空模型选择。
- [主窗口收到打开未归属弹框事件时状态已经变化] → 先刷新权威未归属快照，仅在仍存在有效 session 和正时长时打开。
- [本地写后广播重复触发刷新] → 复用现有 80ms domain 合并与 request sequence，重复事件只产生一轮有效结果。
- [25ms 指针监控读取动态状态增加锁频率] → 锁内只复制小型 bounds/state，不执行窗口 API；监控仍只在面板可见时运行。
- [选择区域开放影响原有三秒关闭倒计时] → 模式切换和窗口内部交互清除 outside timestamp，防止区域变化瞬间继承旧倒计时。

## Migration Plan

1. 先加入事件和窗口模式命令，保持现有紧凑界面不调用新能力。
2. 接入托盘显示刷新、主体/事项写后广播和未归属处理导航，并验证两个 WebView 状态收敛。
3. 接入托盘事项选择 open/close 事件和动态扩展窗口，随后启用单行候选布局。
4. 运行前端业务测试、生产构建、Rust 定位/边界测试和 `cargo check`，再用实际 Windows 可执行文件执行托盘交互矩阵。

回滚时移除前端对新事件和 resize 命令的调用即可恢复固定 `420x360` 面板；新增事件和命令可暂时保留为未使用兼容接口，不涉及数据迁移。
