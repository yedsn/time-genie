# Design

## Context

见 `proposal.md` 与 `specs/unified-task-selection/spec.md`。当前 `TaskSelectControl.vue` 已被顶部快速计时、计时工作区、手动补录、时间记录分配和未归属时间弹框共同复用，但它在输入框左侧内嵌主体选择器，并以“全部主体”为默认值把所有事项合并到一个候选列表。组件还把未完成和已完成事项再次分组，未直接复用待办所使用的主体树形顺序。

当前计时入口通过 `intentMode` 使用显式一级/二级创建意图；非计时入口则在失焦或提交时调用 `store.addQuickTask` 隐式创建临时一级事项。后续保存工时前，各入口调用组件暴露的 `commit()`，再由现有 store 方法持久化本地草稿事项。元素库的 autocomplete 支持候选头部插槽，可在不另造浮层定位系统的情况下承载主体 Tab。

## Goals / Non-Goals

**Goals:**

- 让一个公共组件承担主体 Tab、当前主体事项树、搜索、已有事项选择和显式分级创建。
- 复用待办数据的既有顺序，避免选择器维护第二套排序规则。
- 让计时和非计时入口共享同一交互状态机，同时保持各调用方现有的业务提交边界。
- 保持紧凑、默认和焦点三种尺寸变体可用，并补足键盘与窄宽度行为。

**Non-Goals:**

- 不把报告范围的批量勾选、待办编辑器或“调整今日实际”的批量编辑改造成单事项选择器。
- 不改变最多两级、父事项不可直接计时、父级可接受子事项等领域规则。
- 不增加数据库迁移、云端 RPC 或新的事项创建协议。
- 不恢复已完成历史到常规候选列表；公共工作数据继续使用现有进行中事项集合。

## Decisions

### 1. 在 autocomplete 候选头部承载主体 Tab

移除组件外层的 `el-select`，使用 autocomplete 的 header 插槽渲染主体 Tab。Tab 区保持单行、横向可滚动并固定在候选滚动区域上方；事项行仍由现有候选模板渲染。这样输入框在所有入口都获得完整横向空间，主体切换与事项浏览也处于同一操作上下文。

备选方案是自建 Popover、输入框和虚拟列表。它可以完全控制焦点，但会重复实现 autocomplete 的键盘、高亮、定位和关闭行为，本次没有足够收益。另一个方案是在输入框尾部保留主体下拉，仍会占用紧凑入口宽度，也不能解决主体与候选列表割裂的问题。

### 2. 组件维护局部激活主体，不修改全局待办主体

选择器为每个实例维护 `activeSubjectId`。打开或模型事项变化时，默认主体优先级为“已选事项所属主体 -> `store.selectedSubjectId` -> 第一个可用主体”。用户在某个选择器内切换 Tab 只刷新该实例的候选，不调用 `store.selectSubject`，从而避免分配弹框中的操作意外跳转待办页面。

主体变化时保留 `inputText`、`dirty` 和现有 `modelValue`；若处于父级选择层，则返回搜索/创建方式层，因为父级候选与主体强绑定。组件随后重新请求候选并重置键盘高亮，防止确认旧主体的隐藏项。

备选方案是所有选择器直接双向绑定全局主体。它能让不同入口同步主体，但一次分配中可能存在多个选择器，任一行切换主体都会影响其他行及主导航，副作用过大。

### 3. 从同一主体事项数组生成树形候选，不做完成状态二次排序

常规工作数据已经通过后端 `task_list(includeCompleted: false)` 按主体、排序值和创建时间读取，并经树形整理后供待办使用。选择器按 `activeSubjectId` 从这份数组过滤，并使用与待办相同的父子扁平顺序；事项行增加显式深度字段或等价样式，以缩进而不是重复完整路径来表达层级。搜索匹配仍检查标题和完整路径，但不改变匹配项的相对顺序。

为防止后续两处树排序再次分叉，优先把“按已有数组构造父子扁平顺序/深度”的纯逻辑抽到共享模块，供 store 或选择器复用；若现有数组已严格保持待办顺序，则选择器只过滤并计算深度，不再额外排序。

备选方案是继续使用完整路径文本平铺列表。它在同名事项搜索时有帮助，但视觉上仍难快速扫描层级，因此完整路径只用于搜索和悬浮提示。

### 4. 将显式创建意图扩展到所有调用方

删除非 `intentMode` 的失焦自动创建分支。组件统一只在用户点击“新建为一级事项”或完成“新建为二级事项 -> 选择父级”后产生结构化创建意图。计时入口继续把意图交给现有原子计时转换；补录和分配入口则由组件或调用方使用已有本地草稿创建能力创建对应层级的未持久化事项，再通过 `update:modelValue` 返回事项 ID，后续保存工时时仍由 `persistTimerTask` 走现有持久化流程。

为保持公共入口简单，组件对外保留现有 `commit()`，但它只解析已存在的精确匹配或返回当前具体事项，绝不因为失焦、表单保存或 `commit()` 本身创建事项。新建动作完成后，`commit()` 才能返回新草稿 ID。

若现有 store 缺少“按指定主体创建二级草稿”的通用入口，则补充一个最小的本地草稿方法，复用 `addTask`/`addChildTask` 的字段和插入规则；不得引入新的后端命令。

备选方案是让补录和分配入口也直接持久化新事项后再保存工时。它会改变失败边界，并可能留下用户尚未提交工时就已保存的孤立事项，因此继续沿用本地草稿延迟持久化。

### 5. 保留一个公共组件，调用方只处理业务结果

`GlobalTimerBar.vue` 和计时页继续处理 `TaskSelectIntent` 与忙碌状态；手动补录、历史分配和未归属分配只接收模型事项 ID，并沿用各自保存、完成事项和错误处理流程。样式通过组件变体和容器响应式规则适配不同宽度，不在调用方复制 Tab 或候选逻辑。

验证以纯逻辑测试和源代码契约检查覆盖默认主体、切换保留、树形顺序、创建状态机及全部调用点，再运行类型检查和前端构建。

## Risks / Trade-offs

- [Autocomplete 头部点击可能触发输入框失焦或关闭浮层] -> 在 Tab 的指针事件阶段阻止默认失焦，并在切换后主动保持输入焦点、刷新候选和高亮。
- [多个选择器实例各自记忆主体，用户可能期望同步] -> 每次打开都有一致的默认规则，且已选事项永远优先定位到其所属主体；不以全局副作用换取隐式同步。
- [取消失焦自动创建会让旧习惯多一步点击] -> 两个创建动作始终紧邻候选列表并支持键盘选择，换取避免误建和所有入口一致。
- [父事项作为不可选行可能占用较多空间] -> 保留它是满足待办顺序和层级识别的必要上下文；继续显示简洁状态与用时，不展开额外详情。
- [非计时入口创建二级草稿可能暴露现有本地草稿方法差异] -> 统一复用同一草稿构造和父级资格校验，并用保存失败保留草稿的现有流程验证。

## Migration Plan

1. 先抽取或补充选择器纯逻辑及验证脚本，锁定默认主体、顺序和创建状态转换。
2. 重构公共选择器模板、状态和样式，移除左侧主体控件与全部主体分支。
3. 将显式创建动作扩展到补录和分配入口，按需补充通用层级草稿创建方法。
4. 运行类型检查、验证脚本和前端构建，并在顶部栏、计时页、补录、历史分配和未归属弹框手工检查键盘与窄宽度。

该变更没有数据迁移。回滚时可恢复旧选择器模板和非计时隐式创建分支；已按新交互创建的事项仍是普通事项，不需要数据回滚。
