# Proposal

## Why

普通事项计时目前会被本地读取协调和云端租约心跳同时推进版本，导致即使只有一台设备，也可能出现本地基础版本落后于云端版本的自冲突。需要明确单一计时权威，并让响应丢失、旧队列和历史幂等冲突自动收敛，避免用户手工处理程序自身制造的冲突。

## What Changes

- 将普通事项计时的开始、暂停、继续、连续性中断、跨日、停止和分配版本链统一为本地生成、按序上传的状态机。
- 云端租约只协调设备持有权和未归属时间边界，不再通过心跳、续租或纯读取隐式修改普通事项计时记录及其版本。
- 云端继续校验计时操作的版本跨度、顺序和幂等性，并返回权威计时快照；其他设备通过增量同步收敛。
- 当旧计时操作的基础版本落后于云端时，客户端 SHALL 区分“请求已经被云端应用”“同一设备的旧中间状态”和“真正的竞争修改”，自动确认或压缩安全的本机操作链。
- 当保留本地最终结果可安全执行时，系统 SHALL 以云端当前版本为基础提交最新完整计时状态，并删除已被覆盖的中间操作；只有无法安全判断时才展示用户冲突。
- 兼容并清理已有 `timer_continuity_close` 幂等冲突、版本冲突和其后的同实体队列链，不删除已结束、已分配的本地时间记录。

## Capabilities

### New Capabilities

- `timer-sync-authority`: 定义普通事项计时的单一版本权威、有序离线操作链、租约职责边界以及幂等和版本异常的自动收敛规则。

### Modified Capabilities

无。当前项目尚未建立持久化主规格，本变更新增普通事项计时同步能力规格，并与既有未归属时间变更保持职责分离。

## Impact

- Rust 本地计时与同步队列：`src-tauri/src/time_tracking.rs`、`src-tauri/src/cloud_sync.rs`、必要的 SQLite 迁移与启动恢复逻辑。
- Supabase 权威 schema 与部署补丁：租约 RPC、普通计时协调函数、计时补丁应用和 processed operations 查询。
- 同步冲突与队列界面：自动收敛后的状态、真正冲突的展示条件及诊断信息。
- 测试：单机休眠恢复、窗口/托盘读取、租约续期、响应丢失、重复请求、离线多步操作、跨日和双设备接管。
