# Design

## Context

见 `proposal.md` 和 `specs/shared-unassigned-time/spec.md`。当前实现把云端未归属时间建模为带 `duration_seconds`、多个 `segments`、`collecting/awaiting_resolution` 状态和版本的共享聚合。前端每 5 秒读取状态，运行秒数由已封口分段加开放分段起点在本地派生；事项开始和结束分别写入 pause/resume 操作，跨越阈值会把会话更新为 `awaiting_resolution`。

现有同步协调器同时把本地待上传、Realtime 远端提示和连接恢复都映射到同一个 `syncing` 布尔值，因此即使没有待上传操作，右下角也可能显示短暂的“正在同步”。现有 SQLite 与 Supabase 数据中已经存在未处理会话和分段，迁移不能删除已生成的最终记录或丢失仍需用户处理的历史日期记录。

## Goals / Non-Goals

**Goals:**

- 用一个当天活动起点表达当前空闲累计，不再保存自然增长的累计秒数或开放分段进度。
- 把事项开始、事项结束、未归属处理和连续性中断定义为少量原子边界动作。
- 保证本地操作即时返回，云端提交在后台进行，多设备最终采用同一边界。
- 让保存状态严格对应待上传业务写入，而不是连接或拉取活动。
- 兼容迁移既有活动会话、历史待处理会话和最终时间记录。

**Non-Goals:**

- 不保留事项开始前尚未处理的未归属时间。
- 不恢复未归属暂停/继续、多分段累计或跨设备合并分段。
- 不移除事项计时设备租约、Realtime 增量通知或通用 outbox。
- 不改变分配分钟校验、休息记录、丢弃及事项完成等处理界面的业务含义。

## Decisions

### 1. 用活动锚点替代可暂停的分段聚合

活动状态最小化为工作空间、工作日期、`active_since`、版本和必要的处理元数据。活动锚点存在表示当前空闲；没有活动锚点表示正在事项计时或尚未建立空闲边界。显示秒数始终为 `max(0, now - active_since)`，阈值状态由客户端本地派生。

已有 `unassigned_sessions` 可在兼容期继续作为存储载体，但活动会话只保留一个开放起点，不再追加 pause/resume 分段，也不因时间增长刷新 `duration_seconds`、`last_continuous_at` 或版本。已处理历史会话及其 segments 继续只读保留，避免破坏既有记录。后续可在确认没有旧客户端后再物理精简列和表，本变更不要求立即删表。

备选方案是保留 `accumulated_seconds + active_since`。它可以继续累计事项开始前的空闲段，但仍需要暂停、恢复和多个边界，与本次简化规则不符。

### 2. 事项开始将当前锚点原子转为丢弃终态

本地模式在同一个 SQLite 事务中使当前活动会话失效并创建事项计时；云端模式的事项开始 outbox/RPC 同时校验当前计时版本并清除服务端活动锚点。该清除使用独立的系统处置类型或等价终态，不能生成 time_entry，也不能进入历史待处理列表。

云端以服务端接受事项开始的权威边界为最终时间；本地先乐观清除，若事项开始失败则根据返回的权威状态恢复或收敛。其他设备通过同一次事项变更或关联的未归属实体增量停止显示旧锚点。

备选方案是先要求用户处理未归属时间再允许开始事项。它会保留时间，但增加操作阻塞，不符合“直接开始即清零”的目标。

### 3. 事项停止原子创建或取得唯一的新锚点

停止最后一个活动事项时，以权威 `ended_at` 作为新锚点。服务端在同一事务或同一幂等操作链中 compare-and-create 当天活动锚点，并通过工作空间加工作日期的唯一约束让并发设备取得同一结果。若仍存在其他活动计时，则不创建锚点。

创建锚点是一次真实业务写入，应进入 outbox 并计入待保存数量；之后秒数增长不再写入。

### 4. 未归属处理继续使用版本和 operation ID

分配、休息和丢弃仍以锚点 ID、expected version 和 operation ID 原子提交。服务端在事务中锁定活动锚点、以权威时间计算实际时长、生成至多一个最终记录，并在仍为空闲时以同一个 `resolved_at` 创建下一锚点。重复或竞争请求返回已经接受的终态和下一锚点。

处理前展示的秒数来自客户端本地时钟；最终记录以服务端边界计算，允许出现很小的显示校正。离线处理先本地保存并排队，重连时若锚点已被事项开始清除或由另一设备处理，则采用云端终态，不重复生成记录。

### 5. 连续性中断使用本地观察，但重置边界需要共享

客户端保留不进入 outbox 的本地连续运行观察时间。检测到超过容忍窗口的退出、休眠或调度中断时，旧活动锚点不计入中断期间；恢复客户端提交一个幂等的 anchor-reset 动作，以恢复确认时间替换旧锚点。服务端使用版本比较和工作空间锁避免多设备同时恢复产生多个锚点。

若另一台设备在此期间持续在线，它仍可能认为工作空间连续空闲。为了符合“单个客户端退出期间不累计”的规则，重置动作以发起恢复的客户端观察为准，会结束所有设备正在显示的旧锚点。这是简化模型的明确取舍。

### 6. 跨日只切换锚点，不累计前一天开放秒数

连续运行跨过工作日边界时，旧日期锚点在日界线封口为历史待处理会话，新日期以日界线建立活动锚点。若跨日前后检测到连续性中断，则旧锚点按最后确认边界处理，新日期从恢复时间开始。该动作每个工作日最多同步一次。

已存在的历史待处理会话不因用户开始今天的事项而删除，用户仍可按现有入口处理；“开始事项即清零”只作用于当前活动锚点。这样避免升级时静默删除过去日期的可结算时间。

### 7. 将保存状态与传输活动解耦

后端状态分离为：待上传操作数量与状态、冲突/失败，以及后台传输或拉取活动。右下角主状态只使用前两类：待上传数量大于零时显示“还有 N 项待保存”，清零后显示“所有更改均已保存”。连接建立、Realtime catch-up、远端增量拉取和未归属本地刷新不得设置面向用户的保存中状态。

诊断页可以继续展示后台连接和拉取活动，但它不驱动保存状态动画。连续多项真实上传可保持一个稳定的进行状态，避免每轮协调器闪烁。

### 8. 兼容迁移优先收敛，不立即删除旧结构

SQLite 迁移为活动会话增加可区分系统清除的处置信息或等价标记，并建立当天活动锚点唯一约束。升级时：

1. 已 resolved/discarded 会话和已生成 time_entry 原样保留。
2. 过去日期的 awaiting_resolution 会话保留为历史待处理。
3. 当前日期存在多分段活动会话时，以当前开放分段起点作为新锚点；若没有开放分段则不恢复活动锚点。旧的已封口分段不并入新显示时长。
4. 云端已有权威锚点时优先采用云端；本机候选只在云端没有活动锚点时参与 compare-and-create。
5. 旧 pause/resume/awaiting-resolution outbox 若尚未发送，则在迁移中折叠为与当前锚点一致的一次 upsert 或标记为已被迁移取代，不能继续重放旧语义。

Supabase 先部署兼容 RPC 和约束，允许新客户端读写简化锚点；旧客户端在兼容窗口内可能继续提交完整镜像，服务端需要拒绝或归一化会重新引入多分段活动累计的更新。

## Risks / Trade-offs

- [开始事项会永久放弃尚未处理的当前未归属时间] → 在规格和界面文案中明确该规则；不生成隐藏记录，也不提供自动恢复。
- [多设备本地时钟略有偏差] → 展示使用本地时钟，最终处理与新锚点采用服务端权威边界并允许轻微校正。
- [一个设备休眠恢复会重置其他在线设备的锚点] → 以版本化 reset 收敛到一个共享边界，并通过诊断日志记录重置来源。
- [旧 outbox 重放恢复旧分段语义] → 迁移时识别旧操作类型并折叠或废弃；服务端兼容层不接受活动累计镜像覆盖新锚点。
- [事项开始成功但锚点清除未传播] → 服务端将两个变化放在同一事务和同一 workspace change 序列中，客户端增量应用后强制刷新计时与未归属域。
- [保存状态不再展示纯拉取活动，用户误以为没有联网] → 账号或连接诊断区域继续显示连接异常，但不把下载活动描述为待保存。

## Migration Plan

1. 先部署 Supabase 兼容补丁：简化锚点读写、事项开始清除、事项停止创建、处理后重建、连续性重置、唯一约束与旧 payload 兼容。
2. 发布 SQLite 迁移和 Rust 状态机，迁移当前活动会话与旧 outbox，同时保留历史待处理和最终记录。
3. 更新前端本地派生计时与阈值判断，移除依赖 pause/resume/awaiting-resolution 同步的刷新路径。
4. 将右下角保存状态切换到真实 outbox 数量，并把连接/拉取活动留在诊断信息。
5. 完成双设备、离线、休眠、跨日、旧数据升级和状态提示验收后发布。

回滚时保留新增字段和 RPC。旧客户端可以继续读取兼容会话，但无法恢复已经由新规则清除且未生成记录的未归属时间；回滚不得尝试重建这些时间。
