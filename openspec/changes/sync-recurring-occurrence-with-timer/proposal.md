# Proposal

## Why

周期事项首次通过计时流程被物化时，目前只在本地创建当日轮次，云端计时原子操作没有同步该轮次，导致后续完成或恢复操作以本地版本更新一个云端不存在的实体，并产生 `current version <NULL>` 的伪冲突。需要让计时事实与其引用的周期轮次一起可靠收敛，并为已经进入该异常状态的本地队列提供安全恢复。

## What Changes

- 在开始或切换到周期事项计时时，将当日周期轮次纳入同一次云端计时转换，保证远端在接受计时记录时同步具备对应轮次。
- 保持本地优先体验：本地事务仍立即开始计时，云端同步失败时保留可重试操作，不因网络响应阻塞按钮反馈。
- 对“本地存在完整周期轮次、云端实体不存在”的既有同步冲突提供自动重基为创建的恢复路径，不再要求用户反复重试不可能成功的版本更新。
- 保留真实多设备竞争保护；只有能够确认云端缺失且本地实体可完整创建时才自动恢复，不覆盖云端已存在的未知版本。
- 增加周期事项首次计时、完成、恢复、双设备竞争及历史 `<NULL>` 冲突恢复的验证。

## Capabilities

### New Capabilities

- `recurring-occurrence-timer-sync`: 定义周期事项当日轮次随计时转换创建、后续版本连续同步，以及云端缺失轮次时的安全自动恢复行为。

### Modified Capabilities

无。当前项目没有已同步到主规格目录的对应能力，本变更以新的增量能力记录要求。

## Impact

- Rust 本地计时与同步入队逻辑：`src-tauri/src/time_tracking.rs`、`src-tauri/src/cloud_sync.rs` 及相关测试。
- Supabase 云端原子操作和实体版本应用：`supabase/schema.sql`，以及必要的数据库补丁或部署 SQL。
- 同步冲突恢复逻辑：周期轮次在云端缺失时的重基创建与队列清理。
- 不改变普通事项计时、计时界面交互和单活动计时约束；不引入新的用户操作步骤。
