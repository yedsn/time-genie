# Design

## Context

参见 `proposal.md` 的问题说明。当前本地计时转换在事务内调用 `ensure_occurrence_if_recurring`，但排入 `timer_transition_apply` 的载荷只包含原计时、可选普通事项和新计时。云端 RPC 因而无法知道本地刚物化了周期轮次。后续周期状态操作根据本地已有版本发送更新，云端实体缺失时严格版本检查返回 `current version <NULL>`。

现有“分配今日预计”流程已经演示了正确的创建依赖：本地首次物化周期轮次时先排入 `task_occurrence` 创建，再让引用它的操作依赖该创建。计时转换还具有结束旧计时、开始新计时和清理未归属边界的原子语义，因此不能简单在 RPC 成功之后补写轮次。

## Goals / Non-Goals

**Goals:**

- 让首次开始周期事项计时时，云端计时事实与当日轮次在同一原子转换内建立。
- 保证已存在轮次的重复计时不改变轮次状态或版本。
- 让首次计时之后的完成、恢复操作拥有连续可提交的云端版本基础。
- 安全恢复已经形成的“本地有轮次、云端不存在”冲突。
- 保留现有多设备计时先到事实优先、单活动计时和幂等操作语义。

**Non-Goals:**

- 不改变周期规则的生成、匹配或编辑语义。
- 不改变普通事项开始计时、结束计时和前端按钮交互。
- 不对云端确实存在竞争版本的周期轮次做无条件覆盖。
- 不引入持续上传经过时间或计时写入权。

## Decisions

### 1. 在 `timer_transition_apply` 中携带可选周期轮次

本地计时事务在调用 `ensure_occurrence_if_recurring` 前读取原有轮次；只有“此前不存在、调用后新建成功”时，才把完整 `task_occurrence` payload 放入计时转换载荷。云端 RPC 在写入新活动计时前，以创建语义应用该轮次。所有写入继续共用同一操作 ID、数据库事务和幂等结果。

选择该方案是因为计时转换本身已经是跨多个实体的原子业务边界。若改成独立 outbox 创建操作，则需要额外表达计时转换对轮次创建的依赖，并处理其中一个已发送、另一个尚未发送的中间状态；这会扩大竞态面。

当轮次早已存在时，载荷不携带它，避免开始计时意外重开已完成轮次或无意义增加版本。

### 2. 云端对周期轮次采用幂等创建和等价跟随

云端收到可选轮次时：

- 若实体不存在，要求 payload 为初始版本并创建。
- 若实体已存在且关键身份一致，则保留先到轮次，不推进版本；计时转换继续按现有先到事实收敛规则处理。
- 若实体身份或内容存在不可解释冲突，则拒绝转换，避免把错误日期或事项绑定到计时。

该行为允许两台设备几乎同时首次物化同一轮次，同时不把第二次等价创建变成用户可见冲突。替代方案是直接调用通用严格创建补丁，但它会在第二台设备提交时返回“预期新实体”的冲突，不符合已有计时事实的跟随模型。

### 3. 周期轮次云端缺失时允许重基为创建

冲突处理的 `keep_local` 路径目前拒绝所有“本地是更新、云端不存在”的实体。调整为仅对 `task_occurrence` 放行：使用同实体最新本地 payload，把版本重写为 1、基础版本置空、状态改回 pending，并清理已被最终 payload 覆盖的同实体后继操作。

此恢复使用完整本地最终快照，因此恢复的是用户当前看到的最终状态，而不是依次伪造丢失的 v1、v2、v3。通用云端应用逻辑已允许新建周期轮次使用版本 1；其他实体仍维持“云端删除不可覆盖”的保护。

自动恢复可在识别到明确的 `current version <NULL>` 周期轮次冲突时复用同一重基函数；若现有发送架构不适合在失败处理阶段安全读取云端快照，则至少保证用户选择“保留本机”可一次修复并继续排空队列。规格要求的自动恢复应通过针对缺失轮次错误的受限分支完成，不扩展到普通删除冲突。

### 4. 同步后的本地版本以云端结果校准

计时转换返回值增加可选周期轮次结果，使客户端在操作成功或跟随既有事实时，用云端权威轮次校准本地记录。这样并发首次创建时，即使另一设备先到，本机也不会继续持有与云端不一致的初始版本或状态。

若现有通用增量拉取会在同一次成功处理后立即覆盖该实体，也仍保留 RPC 返回字段，避免成功响应与下一次拉取之间出现后继操作使用错误基础版本的窗口。

## Risks / Trade-offs

- [风险] 已部署客户端向旧版云端 RPC 发送新字段时旧云端会忽略字段，问题仍可能发生。 → [缓解] 先部署兼容新字段的云端函数，再发布客户端；云端函数对缺少字段的旧客户端保持兼容。
- [风险] 等价首次创建判断过宽可能吞掉真实状态差异。 → [缓解] 只允许相同工作空间、事项和日期的轮次身份等价；已有状态和版本由先到云端事实保留，不用后到 payload 覆盖。
- [风险] 把历史最终状态重基为版本 1 会丢失本地中间版本历史。 → [缓解] 周期轮次版本是并发控制信息，业务最终状态、完成时间、来源和更新时间保留；操作历史仍保留原用户动作记录，重基只修复同步队列。
- [风险] RPC 返回结构变化影响旧客户端。 → [缓解] 仅新增可选 `occurrence` 字段，不删除或改名现有字段。
- [风险] Schema 与独立补丁文件不一致。 → [缓解] 同时更新 `supabase/schema.sql` 和新的日期补丁，并运行 schema 集成验证。

## Migration Plan

1. 部署向后兼容的 Supabase SQL 补丁，为 `timer_transition_apply` 增加可选周期轮次处理与返回字段。
2. 发布客户端，使首次周期计时携带轮次，并消费云端返回结果。
3. 客户端启动或同步重试时识别既有缺失轮次冲突，将安全范围内的 `task_occurrence` 更新重基为创建。
4. 若需回滚客户端，云端新增字段保持可选，旧客户端仍可调用；若需回滚云端，应先停止发布携带轮次的新客户端，避免重新产生遗漏。
