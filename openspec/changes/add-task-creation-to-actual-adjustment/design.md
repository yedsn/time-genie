# Design

## Context

本变更依赖 `add-quick-actual-time-adjustment` 所定义的调整面板、快照、批量调整事务和 `actual_time_adjustments` 实体。现有事项创建支持主体、可选父项、计划日期和两级层级，并在云模式下把事项变化写入 outbox，但每次事项创建与实际调整目前是独立命令和独立事务。

调整面板中的新增事项在确认前必须只是客户端草稿；确认后事项和对应初始调整又必须作为一个业务批次原子落库。该要求不能通过前端依次调用现有“创建事项”和“调整实际”两个命令满足，否则第二步失败会留下孤立事项。

## Goals / Non-Goals

**Goals:**

- 复用现有事项名称、父级、层级和同步校验语义。
- 用客户端草稿标识在一个请求中关联新事项和其初始调整。
- 让新增事项、现有事项调整、新事项调整和 outbox 原子提交且可幂等重试。
- 保持新事项同步先于引用它的实际调整。

**Non-Goals:**

- 不在面板内提供完整事项属性编辑；除名称、父级、当天计划日期和目标实际外，其他字段使用默认值。
- 不在本变更中支持新建父事项或多层草稿树；新事项只能是顶层叶子或现有有效父事项的子项。
- 不允许草稿引用另一个草稿作为父事项。
- 不替代计划页现有完整新增、排序、备注、重复规则等编辑流程。

## Decisions

### 1. 在调整批量请求中携带事项草稿

扩展调整批量请求，增加 `new_tasks`：

- `client_task_id`：仅在本批请求内使用的稳定草稿标识。
- `title`。
- `parent_id`：只能引用当前主体内的现有事项。
- `target_minutes`：0 到 1440 的整数。
- `expected_parent_version`：选择父项时的版本；顶层事项为空。

现有事项调整继续使用正式 `task_id`。新事项初始调整不由前端猜测服务端 ID，而由服务端创建事项后使用 `client_task_id -> task_id` 映射生成。

备选方案是前端先创建事项再提交调整。它无法满足整批回滚，并在网络响应丢失时更容易重复创建，故不采用。

### 2. 只允许引用现有父事项

新事项可以作为顶层事项，或作为现有有效顶层事项的子项。暂不支持在同一面板新建“父事项 + 子事项”的草稿树，也不支持把一个草稿选为另一个草稿的父级。

这样能够沿用当前最多两级的模型，避免在单批请求中增加草稿拓扑排序、循环检测和父草稿失败传播。用户若需要新的分组结构，仍可在完整计划编辑器中创建。

### 3. 服务端复用事项校验，但共享同一个事务

把现有事项创建中的标题、主体、父级、重复事项、直接实际时间、深度和排序计算抽成可在传入事务上运行的内部逻辑。调整批量命令先完成所有只读校验，再在同一 SQLite 事务中：

1. 依请求顺序为草稿生成正式事项 ID，状态为 `open`，计划日期为工作日期，来源标记为调整面板快速创建。
2. 创建所有非零的新事项正向调整和既有事项正负调整。
3. 更新全局修订并写入任务、调整记录对应的 outbox。
4. 写入批次幂等结果，其中包含每个 `client_task_id` 对应的正式事项 ID。

任一步失败则回滚。目标为 0 的草稿只生成事项和事项 outbox，不生成调整实体。

### 4. 父项并发校验使用版本和资格重验

快照返回的可选父项包含版本。提交时服务端验证父项仍属于当前主体、未删除、位于顶层、不是重复事项、没有会阻止转为分组的直接实际时间，并匹配 `expected_parent_version`。任一父项失效时整批冲突，前端保留草稿并提示重新选择。

顶层新增不依赖某个父项版本，但仍受当前主体有效性约束。普通计时增长若使所选父项出现直接实际时间，则父项资格改变，批次必须拒绝，而不是把同一事项同时作为计时叶子和分组父项。

### 5. 草稿只存在于面板本地状态

点击新增时生成客户端草稿 UUID，默认名称为空、父级为空、目标分钟为 0。面板合计逻辑把草稿目标加入目标合计，但当前实际始终按 0 计算。关闭面板直接丢弃草稿，不调用后端。

摘要采用两类行：

- “新增事项”：显示名称、顶层或父项路径、目标和初始正向调整；目标为 0 时显示仅新增。
- “实际调整”：沿用既有事项的基线、目标和正负差额。

### 6. outbox 使用显式依赖顺序

同一事务内先入队事项创建，再入队引用事项的调整创建。调整 payload 保存正式 `task_id`，并通过 outbox 的实体依赖或队列排序保证远端应用前事项已存在。批次幂等记录防止重试重复产生两组实体。

云端原子批量路径同样应创建事项后再创建调整；如果现有同步仍按单实体上传，远端要允许事项成功后调整暂时待重试，并保证重复 upsert 幂等。

## Risks / Trade-offs

- **调整命令同时承担事项创建，领域边界变宽** → 复用事项领域的事务内校验/插入函数，不复制校验规则，外部仍只暴露面向用户意图的批量命令。
- **父项资格在面板打开后改变** → 提交时重验版本和资格，整批拒绝并保留草稿。
- **事项已同步而调整暂时未同步造成短暂不一致** → 明确 outbox 依赖，调整保持待重试；远端最终收敛且不会重复创建事项。
- **只支持现有父项限制快速建树能力** → 保持面板轻量；复杂层级留给完整计划编辑器。
- **目标为 0 的新事项没有时间历史行** → 摘要明确“仅新增”，保存后它出现在计划页但不出现在时间记录页。

## Migration Plan

1. 先实施并验证 `add-quick-actual-time-adjustment` 的数据模型和批量调整能力。
2. 扩展批量命令请求和事务内事项创建逻辑；不新增持久化表，仅可能增加来源枚举/约束支持。
3. 扩展前端草稿、摘要与父项选择界面。
4. 增加本地、云端和双设备测试后发布。

旧客户端不会发送 `new_tasks`，后端将缺省值视为空数组，因此保持兼容。回滚到旧版本时，已经创建的事项和调整仍是普通有效数据，只是不再能从该面板创建新事项。
