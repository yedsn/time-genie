# Design

## Context

见 `proposal.md` 的问题说明。当前计时模块采用本地优先写入：开始、暂停、继续、结束和归属确认都会修改 SQLite 中的完整 `time_entry` 实体，并把当时的完整实体镜像加入 `sync_outbox`。云端 `cloud_apply_patch` 要求 `payload.version = base_version + 1`，同一实体后续操作只有前序成功后才能继续。

前端秒级计时已经通过本地 `Date.now()` 与已保存状态计算；5 秒刷新主要读取 SQLite。冲突风险不来自每秒显示，而来自同一实体在短时间内产生多条版本操作，以及后台推送、快照拉取和用户继续编辑之间的时序。

另一个约束是 `time_entry` 的同步镜像包含时间片、归属和工作日信息，归属确认还可能产生独立的 `task` 或 `task_occurrence` 操作。因此压缩队列不能简单删除所有中间行，必须区分实体最终状态、操作幂等边界和跨实体副作用。

## Goals / Non-Goals

**Goals:**

- 让计时显示和前台操作始终以本地事务为准，不受同步延迟阻塞。
- 自动协调当前设备对同一计时记录产生的连续未发送版本。
- 保持开始、暂停、继续、结束和归属的最终状态完整，避免丢失时间片或重复分钟。
- 把可解释的本机版本链与真正的远端并发更新区分开。
- 让手动同步一次排空可发送的计时最终状态。

**Non-Goals:**

- 不取消计时数据的云端同步，也不把云端降级为仅备份归属结果。
- 不采用最后写入胜出，不允许客户端跳过未知云端版本。
- 不重新设计计时页面、归属确认界面或事项完成规则。
- 不在本变更中解决当前已存在的历史事项完成/取消完成冲突；仅保证新的计时相关操作不继续制造同类伪冲突。
- 不实现多设备同时操控同一活动计时；现有设备租约和单活动计时约束继续生效。

## Decisions

### 1. 保持秒级显示为纯派生状态

运行中的显示时间继续由本地记录的累计秒数、当前时间片开始时间和 `Date.now()` 派生。定时读取不得更新 `time_entries.version`，也不得调用入队接口。后端只有用户执行离散动作时才持久化版本。

备选方案是按固定周期把累计时间写入云端，以便其他设备看到实时秒数。该方案会显著增加写入和冲突，并与本地优先目标相悖，因此不采用。其他设备只需要看到最近一次同步的活动状态和开始时间，也可自行派生显示。

### 2. 在 outbox 入队阶段协调同实体未发送操作

为 `time_entry` 增加专用的入队协调策略。新操作入队前检查同工作空间、同实体且状态为 `pending` 或可确认未发送的前序操作：

- 若前序是新建操作且从未发送，保留其创建基线 `base_version = NULL`，用最新完整实体镜像替换 payload，并保留一个可代表最终状态的操作。
- 若前序建立在已知云端版本上且从未发送，可把 payload 更新为最新完整镜像，并保留最早可验证的云端基线；发送端允许 payload 版本跨越多个纯本地版本，但必须确认这些中间版本全部属于当前设备的同实体待同步链。
- 若前序状态为 `sending`、`conflict`，或操作结果未知，不执行压缩；后续操作继续排队并等待该边界被解析。
- 不跨越其他设备产生的快照版本，也不跨越已成功提交但本地尚未完成确认的幂等操作。

这要求云端版本校验支持“已验证本地连续链的最终 payload 版本高于 `base_version`”，不能继续强制所有完整镜像只能增加 1。放宽必须限定于具备客户端链证明的请求，避免普通请求借此跳过未知版本。建议在 outbox 操作中保存或传递 `local_version_span`/`previous_operation_id` 等证明信息，而不是只靠 payload 版本猜测。

备选方案是完全不压缩、只严格顺序发送。它理论上正确，但网络中断后会保留大量中间状态，且现有问题说明严格链在本机仍可能因发送与快照时序进入冲突，因此需要显式协调。

### 3. 业务副作用与实体快照分开保留

计时状态操作最终都通过完整 `time_entry` 镜像表达，因此开始、暂停、继续、结束和归属的中间实体镜像可以在满足条件时压缩。以下内容不能随镜像压缩而丢失：

- `timer.started`、`timer.stopped` 等本地自动化事件的幂等记录。
- 归属确认触发的 `task`、`task_occurrence` 独立实体操作。
- 用户可见的待确认记录 ID 和已经提交的本地归属。

Hook 继续在本地事务完成后发布，不依赖每条 outbox 行是否最终发送。任务完成操作保留独立队列项，并通过实体键建立发送依赖。

### 4. 为跨实体操作引入轻量依赖关系

归属确认产生的时间记录更新应先发送；同一次确认产生的事项或周期事项完成操作在该时间记录成功后才可发送。依赖只用于发送顺序，不把多个实体合并成一个云端事务，因为现有 `cloud_apply_patch` 以单实体为边界，改为跨实体 RPC 会扩大迁移和失败恢复复杂度。

推荐在 outbox 增加可空的 `depends_on_operation_id`，或使用等价的本地依赖表：

- 普通独立操作依赖为空。
- 归属产生的 task/task_occurrence 操作依赖最终的 time_entry 操作。
- 领取队列时只有依赖操作已删除或标记成功，当前操作才可领取。
- 如果 time_entry 操作被压缩，依赖指向压缩后的保留操作。

备选方案是依靠 `created_at` 顺序。全局时间顺序不能表达“不同实体中只有这一组有依赖”，也会让无关事项被不必要地阻塞，因此不采用。

### 5. 拉取快照不得覆盖本地活动计时和待确认结果

现有快照导入已经保存本地活动计时覆盖层。本变更扩展保护条件：同一 `time_entry` 只要存在 pending/sending/failed/conflict outbox，或者刚结束且仍待归属确认，就不得被较旧或等版本云端快照覆盖。队列完全清空后再以云端快照确认最终状态。

如果云端快照包含更高且无法由本地操作链解释的版本，仍进入冲突处理，不自动覆盖本地或云端。

### 6. 冲突分类基于实体和可解释版本链

发送失败时记录：实体类型、实体 ID、本地动作类型、基线版本、payload 版本、云端当前版本以及是否存在本地前序链。

- 本地链可解释：恢复或重新协调队列后自动重试，不增加用户可见冲突计数。
- 网络、认证或结果未知：保持 pending/failed，停止当前发送批次。
- 云端未知版本：标记 conflict，并沿用“使用云端/保留本地”处理。

冲突界面可继续使用现有结构，但详情应能说明冲突属于时间记录、事项或周期事项，避免用户把事项完成冲突误认为计时冲突。

### 7. 保持手动同步和后台同步的不同预算

后台同步继续每轮处理可领取批次，避免长时间持锁。手动同步持续排空队列，并在每轮重新计算压缩和依赖就绪状态。两者都遵守同一实体顺序、依赖关系和停止条件。

## Risks / Trade-offs

- [压缩完整镜像时丢失中间时间片] -> 只使用最新 SQLite 完整实体镜像替换 payload，并针对暂停/继续后的 segments 做结构化回归测试。
- [放宽 payload 版本检查被滥用] -> 云端只接受带可验证连续链证明的跨版本 payload；没有证明时保持 `base + 1` 校验。
- [发送结果未知时错误压缩] -> `sending` 和结果未知操作形成硬边界，先通过操作幂等查询或重试确认，再处理后续队列。
- [跨实体依赖导致队列永久阻塞] -> 依赖操作成功删除时视为满足；被用户选择“使用云端”删除时同步清理或重新挂接依赖，并增加孤儿依赖检查。
- [快照长期无法拉取] -> 本地业务继续可用；队列清空后自动拉取，设置页仍提供手动同步和重置本地数据入口。
- [旧客户端不认识新的 SQL 参数或字段] -> 云端函数以兼容参数或新增函数版本发布，先部署云端兼容能力，再发布客户端。
- [计时结束成功但事项完成冲突] -> 将时间记录成功与事项冲突分开呈现，避免回滚或重复提交已经成功的时间归属。

## Migration Plan

1. 增加本地 outbox 依赖和版本链元数据迁移，旧记录默认无依赖、单版本跨度，保持原发送语义。
2. 更新 `supabase/schema.sql` 并生成可重复执行的补丁 SQL，为跨本地版本镜像提供受约束的校验能力；先在服务器执行 SQL。
3. 发布客户端入队协调和依赖领取逻辑；旧客户端仍可按原 `base + 1` 方式调用云端函数。
4. 对升级时已有的 pending 队列不做破坏性自动压缩；首次同步时只对可证明未发送且链完整的同实体操作执行协调。
5. 回滚客户端时保留新增列，旧代码忽略它们；云端兼容函数继续接受旧请求。不得通过回滚删除用户尚未同步的 outbox 数据。
